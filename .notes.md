# Root R6 — async-let not registered in analyzer scope (strict-flip false positive)

## Symptom
Under `TypeDiagnosticMode::Strict`, a valid program of the shape

```shape
async fn run() -> int {
    async let x = fetch_value()
    let y = await x        // <- strict checker: "Undefined variable: 'x'"
    return y
}
```

is wrongly rejected with `Undefined variable: 'x'`. The program is VALID — it ran
under baseline ReliableOnly; the compiler + VM bind `x` correctly. Only the strict
analyzer scope had the gap.

## Root cause (located)
`crates/shape-runtime/src/type_system/inference/expressions.rs:1082`

`async let x = expr` is represented as an EXPRESSION (`Expr::AsyncLet`), not a
statement. The inference arm was:

```rust
Expr::AsyncLet(async_let, _) => self.infer_expr(&async_let.expr),
```

It inferred the inner expr's type but NEVER called `self.env.define(name, ...)`,
so the binding name was never registered into the analyzer scope. A later sibling
`await x` resolves `x` via `Expr::Identifier` -> `self.env.lookup("x")`
(expressions.rs:48-79), finds nothing, and raises `TypeError::UndefinedVariable`.

`async let` is statement-positioned (no let-in body): its binding must be visible
to the SIBLING statements that follow, so the name registers into the CURRENT
scope — unlike `Expr::Let` (expressions.rs:701) which pushes/pops a fresh scope
around a `body`.

## Fix
Register the binding into the current scope after inferring the inner type:

```rust
Expr::AsyncLet(async_let, _) => {
    let inner_type = self.infer_expr(&async_let.expr)?;
    self.env.define(&async_let.name, TypeScheme::mono(inner_type.clone()));
    Ok(inner_type)
}
```

type_system only. No touch to mir/solver.rs, mir/storage_planning.rs,
executor/snapshot.rs.

## Why this is a CORRECTED checker, not a blanket suppression
The fix registers ONLY the name that async-let actually binds. A genuinely-wrong
program of this shape STILL errors:

  - `async let a = fetch_a(); let v = await nonexistent`
    -> STILL "Undefined variable: 'nonexistent'" (verified).

`is_broad_suppression` does not apply — there is no error-swallowing.
