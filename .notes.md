# R3 — enum function-type not-compatible-with-itself (strict-flip false positive)

## Symptom
Under `TypeDiagnosticMode::Strict`, a valid program calling a fn that takes/returns
an enum was rejected with an absurd self-incompatibility:

```
Could not solve type constraints:
  (Color) -> string is not compatible with (Color) -> string
```

Valid under baseline `ReliableOnly`; strict's checker wrongly rejected it.

## Root cause (TWO facets, both in type_system/)

### Facet 1 — Basic/Reference nominal-name mismatch in constraint solver
`crates/shape-runtime/src/type_system/constraints.rs` `unify_annotations()`.

The same enum `Color` is carried as `Basic("Color")` at one site (the resolved
declaration param) and `Reference(TypePath{ qualified: "Color" })` at the call
site. The `(Basic, Reference) | (Reference, Basic)` cross arm compared the WHOLE
annotation with `ann1 == ann2`, which is `false` across variants (`Basic` != a
`Reference` struct) even when the names agree. The two `(Color)->string`
function types then failed to unify.

Confirmed via instrumented Debug dump:
```
L = Function { params: [Concrete(Basic("Color"))],            returns: Basic("string") }
R = Function { params: [Concrete(Reference(TypePath{"Color"}))], returns: Basic("string") }
```

Fix: compare by nominal name via `TypeAnnotation::as_type_name_str()`, not by the
variant tag. Distinct names (`Basic("Color")` vs `Reference("Dir")`) still fail.

### Facet 2 — tail-expression return not recognized (MissingReturn FP)
`crates/shape-runtime/src/type_system/checker.rs` `has_return_statement()`.

Once facet 1 was fixed, the real blocker for the 51 tests surfaced: every enum
function whose body is a tail `match` (no explicit `return`) was rejected with
`Function 'name' must return a value`. `has_return_statement` only recognized
explicit `Statement::Return`, if-both-branches, and while/for — it did NOT model
Shape's tail-expression return at all (`fn f() -> int { 42 }`,
`fn g(c) -> string { match c { ... } }`, `fn h(b) -> int { if b {1} else {2} }`
all returned a value with NO `return` keyword).

This was masked under `ReliableOnly` by the dropped `should_emit_type_diagnostic`
allowlist (`compiler_impl_initialization.rs:863`, now hard-`true` under strict-flip).

Fix: added `block_yields_tail_value` / `block_items_yield_tail_value` /
`expr_yields_tail_value` helpers. A value-producing TAIL statement satisfies the
requirement; tail `if`/`match`/block recurse so every branch/arm must yield a
value. `Expr::Unit` and one-armed `if` (else None / synthesized Unit) correctly
do NOT satisfy a non-void return — so genuine MissingReturn still fires.

## Correctness (NOT a blanket suppression)
- TP3: `name(Dir::North)` where `name(c: Color)` STILL rejects
  → `(Color) -> string is not compatible with (Dir) -> string`.
- TP4: body ending in `let` STILL rejects (`void is not compatible with int`).
- TP5: one-armed `if` as tail STILL rejects (`must return a value`).
- TP1: non-bool in `if` STILL rejects (`int is not compatible with bool`).
- TP2: if/else branch mismatch STILL rejects (`int is not compatible with string`).
