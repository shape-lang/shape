# R4: named-struct vs structural-object unification (strict-flip false positive)

## Symptom
Strict mode (`TypeDiagnosticMode::Strict`) wrongly rejected valid programs that
pass a named struct to a fn param / return it:

```
({ x: number, y: number }) -> number is not compatible with (Point) -> number
```

The program is valid and ran under baseline `ReliableOnly`.

## Root cause
A struct definition `type Point { x, y }` is registered as a *type alias*
mapping the name to its structural object shape
(`inference/items.rs:110` + `:194` `define_type_alias(name, Object(fields))`).

- A declared param `fn f(p: Point)` resolves through that alias to
  `TypeAnnotation::Object([x, y])`.
- A `Point { .. }` literal stays nominal: `infer_struct_literal_type`
  (`inference/expressions.rs:1134`) returns `TypeAnnotation::Reference("Point")`.

At the call site (`inference/access.rs:656`) the constraint
`func_type ~ expected_func_type` becomes `Object([x,y]) ~ Reference("Point")`.
`ConstraintSolver::unify_annotations` (`constraints.rs`) had **no arm** for
`Object ~ Basic/Reference(named struct)` — it fell through to `_ => Ok(false)`,
producing the spurious "not compatible" error.

## Fix (type_system only)
`crates/shape-runtime/src/type_system/constraints.rs`
- New `struct_schemas: HashMap<String, Vec<ObjectTypeField>>` on `ConstraintSolver`
  + `set_struct_schemas` setter (mirrors `set_method_table`/`set_trait_impls`).
- New `unify_annotations` arm: `Object ~ Basic(name)` / `Object ~ Reference(path)`
  (both directions) resolves the struct's fields via `struct_fields(name)` and
  delegates to the existing **exact-match** `object_fields_compatible`
  (equal field set + per-field unification). Gated on `name` being a registered
  struct schema — non-struct names still fall through to `_ => Ok(false)`.

`crates/shape-runtime/src/type_system/inference/mod.rs`
- Before solving, build `struct_schemas` from `self.struct_type_defs`
  (excluding comptime fields, matching the alias construction in `infer_item`/
  `predeclare_struct_type`) and pass to `solver.set_struct_schemas`.

## Why this is a CORRECTION not a suppression
Field comparison stays exact:
- Wrong struct (`Other{a,b}` into `Point` param): STILL rejected
  ("({ x: number, y: number }) -> number is not compatible with (Other) -> number").
- int-into-number-field mutation (`p.x = 10`): STILL rejected.
- Unregistered name + structural object: STILL no unification.
Covered by new unit test `test_named_struct_unifies_with_structural_object`
(positive both directions + 2 negatives).
