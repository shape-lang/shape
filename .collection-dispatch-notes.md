# Collection-Method-Dispatch strict-flip FP — root analysis + fix

## Repro (strict CLI, `target/debug/shape run`)
- `[1,2,3].map(|x| x*2)`        → `Type constraint violation: Concrete(Array(Basic("int"))) cannot have fields`
- `let a=[1,2,3]; a.first()`    → `Method 'first' not found on type 'Vec'`
- `"hi".split(" ")`             → `Method 'split' not found on type 'string'`
- `a.length` / `[1,2,3].length` → WORK (handled by `is_length_bearing_type` short-circuit in access.rs:69)

The two surfaced messages are TWO FACES OF ONE ROOT. For a `Concrete(Array(...))`
receiver the method-call fallback in `inference/expressions.rs::Expr::MethodCall`
pushes BOTH a `HasField` constraint (via `infer_property_access`, access.rs:222)
AND a `HasMethod` constraint (expressions.rs:565). Which message wins is
constraint-solve-order: `HasField` on a non-object → constraints.rs:694
"cannot have fields"; `HasMethod` on Array → constraints.rs:872 maps the receiver
to type_name "Vec", lookup misses, constraints.rs:878 "Method not found on 'Vec'".

## ROOT (why resolution fails)
`Compiler::compile` (compiler_impl_reference_model.rs:1355) runs the strict
type-checker over `analysis_program` = the USER file only (desugared +
annotation-extend-augmented). It does NOT include the stdlib prelude `.shape`
items. `analyze_program_with_mode` → `TypeChecker::new()` →
`TypeInferenceEngine::new()` → `MethodTable::new()` which registers ONLY the
3 universal methods (`type`/`to_string`/`toString`). The Vec/string/HashMap
method signatures live in stdlib `extend Vec<T>` / `extend string` /
`extend HashMap<K,V>` blocks (crates/shape-runtime/stdlib-src/core/{vec,
string_methods,hashmap_methods}.shape) — registered into the MethodTable only
when those items pass through `register_extend`/`register_impl` at inference
time. The strict analysis engine never sees them, so
`MethodTable::resolve_method_call` returns `None` for every collection method
→ falls to the HasField/HasMethod error path.

Runtime works (programs run under baseline) because the actual bytecode
`.method()` dispatch goes through shape-vm's PHF method registry, NOT the
type-checker MethodTable. Baseline (`ReliableOnly`) suppressed these via
`should_emit_type_diagnostic`; strict emits them → ~500 FP.

## FIX
Seed `MethodTable::register_builtin_methods` (the existing builtin-seed seam,
same place the universal methods are registered) with the canonical builtin
collection-method signatures for `Vec`, `string`, `HashMap`, mirroring the
stdlib `.shape` definitions. Generic/closure-taking methods use
`GenericMethodSignature` (TypeParamExpr trees); monomorphic ones use plain
`MethodSignature`.

This is a CORRECT RESOLUTION, not a blanket suppression: a genuinely-unknown
method on a collection (e.g. `[1,2,3].frobnicate()`, or `contains` which is NOT
a stdlib Vec method) is still absent from the table → still errors. The 41
true-positive wins (non-bool-in-if; if/else branch mismatch) are untouched —
those never depended on collection method resolution.

sub_roots = 1 (single seam: incomplete builtin MethodTable; the two messages
collapse to it).
