## 1. Goals & non-goals

### Goals

1. **A foreign-function-bearing program survives every movement the runtime offers.** `fn python` / `fn typescript` / `extern C fn` code can be (a) transferred per-function to a remote node and executed there, (b) snapshotted between foreign calls, (c) resumed on the same or another node — each with defined, user-legible behavior in every failure mode.
2. **One identity story.** A foreign function has exactly one content-addressed identity, agreed on by every node: the sender, the receiver, the snapshot store, and the linker all key on the same `ForeignFunctionEntry.content_hash`, whose coverage is fixed here (§4.1).
3. **Extensions are declared node capabilities, never assumptions.** A blob states what language runtimes (and versions) it needs; a receiver/resumer resolves or refuses with a clean `CapabilityUnavailable{sub_kind}` (remote) / `SnapshotCapabilityMissing{sub_kind}` (resume; concretely `SnapshotError::CapabilityMissing`) — never a panic, never a silent local fallback.
4. **The snapshot barrier rule at foreign frames is a single, ratified rule** consumed identically by WF-2A and WF-2B: foreign runtime state is opaque and NEVER serialized; a live foreign frame refuses `snapshot()` with a clean error (§4.5).
5. **The Ffi permission travels and is enforced four times**: baked into the blob content hash at compile time, unioned by the linker, checked by the receiving/resuming node at load time, and checked again at every foreign call on the executing node (§4.6).
6. **No new value carriers.** Composition happens entirely at the metadata layer (hashes, manifests, capability matching, permission sets). Every value continues to cross boundaries on the carriers the sibling designs already fixed: `KindedSlot`/`NativeKind` runtime-side, `SerializableVMValue` + parallel kind tracks on the wire, msgpack on the extension side per ADR-006 §2.7.5/§2.7.29. This doc adds **zero** marshal machinery.
7. **Where a sibling doc's choice blocks composition, this doc names it and proposes the amendment** (§4.10) — no silent contradiction.

### Non-goals

- **Shipping extension binaries or native libraries over the wire.** Extensions and `.so`s are installed artifacts (via `shape ext install` / the host package manager), never network payloads. A node that lacks one refuses cleanly.
- **Serializing foreign runtime state** (Python interpreter heap, V8 isolates, C process state). Ruled out by ffi-rebuild §5-R11 and snapshot-resume §5.8; restated here as the foundation of the barrier rule.
- **Cross-node foreign *callback* continuity** (a C callback into Shape surviving transfer). For callbacks invoked *during a live foreign frame*, the barrier makes the case unreachable (no snapshot ever contains a foreign frame). **Dormant registrations** — a C library that stored a Shape callback at registration time for later invocation (ffi-rebuild §4.6.6 pattern) — are live cross-call state with no live frame; they are process-local and do NOT survive resume. That loss is *surfaced*, never silent: registration count recorded in the manifest, one-time resume notice, book caveat (§4.5, OQ-3).
- **Distributed scheduling/placement of foreign work.** `@remote` takes an explicit address (WF-2C non-goal, inherited).
- **Arrow IPC / bulk-data paths** — same deferral as ffi-rebuild (its Open Question 8).
- **Provisioning or verifying the foreign-language *environment*** — the Python packages a `fn python` body imports, the deno module cache, the interpreter version. These are not Shape-visible declarations; §4.4.4 defines the surfaced failure behavior, ships the diagnostics (ping/manifest `backend`), and requires the book caveat (§6 F5). Declared environment constraints are Open Question 8 — not invented here without ratification.

## 3. Constraints (binding, quoted)

1. **CLAUDE.md §Forbidden Patterns** — "*`ValueWord` at runtime. Deleted. Do not reintroduce as a 'shim', 'bridge', 'compatibility layer', or 'serialization helper'. Snapshot/wire uses per-slot kind metadata.*" Refusal regex `(decode|tag|kind|dispatch|value.call|closure.callback|frame.setup|callee|capture) (bridge|probe|helper|hop|translator|adapter|shim)` applies to every name in this design. Named components here — `ForeignEntryObject`, `ExtensionReq`, `NodeCapabilitySet`, `resolve_extension_requirement` — are stores, requirement records, and resolution functions, not boundary translators.
2. **ADR-006 §2.7.5 (cross-crate ABI policy):** "*stable ABI surfaces (extension contracts, persisted formats, FFI handoffs to non-Rust callers) stay on raw bits + parallel `NativeKind`. Internal Rust dispatch … uses `KindedSlot`.*" Foreign entries and manifests are persisted formats; values inside requests/snapshots ride `SerializableVMValue` + parallel `NativeKind` tracks (§2.7.7/Q9), exactly as WF-2B/WF-2C already specify. Nothing here adds a wire value form.
3. **ADR-006 §2.7.29 (foreign-marshal protocol):** declared types are the only oracle; "*the wire bytes are NOT free to re-discriminate*"; forbidden: "*`ValueWord` revival 'for the wire'*", "*tag-bit dispatch reintroduction under any rename*". Remote invocation of a foreign function marshals **twice** (Shape wire → receiver VM; receiver VM → extension msgpack) and both crossings use the already-designed protocols unchanged.
4. **ADR-006 §2.7.4 (surface-and-stop):** every not-yet-covered cell in the composition matrix surfaces a structured error naming the gap — never a placeholder execution.
5. **ADR-006 §2.7.8/Q10:** no Bool-default kinds anywhere; foreign-call args on the receiver come from `frame_descriptor` kinds exactly as WF-2C's `run_remote_call` template already does (`remote.rs:694-897`).
6. **Sibling-design decisions are inputs, not re-litigated:** ffi-rebuild's lazy linking (§4.2), shared `invoke_foreign_kinded` core (§4.9), `Ffi` permission shape (§4.8), vtable `runtime_descriptor`/`state_model` (§4.7); snapshot-resume's CodeManifest (§4.3), barrier framework (§4.6.1); distributed-transfer's verify-then-cache blob protocol (§4.3) and never-trust-the-sender permission story (§4.6). Where composition requires changing one of them, the change is an explicit named amendment (§4.10).
7. **Fix-plan §0 rules:** StructuredOutput ≤6 fields for workflow agents; adversarial refuters for every "fixed" claim; book truth-gate as checkpoint regression; toolchain via `direnv exec`.

### 4.1 Foreign function identity — exactly what the content hash covers

Two nodes agree a foreign function is "the same function" iff its `content_hash` matches. Ratified coverage (current `compute_content_hash` at `core_types.rs:198-228` + the ffi-rebuild §4.7 stage-0 fix + this doc's completions):

**IN the hash (function identity — changes any of these, you have a different function):**

| Field | Why |
|---|---|
| `language` | `fn python f` ≠ `fn typescript f` with identical bodies |
| `body_text` | the source is the function |
| `param_types`, `return_type` | the Shape-side call ABI; drives marshal arm selection (§2.7.29 declared-type oracle) |
| `param_names` *(ffi-rebuild §4.7 addition)* | visible to the foreign body as binding names — semantics-bearing for python/TS |
| `is_async` *(ffi-rebuild §4.7 addition)* | changes invoke integration |
| `native_abi.{abi, library, symbol, signature}` (extern C) | the *declared* library alias + symbol + C signature are the function's contract. **Ratified rule (NOT true at HEAD — amendment A7 makes it true):** `NativeAbiSpec.library` stores the **declared alias** and the hash covers the alias; resolution to a concrete path/soname is deferred wholly to the *executing* host. At HEAD the entry instead stores the compile-host-**resolved** string — `functions_foreign.rs:99-101` bakes `resolve_native_library_alias(...)` output into the entry (`#[cfg(target_os)]` sonames like `libc.so.6` vs `libSystem.B.dylib` at `:861-869`, package `load_target`s at `:880`, or `resolve_for_host()` results, possibly absolute paths, at `:890-892`), and `compute_content_hash` (`core_types.rs:216`) hashes that resolved string — so the *same declared function gets a different hash per compile host*, defeating portability and cross-node dedup. The compile-side fix (store the alias, resolve at link-now / load-verify per §4.4.3) is **hash-affecting** and rides the WF-2A stage-0 hash-stabilization window (A7, §4.10). |

**OUT of the hash (deliberately — each with its recovery mechanism):**

| Field | Why excluded | Recovered how |
|---|---|---|
| `name` | content addressing: two aliases of one body dedup. **Ratified rule: `name` is advisory, diagnostics-only — no load-bearing consumption anywhere.** The one load-bearing use at HEAD (`__ffi_{name}_return` schema lookup, `functions_foreign.rs:116`) is removed by keying the return schema on the content hash instead (§4.7) | entry record (diagnostics text only) |
| `arg_count` | derivable — never trusted from a wire/store object | **re-derived at assembly: `arg_count = param_types.len()`** (§4.2.1) |
| `dynamic_errors` | derived from the runtime's `ErrorModel` at link time (`core_types.rs:76-79`) | link-now re-derivation on the executing node (§4.2.1) |
| `return_type_schema_id` | **registry-local numeric id — ids never cross node boundaries** (§4.7; same rule that fixed comptime root cause B) | re-resolved by **hash-derived schema name** (`__ffi_h{hex16}_return`, §4.7) in the consuming registry |
| Extension version | node-capability constraint, not function identity (ffi-rebuild §4.7 / its Open Question 2). Putting it in the hash would invalidate every foreign blob on every extension patch release and make cross-version-compatible clusters impossible. | `ExtensionReq` matching (§4.3) |
| Extension ABI version | enforced by the loader gate at `.so` load (`loader.rs:112-143`), a node property | `NodeCapabilitySet` (§4.3) |
| Resolved library path, platform triple (extern C) | per-host facts | receiver-side `resolve_for_host()` + platform matching (§4.4.3) |

**Blob-level composition (correct only after §4.2.0):** `FunctionBlob.foreign_dependencies` is inside `FunctionBlobHashInput` (C3), so a Shape function that calls `fn python f` has a different blob hash than one calling a modified `f` — foreign source edits propagate into every dependent blob hash automatically. **But at HEAD this is not yet sound for transfer or for cross-program dedup** (C10): the `CallForeign` operand is a program-level positional index inside the hashed instruction stream, and the compiler's `sort()`+`dedup()` of `foreign_dependencies` discards the operand-index→hash correspondence. §4.2.0 canonicalizes both. `required_permissions ∋ Ffi` is already inside the blob hash (`content_addressed.rs:114` + ffi-rebuild §4.8.3) — that half needs no mechanism.

### 4.2 `ForeignEntryObject` — foreign entries become content-addressed store/wire objects

**The hoist that closes gaps C4 and C10.** `ForeignFunctionEntry` today only exists as a program-level `Vec` (C4), and `CallForeign` addresses it by a program-level positional index the linker never remaps (C10); per-function transfer and blob-graph snapshots need entries addressable by hash **and** an explicit operand-index↔hash correspondence. Design:

#### 4.2.0 Operand-index ↔ hash correspondence (the load-bearing mapping — fixes C10)

`Operand::ForeignFunction(u16)` is redefined from *program-level* index to **blob-local ordinal**, and the correspondence is made explicit and canonical:

1. **Blob build (compile side).** `foreign_dependencies` changes semantics from *sorted+deduped* to **ordered, first-use-deduped**: hashes appear in order of first occurrence in the blob's instruction stream (dedup preserves first-occurrence order — the `sort(); dedup()` at `compiler/mod.rs:481-482` is replaced). Simultaneously, every `CallForeign` operand in the blob's instructions is **rewritten at blob build** from the program-level index to the blob-local ordinal — the position of that entry's hash in this blob's `foreign_dependencies`. This mirrors how `Call`/`Constant::Function` references are hash-normalized at blob build; it is the same normalization applied to the one operand class that was missed. **Build invariant (new):** at HEAD an entry whose `content_hash` is `None` is *silently skipped* when collecting `foreign_dependencies` (`compiler/mod.rs:471-478`) — under the ordinal rewrite a skip would shift every subsequent ordinal. Hash presence becomes an enforced build invariant: every entry reachable from a `CallForeign` operand carries `Some(content_hash)` at blob build; a violation is an internal compile error, never a skip.
2. **Canonicalization corollary.** After (1), the hashed instruction stream contains only blob-local ordinals that are deterministic functions of the blob's own instruction sequence — a blob's content hash no longer depends on the origin program's foreign-table ordering, so identical functions compiled in different programs share hashes and cross-node blob dedup (WF-2C §4.3) is sound for foreign-bearing code.
3. **Link (every consuming node — local, receiver, resumer).** The linker gains a `ForeignFunction` remap: for each blob, blob-local ordinal → the linked program's `foreign_functions` table index, via the blob's ordered `foreign_dependencies` (ordinal → hash → assembled-table index). `Operand::ForeignFunction(_)` moves out of `linker.rs:190-203`'s "Unchanged operands" arm into the remapped set, exactly parallel to function-reference remapping. A hash in `foreign_dependencies` with no assembled entry is a structured link error (`LinkError::MissingForeignEntry{hash, blob}`), never an out-of-bounds index. Symmetrically, a blob-local ordinal `≥ foreign_dependencies.len()` in a received blob is `LinkError::ForeignOrdinalOutOfRange{blob, ordinal, table_len}` — hash verification on receipt proves the bytes match the claimed key, not that the sender's compiler was honest, so a self-consistent malformed/malicious blob must hit a structured link error (same WF-2C B4 de-panic class), never an index panic.
4. **Format/hash impact + sequencing (stated, not hidden; corrects a contradiction an adversarial review caught).** (1) changes blob bytes and therefore blob hashes — a **one-time hash-affecting blob-format change**. An earlier draft scheduled it "inside stage F0" while also claiming it rode WF-2A stage 0's hash-stabilization window — contradictory, since ffi-rebuild's stage 0 is a Wave-1 commit (rides WF-1D) and WF-2F/F0 runs only after WF-2A+2B+2C; as drafted there would have been *two* invalidation events with WF-2B `SnapshotStore`s and WF-2C `RemoteBlobCache`s populated on the old format in between. **Ratified sequencing: the format mechanics are hoisted into WF-2A stage 0's Wave-1 hash-stabilization commit** (amendments A6/A7 bind WF-2A stage 0 to include them): ordered first-use-deduped `foreign_dependencies` + the `CallForeign` ordinal rewrite + the linker `ForeignFunction` remap (the rewrite and the remap MUST land in the same commit — rewritten operands without the remap break local linking) + A7's alias storage + A5(ii)'s `__ffi_h{hex16}_return` rename if the anonymous schema name reaches any hashed payload. One invalidation event, before any snapshot store or remote cache ever populates. WF-2F stage F0 then *verifies* the landed format (canonicalization + link-error probes, §6) — it introduces no format change of its own. `FunctionBlobHashInput` itself needs no new field — the ordered `foreign_dependencies` it already covers *becomes* the correspondence table.

#### 4.2.1–4.2.6 Entry objects, wire, store, assembly

1. **Store object class + canonical serialization (mechanism named — an adversarial review correctly noted the derive can't do this).** The content-addressed store (snapshot `SnapshotStore`; receiver `RemoteBlobCache`) gains a second object class beside `FunctionBlob`: a serialized foreign entry keyed by its `content_hash`. No new struct — the entry *is* the object — **and the store/wire serialization is narrowed to the hash-covered fields + the advisory `name`**: `{name, language, body_text, param_names, param_types, return_type, is_async, native_abi}`. The derive cannot express this (`ForeignFunctionEntry`'s derive serializes ALL fields, `core_types.rs:64-108`), so the mechanism is a **`foreign_entry_canonical` serde-with module** beside `compute_content_hash` in `core_types.rs`: encode emits exactly the narrowed field set (rmp-serde); decode produces an ordinary `ForeignFunctionEntry` with every derived field re-established by the consumer, **never read from the object**: `arg_count = param_types.len()` at assembly; `dynamic_errors` from the executing runtime's `ErrorModel` at link-now; `return_type_schema_id` re-stamped per §4.7; `content_hash` recomputed, never trusted. **Blast radius bounded:** the module applies ONLY at the two store/wire sites — `#[serde(with)]` on `RemoteCallRequest.foreign_entries` (A3(i)) and the store-object encoder — while the program-level persisted formats (`ContentAddressedProgram`/`BytecodeProgram`, `content_addressed.rs:282` / `core_types.rs:531`) keep the wide derive unchanged (their stamps and registry-local ids are valid *within* the persisted program; changing them would invalidate cached bytecode for nothing). **Drift-proofing:** a unit test asserts the canonical field set ≡ `compute_content_hash` coverage + `name`, so a future hash-coverage change that forgets the encoder fails mechanically. This is not the R8-rejected second struct: there is one struct, one hash-coverage list, and one encode view over it — no independent field set to drift. Verification on receipt = decode + `compute_content_hash()` + compare to claimed key, identical to blob verification (WF-2C §4.3-2). **Integrity property this buys:** every load-bearing byte of the object is hash-covered; the single non-hashed field (`name`) is diagnostics-only by the §4.1 rule, so tampering with it can change error text, never dispatch, marshal, or schema binding.
2. **Closure computation.** `build_minimal_blobs_by_hash` (`remote.rs:454-489`) is extended (or paired with a sibling walk) to also collect the union of `blob.foreign_dependencies` across the closure and look up the corresponding entries from the program's `foreign_functions` table (sender-side lookup: an in-memory `content_hash → index` map over `program.foreign_functions`, built once — the entries live in the program `Vec`, not the blob content store). Output: `(Vec<FunctionBlob>, Vec<ForeignFunctionEntry>)`.
3. **Wire.** `RemoteCallRequest` gains `#[serde(default, with = "foreign_entry_canonical")] pub foreign_entries: Vec<ForeignFunctionEntry>` (canonical narrowed serialization per 4.2.1; amendment A3, §4.10) — additive, negotiable exactly like blobs (a receiver that has hash H cached tells the sender to strip it; entries are typically small, so v1 may skip entry-level negotiation and always send — see §6 stage F1).
4. **Snapshot.** `CodeManifest` gains `foreign_entries: Vec<[u8;32]>` (amendment A2, §4.10); each entry is stored as its own content-addressed object per snapshot-resume §4.3.5's write ordering (written in step 2, alongside blobs).
5. **Receiver/resumer assembly.** The consuming node builds its `foreign_functions` table from the **deduped union of verified entry objects** across the closure (any deterministic order — table order is no longer semantic, because §4.2.0-3's linker remap resolves each blob's ordinals through its own ordered `foreign_dependencies`). **Object-class discrimination is by keyspace, not by sniffing:** store keys are `(ObjectClass, [u8;32])` — on disk, sibling prefixes (`blobs/`, `foreign/`); in `RemoteBlobCache`, separate maps. A fetch always knows its class from the requesting context (blob deps resolve in the blob class, `foreign_dependencies` in the entry class), and the two unrelated hash constructions (manual `\0`-separated SHA-256 at `core_types.rs:200-223` vs rmp-serde of `FunctionBlobHashInput` at `content_addressed.rs:147-152`) can never be confused at fetch time. **Missing-hash classification is explicit on the wire:** the `MissingModuleFunction` error payload gains `#[serde(default)] missing_entries: Option<Vec<[u8;32]>>` beside `missing_blobs` (amendment A3) — the receiver classifies (it knows which lookup failed), and the sender's retry resends blobs in `function_blobs` and entries in `foreign_entries`, no shared-namespace guessing (this also amends WF-2C's §4.3-5 sender-retry step, which only knew about blobs). Resume path: `MissingBlob{hash}` gains a sibling `MissingForeignEntry{hash}`.
6. **`return_type_schema_id` re-stamp.** At assembly, each entry's `return_type_schema_id` is **discarded and re-resolved** in the assembling program's schema registry by the anonymous return schema's **hash-derived name** (`__ffi_h{hex16}_return` where `hex16` = first 16 hex chars of the entry's `content_hash`; registered from the blob's `type_schemas` / the manifest's schema registry). Keying by content hash — not by function name — makes the re-stamp immune to name dedup and name tampering, and correctly *shares* one return schema between two aliases of one body (their `return_type` is identical by hash construction). Compile-side change to `functions_foreign.rs:116`'s naming scheme, folded into stage F0 / amendment A5. Ids never travel (§4.7).

Nothing else about the entry changes: link-now (`runtime.compile()` / `link_native_function`) happens lazily on the executing node exactly per ffi-rebuild §4.2 — a node that receives foreign entries but never calls them never needs the extension (except the remote/resume load-time *availability* verification of §4.3.2/§4.4.3, which checks presence, not linkage).

### 4.3 Extensions as remote/resume dependencies — `ExtensionReq` and node capability matching

#### 4.3.1 The requirement record

```
ExtensionReq {
    language_id:    String,          // "python" | "typescript" | ... (vtable language_id)
    extension_name: Option<String>,  // from runtime_descriptor.extension_name if known;
                                     //   None = any extension providing language_id
    semver_req:     Option<String>,  // constraint, e.g. ">=0.4, <2" — from the declared
                                     //   extension spec (syntax below); None = any
}
```

**No `abi_version` field (deliberate — corrects an earlier draft and snapshot-resume's sketch).** Foreign entries are source text; they have no Shape-ABI dependence, so "the ABI the entry was compiled against" is not a well-defined traveling fact. The marshal contract that matters is **executing-host ↔ its own installed extensions**, and that is already enforced fail-safe by the host-local loader gate (`loader.rs:112-143`: a `.so` whose ABI ≠ the host binary's `ABI_VERSION` refuses to load). ABI is a node property, not a program requirement — putting it in the req would forbid resuming a snapshot on a node running a newer Shape ABI whose extensions match that ABI, for zero safety gain. `NodeCapabilitySet` still records each extension's ABI for diagnostics (`sub_kind: AbiSkew` text, §4.3.2).

**Declaration syntax (the contract input — new, owned by this design + amendment A5 to ffi-rebuild).** `ExtensionSpec` (`bin/shape-cli/src/extension_loading.rs:32-37`, today `{name, path, config, source}`) gains `version_req: Option<String>` (semver constraint grammar, validated at parse). Declared in either surface, merged by the existing precedence rules (`extension_loading.rs:167-175`):

```toml
# shape.toml
[extensions.python]
version = ">=0.4, <2"        # other keys (path, config) unchanged

[extensions.typescript]      # bare table = any version (version_req: None)
```

```shape
//! extensions:
//!   python: { version: ">=0.4" }     # script frontmatter, same keys as the toml table
```

`shape check` parses these identically to `shape run` (ffi-rebuild S6 already requires the shared entry point).

**Construction time:** at program load / manifest build / request build, one `ExtensionReq` per distinct `language` among the relevant dynamic `ForeignFunctionEntry`s (native `extern C` entries produce **no** ExtensionReq — their requirement is the library alias, checked separately, §4.4.3). **Scoping (per movement path, resolving an ambiguity an adversarial review caught):** on the *transfer* path, reqs are built **closure-scoped** — one per distinct language among the entries referenced by the transferred closure, not the whole program — so a python-only remote call from a program that also declares TS fns does not spuriously refuse on a python-only receiver; defensively, the receiver ignores any req whose language appears in none of the closure's entries (a buggy or malicious over-broad req can then only fail to narrow — it still cannot grant, per the caveat below). On the *manifest/resume* path, reqs are program-scoped: the whole manifest resumes. `semver_req` comes from the user's declared extension spec above, not from what happens to be installed — the *declaration* is the contract. If the runtime was already linked when a snapshot is taken, the observed version from `runtime_descriptor` is recorded **informationally** as `observed_version` beside the req in the manifest (diagnostics only; not a match input under the recommended policy — Open Question 1).

**The reqs travel on both movement paths.** `CodeManifest.extensions: Vec<ExtensionReq>` (resume path, A2) and — closing a gap an adversarial review found — `RemoteCallRequest` gains `#[serde(default)] extension_reqs: Vec<ExtensionReq>` (transfer path, A3(v)); without it, `semver_req` could never fire on transfer and a `python >= 0.4` program would silently execute on a python-0.1 receiver. **Never-trust-the-sender caveat:** reqs are advisory *constraints*, not permission or capability claims — a sender-supplied req can only cause the receiver to **refuse** (narrow), never to grant, load, or execute anything it otherwise wouldn't; a malicious req is a self-inflicted refusal. The receiver's own grants/scopes remain the sole authority (§4.6).

**Amendment to snapshot-resume §4.3.2 (A2, §4.10):** its sketched `ExtensionReq {name, abi_version, content_hash}` is replaced by the shape above. Rationale: a `.so` content hash is a **platform-and-build-specific artifact hash** — pinning it in the manifest makes every snapshot non-resumable on any node with a differently-built (even bit-different, same-version) extension, and cross-platform resume impossible by construction. Version/ABI matching via `runtime_descriptor` is the portable equivalent with the same safety property (the loader gate already refuses ABI mismatches fail-safe).

#### 4.3.2 Node capability set and resolution

Each node (a `shape serve` receiver, or a resuming host) builds a `NodeCapabilitySet` at startup from its installed extensions: for every loadable `.so`, `(language_id, extension_name, extension_version, abi_version, platform_triple, backend)` from `runtime_descriptor` (ffi-rebuild §4.7; `backend` is its interpreter descriptor, e.g. `"CPython 3.12.4"` — diagnostic-only, never matched in v1, §4.4.4/OQ-8; absent descriptor → language_id-only entry, matching degrades to language_id + abi_version).

`resolve_extension_requirement(req, caps) -> Resolved | Refused{sub_kind, needed, found}`:

1. filter caps by `language_id` — empty → `sub_kind: MissingRuntime`;
2. filter by `extension_name` if the req names one;
3. only capability entries whose `.so` passed the host-local loader ABI gate are in `NodeCapabilitySet` at all (an installed-but-ABI-mismatched `.so` produces a **diagnostic shadow entry** so the refusal can say `sub_kind: AbiSkew, found: "python 0.4 built for ABI 3, host is ABI 4 — rebuild/reinstall the extension"` instead of pretending nothing is installed). No cross-node ABI equality check exists (§4.3.1 rationale);
4. filter by `semver_req` if present — nonempty at step 2/3 but empty here → `sub_kind: VersionSkew`; **default policy when absent: same-major as `observed_version` if recorded, else any** — where "same-major" means **cargo-caret compatibility semantics**: for `0.x` versions the window is same-minor (`0.5 → 0.6` is a breaking step by ecosystem convention — and both current extensions ARE 0.x, so a naive same-major-literal reading would accept what semver convention calls incompatible; Open Question 1 ratifies);
5. empty result → structured refusal carrying the sub-kind, what was needed, and the nearest installed candidates.

**Refusal surfaces (one shared structured shape — programs and operators match on `sub_kind`, never parse prose):**

```
CapabilitySubKind { MissingRuntime | VersionSkew | AbiSkew | MissingNativeLibrary | MissingSymbol }
```

- Remote path: `CallResponse(Err{kind: CapabilityUnavailable, sub_kind, message})` — new additive `RemoteErrorKind` variant (amendment A3; named `CapabilityUnavailable`, not `ExtensionUnavailable`, because the extern-C case is a *native library*, not an extension, and misfiling it under "extension" would send operators to `shape ext install` for a problem it cannot fix). Message templates per sub-kind: `MissingRuntime`: `"function 'f' requires the python extension; this node has none installed — remediation: shape ext install python"`; `VersionSkew`: `"function 'f' requires python >=0.4; this node has python 0.3 — remediation: upgrade the extension"`; `AbiSkew`: as step-3 text — remediation: rebuild against the host ABI; `MissingNativeLibrary`: `"extern C fn fast_sum requires native library 'mathkit' — not resolvable on this node (tried libmathkit.so via …) — remediation: install the library or fix the lookup path"`; `MissingSymbol`: `"extern C fn fast_sum: library 'mathkit' resolved to /usr/lib/libmathkit.so but does not export symbol 'fast_sum_v2' — the installed library is a different build/version or the declared symbol is wrong — remediation: install the matching library version or fix the declaration"` (a distinct sub-kind, not `VersionSkew`: a same-named wrong library or a typo'd declared symbol is not a version problem, and programs/operators match on `sub_kind` for remediation — filing it under VersionSkew would send them down the wrong path). Sender renders verbatim with the node address prefixed. Never a panic, never local-fallback execution (executing locally instead would silently violate the user's placement intent AND the receiver's permission envelope).
- Resume path: `SnapshotCapabilityMissing{sub_kind, language_or_library, needed, found}` (renamed from snapshot-resume §4.5.1's sketched `SnapshotExtensionMissing` — same generalization rationale; amendment A2), same sub-kinds and message templates. Concrete spelling in snapshot-resume's error catalog: `SnapshotError::CapabilityMissing{sub_kind, language_or_library, needed, found}` (its §4.11) — one variant, two renderings of the name in prose; probes assert the concrete spelling.

**Remote diagnosability (closes the "how does a sender even ask?" gap):** `remote::ping`'s response gains an additive `#[serde(default)] capabilities: Vec<{language_id, extension_name, extension_version, abi_version, backend}>` — the `NodeCapabilitySet` summary the receiver already builds at startup, including the interpreter `backend` string so environment-level skew (CPython 3.9 vs 3.12) is sender-diagnosable even though it is never matched (§4.4.4) (amendment A3(iv), superseding the distributed doc's "ping unchanged" for this one additive field). A sender hitting `CapabilityUnavailable` can programmatically inspect what the node hosts; `shape ext list` remains the receiver-operator's local view. Capability advertisement is diagnostic metadata, not a security surface (it grants nothing; operators who consider it information disclosure can disable it in serve config).

**Check timing:** extension availability (and extern-C library *resolvability*, §4.4.3) is verified **at load/resume time** — before any bytecode executes — even though actual linking stays lazy. Rationale: a resume that re-executes side effects and then dies at the first foreign call is strictly worse than an upfront refusal; the check is cheap (capability-set lookup / alias-resolve + stat). The lazy-link property that *declaring* is never fatal still holds for ordinary `shape run` (ffi-rebuild §4.2 unchanged); load-time verification applies only where a manifest/request explicitly declares the dependency set — remote calls and resumes, where "the program" was already validated once on the origin node.

#### 4.3.3 `shape ext install` interplay

- Resolution consults the same precedence-merged discovery set as local runs (`extension_loading.rs:167-175`): a receiver operator satisfies a refusal by running `shape ext install <name>` (or the OS package) and restarting/`SIGHUP`-reloading serve; the capability set rebuilds.
- **No auto-install, ever, on network input.** A receiver never fetches, builds, or loads code in response to a request (that would be remote code execution *of the toolchain*, bypassing every permission tier). Refusal + operator remediation message is the whole protocol. (Open Question 4 confirms this stance.)
- `shape serve` config additionally gates which languages it is *willing* to host via `ScopeConstraints.ffi_languages` (§4.6) — installed-but-not-granted refuses with `PermissionDenied`, not `CapabilityUnavailable` (distinct operator signals: "install it" vs "you chose not to allow it").

### 4.4 Transfer flow — remote call of a foreign-bearing function

Composes WF-2C §4.3 (blob protocol) with WF-2A §4.2/§4.9 (lazy link + shared core). Sender/receiver deltas over the WF-2C flow, in order:

**Annotation target note (probe-relevant):** `@remote` targets **Shape functions** — the distributed doc's comptime validation is specified for Shape fns, and this design does not extend annotation target validation to foreign declarations. `@remote fn python f(...)` is a comptime target-validation error in v1 ("annotate a Shape fn that calls the foreign fn"); foreign functions travel as *dependencies* of the annotated Shape function's closure. (Direct annotation support is a possible later ergonomic addition; nothing here forecloses it.)

**Sender (`remote::call`):**

1. Closure computation returns `(blobs, foreign_entries)` (§4.2.2).
2. Pre-flight: if any blob's `required_permissions` contains `Ffi`, nothing special happens sender-side — permissions are the receiver's decision (never-trust-the-sender is symmetric: the sender doesn't pre-judge either).
3. Request carries `foreign_entries` (§4.2.3) and `extension_reqs` (§4.3.1); negotiation strips cached entries like blobs. On a `MissingModuleFunction` retry, the sender resends per the explicit `missing_blobs`/`missing_entries` classification (§4.2.5).

**Receiver (`handle_call`), after WF-2C steps 1–3 (merge, verify, cache) extended to entry objects — gate order corrected per adversarial review (permission BEFORE any dlopen):**

4. **Assemble + link fallibly** (WF-2C §4.3-4): build the `foreign_functions` table from verified entry objects (§4.2.5) and run the §4.2.0-3 operand remap — pure data work, no extension or library code touched; the linker union now includes `Ffi` from foreign-bearing blobs.
5. **Permission load gate:** `load_linked_program_with_permissions(linked, &server_granted)` — a foreign-bearing program is refused with `PermissionDenied{missing: [ffi]}` unless the server grants `Ffi` (plus the coarse `ffi_languages`/`ffi_libraries` scope pre-checks of §4.6 where evaluable at load; call-time scope checks remain authoritative). **This ordering is load-bearing twice over:** (a) `dlopen` executes ELF constructors — no operator-installed library code may run in response to a request the server would refuse anyway (the same rule ffi-rebuild §4.8.2 pins for the local link-now path, applied at the request level); (b) signal precedence — when both refusals would apply, the operator's *choice* (`PermissionDenied`: "the operator chose not to allow it") must win over the *installation gap* (`CapabilityUnavailable`: "install it") or the error sends the sender chasing an install that cannot help (§4.3.3's "distinct operator signals").
6. **Capability check** (§4.3.2), only for permission-cleared requests: every distinct `language` in the entries referenced by the closure resolves against `NodeCapabilitySet` under the request's `extension_reqs` constraints (reqs for languages absent from the closure are ignored, §4.3.1), and every `native_abi` alias resolves **and its declared symbol dlsym-verifies** per §4.4.3 — else `CapabilityUnavailable{sub_kind}` before execution.
7. **Execute** under the server's `ResourceLimits`. The foreign call itself goes through the receiver VM's ordinary `op_call_foreign` → link-now → `invoke_foreign_kinded` (ffi-rebuild §4.3/§4.9) — the remote path adds **no** special foreign invocation code; by the time bytecode runs, a remotely-received foreign function is indistinguishable from a locally-compiled one. Runtime `check_permission(Ffi, scope)` fires per call on the receiver (fourth enforcement point).
8. Foreign runtime errors (`Err` on the declared `Result<T>`) are ordinary values — they marshal back through the normal return path. Per the Q13 ratification override (2026-07-05), this Err path also carries **nonconforming foreign returns**: they arrive at the sender as class-1 `Err` with the `TypeConformanceError:` discriminator prefix intact (ffi-rebuild §4.5 (1b)) — an ordinary value, not a remote error. The remaining marshal/link errors on the receiver (arg-path marshal failure, surface-and-stop backstop, link errors) map to `RemoteErrorKind::RuntimeError` with the ffi-rebuild §4.5 class-2/3 structured text intact.

#### 4.4.3 extern C on the receiver (and at resume verify)

- The entry's `native_abi.library` **alias** (post-A7 the entry stores the declared alias, §4.1) re-resolves on the executing host — **against the executing host's own configuration, never the origin's.** An adversarial review correctly flagged that "re-resolves via `resolve_for_host()`" was undesigned: `resolve_for_host()` is a method on `NativeDependencySpec` from the *origin project's* `shape.toml` native-deps table (`dependency_spec.rs:199`), which travels in neither the entry, the request, nor the manifest — there is nothing origin-side to consult, by design. **Receiver-side resolution chain (mirrors the compile-side chain at `functions_foreign.rs:855-896`, with host-local inputs):** (i) the built-in well-known alias table (`"c"`/`"libc"` → the host platform's soname); (ii) the executing host's *own* declared native deps — a `[native_libraries]` alias→spec table in `shape serve` config (new, this design; on the resume path, the resuming host's project/config equivalent), with the same `NativeDependencySpec` semantics `resolve_for_host()` implements today; (iii) soname convention (`lib{alias}.so` via the platform's dlopen search path). Unresolvable after (i)–(iii) → refusal below. This is the same "the receiver's filesystem, the receiver's rules" locality that already governs the `ffi_libraries` scope glob.
- **Load-verify depth (upgraded — fail-early parity with the dynamic-language guarantee):** on the two declared-dependency paths (remote step 6 — after the permission gate, per §4.4's corrected ordering; resume verify), verification is not merely alias-resolvability but **`dlopen` + `dlsym` of each declared symbol** for every extern-C entry in the closure/manifest — cheap, bounded by the entry count, and it catches the stale-`.so`-at-the-same-path case (library present, symbol/version skewed) *before* any bytecode executes, honoring §4.3.2's own rationale (a resume that re-executes side effects and then dies at the first foreign call is strictly worse than an upfront refusal). The opened handle is cached, so first-call link-now finds it warm; ordinary local `shape run` keeps fully-lazy `dlopen` (ffi-rebuild §4.2 unchanged — local runs have no declared-dependency manifest, and declare-is-never-fatal holds there). Trust note: the verify-time `dlopen` runs the same operator-installed library the lazy path would run moments later — no new code source is introduced. (Open Question 5 now covers this depth choice.)
- Unresolvable alias → `CapabilityUnavailable{sub_kind: MissingNativeLibrary}` naming the alias and the resolution attempted: `"extern C fn fast_sum requires native library 'mathkit' — not resolvable on this node (tried libmathkit.so via lookup paths …)"`. Resolvable-but-symbol-missing → `CapabilityUnavailable{sub_kind: MissingSymbol}` naming library, resolved path, and symbol (§4.3.2 — a dedicated sub-kind; an earlier draft filed this under `VersionSkew`, which misdirects remediation for wrong-library and typo'd-symbol cases).
- **No library bytes ship in v1** (ffi-rebuild §4.11.4 upheld). Platform mismatch is subsumed by alias resolution failure; `runtime_descriptor.platform_triple` is used only for diagnostics text. (Open Question 5 covers whether a stricter declared-platform check is wanted.)
- The receiver's `ffi_libraries` scope glob is matched against the **post-resolution path** on the receiver (ffi-rebuild §4.8.2 semantics, evaluated with receiver-local resolution — the receiver's filesystem, the receiver's rules).

#### 4.4.4 Foreign-language *environment* failures — the bounded residual gap (stated, surfaced, diagnosable)

The load-verify gates check everything *declared to Shape*: extension presence/version/ABI (§4.3.2), library alias + symbol (§4.4.3). They can NOT check the foreign body's own environment: `import numpy` inside a `fn python` body on a node whose Python lacks numpy; a deno module-cache miss; interpreter skew (origin CPython 3.12, executing node 3.9, syntax/stdlib behavior differs). For a user moving python code between nodes this is the most probable real-world failure, so its behavior is defined, not left silent:

- **Surfaced behavior (every movement path):** such failures surface at link-now / first call as the ffi-rebuild §4.5 structured error classes — a body import failure or runtime environment error is a class-1 foreign exception → `Err` on the declared `Result` carrying the foreign traceback (or class-3 structured compile-error text for syntax-level interpreter skew), naming the function and language; on the remote path it maps to `RemoteErrorKind::RuntimeError` with the text intact and the node address prefixed by the sender. Never a panic, never a silent `None`.
- **Honest tension, owned:** this is *after* the load gates, mid-run, potentially after side effects — a bounded exception to the fail-early rationale of §4.3.2. Fail-early covers every Shape-visible declaration; the foreign body's internal dependencies are declared nowhere Shape can see them, and verifying them would require executing foreign code at verify time (strictly worse: §4.3.3's no-code-execution-on-network-input rule would fall).
- **Diagnostics shipped here:** `runtime_descriptor.backend` (e.g. `"CPython 3.12.4"`, ffi-rebuild §4.7) is included in the `remote::ping` capabilities summary (§4.3.2) and recorded informationally in the manifest beside `observed_version` — interpreter skew is *diagnosable* by sender/resumer even though it is never *matched* in v1.
- **Non-goal + book caveat (required, §6 F5):** environment provisioning is deployment tooling's job; nodes executing `fn python` code must be provisioned with the packages the bodies import (§1 non-goals).
- **Declared environment constraints** (an `ExtensionReq.backend_req`, or a per-program `[foreign.python] requires = ["numpy>=2"]` table matched at load-verify) are **Open Question 8** — deliberately not invented here: it grows a package-manager-shaped verification surface and ratification should decide whether Shape wants to own it. Matrix row in §4.9; probe M11.

### 4.5 Snapshot semantics at foreign frames — the barrier rule (ratified single rule)

**Rule: a snapshot is refused while any foreign frame is live; foreign runtime state is opaque and never serialized; snapshots between foreign calls are always valid and resume re-links lazily.**

This is the rule both sibling docs already converged on (ffi-rebuild §4.7 state_model policy (a)/(b); snapshot-resume §4.6.1 barrier row 1). This doc ratifies **refuse** over the alternative (run-to-completion-then-suspend) and gives the justification the charter asks for:

- **Why refuse, not run-to-completion:** `snapshot()` can only appear in a live foreign frame's dynamic extent via a Shape callback invoked *from* foreign code (`RawCallableInvoker` re-entry). "Run the foreign call to completion, then snapshot" would mean: return a not-yet-valid `Snapshot::Hash` marker to the callback's continuation *inside* the foreign call (the stdlib contract requires `snapshot()` to return the hash — but the hash cannot exist until after the foreign frame unwinds), or block the callback until… itself. It is semantically incoherent, not merely hard. Refusal with `SnapshotBarrier{reason: ForeignFrame{function, language}}` is honest, catchable, and the program can retry after the foreign call returns. **Message template:** `"cannot snapshot() inside foreign call 'f' (python): foreign runtime state cannot be captured — retry after the foreign call returns"`.
- **Asynchronous interrupt (Ctrl+C) composes via deferred flag *observation*, not a capture-time barrier wait.** Rule owned by snapshot-resume §4.4, quoted exactly: "*while `foreign_reentry_depth > 0`, the flag stays set but is **not observed**; the outer loop's first check after the foreign call returns performs the capture*" — and, for every other barrier, "*Termination is immediate once the flag is observed — there is no 'wait for barrier-free' loop*". (An earlier draft of THIS doc misquoted the sibling as capture-time barrier consultation with capture "at the first barrier-free check" — a wait-for-barrier-free loop the sibling explicitly rejects; corrected here, foreign-frame behavior unchanged.) Why the observation gate and not naive instruction-boundary reasoning: flag checks fire between VM instructions, and while a Shape callback runs *inside* a live foreign frame the nested dispatch loop's checks DO fire — without the depth gate, `Interrupted` would unwind *through* the foreign runtime (Ctrl+C swallowed as a catchable foreign-call error) and any later capture would see torn state (foreign frame unwound, its result never pushed). Net behavior: an interrupt during a foreign call (with or without a live callback) defers to the first check after the foreign frame unwinds — run-to-completion semantics for the foreign-frame case only; if capture *then* hits some other persistent barrier (e.g. a module-scope Channel), the run terminates now with no save and the message names the barrier (snapshot-resume §4.4/§4.11) — it does not wait. If the foreign call never returns, second-Ctrl+C force-exit applies (snapshot-resume Open Question 7's cooperative-cancellation hook remains its open question, answered by ffi-rebuild §4.12; nothing here depends on it).
- **Detection:** the barrier check inspects (i) the call stack for foreign-entry frames and (ii) a VM `foreign_reentry_depth` counter incremented by `invoke_foreign_kinded` around the vtable/libffi call and by the callback invoker on re-entry — so a snapshot attempted from a callback is caught even though the foreign activation itself is not a Shape frame. Counter maintenance lives in the one shared core (ffi-rebuild §4.9 invariant), so vm and jit tiers cannot diverge on it.
- **What is therefore true of every snapshot, by construction:** no snapshot ever contains a foreign frame, foreign locals, or extension state. Cross-node resume never moves extension state — only extension *availability* matters (already stated in snapshot-resume §4.8; this doc supplies the availability semantics, §4.3).

### 4.6 Permission propagation — Ffi across the wire and across resume

The four enforcement points, each with its file-anchored mechanism:

1. **Compile:** `compile_foreign_function` adds `Ffi` to the declaring function's `required_permissions`; caller-inherits-callee propagation (`compiler_impl_initialization.rs:475-501`) spreads it to every reachable caller; it lands inside each blob's content hash (`content_addressed.rs:114`). *Consequence for composition:* a sender cannot strip `Ffi` from a foreign-bearing blob without changing every hash in the dependency chain — the Merkle property WF-2C §4.6 relies on covers Ffi with zero new code.
2. **Link (receiver/resumer-side, from verified bytes):** linker union (`linker.rs:327-329`) recomputed on the consuming node from hash-verified blobs; manifest/request permission claims are never read as data (WF-2C §4.6, snapshot-resume §4.7.3 — both preserved verbatim).
3. **Load:** `load_linked_program_with_permissions` on the remote path (WF-2C stage 1.2); the §4.5.1-step-1 `union ⊆ granted` check on the resume path. Missing `Ffi` → `PermissionDenied{missing:[ffi]}` / `SnapshotPermissionRefused{missing:[ffi]}` before execution. **Message templates:** remote — `"this program requires permission Ffi (it calls foreign code); the server at <addr> does not grant it — server operator remediation: grant ffi in serve config, optionally scoped (ffi_languages = [\"python\"])"`; resume — `"cannot resume: the snapshot requires permission Ffi but the current grant set excludes it — re-run with the original grants or an explicit [permissions] ffi = true"`.
4. **Call:** `op_call_foreign` step 3 `check_permission(Permission::Ffi, scope)` on the **executing** node, every call (ffi-rebuild §4.3). This is not redundant with (3): scope constraints (`ffi_languages`/`ffi_libraries`/`ffi_symbols`) are evaluated per-entry at call time against the executing node's local resolution (§4.4.3), and permission config may be tighter than the load-time coarse grant (e.g. `Ffi` granted scoped to python only — a TS entry in the same program loads but refuses at call).

**ScopeConstraints for extension identity:** `ffi_languages` is the extension-identity scope (which language runtimes may execute); `ffi_libraries`/`ffi_symbols` scope extern C. A **per-extension-name scope** (allow python only if provided by extension "python" ≥ some version) is deliberately NOT added: capability matching (§4.3.2) already pins provider identity/version *requirements* program-side, and the node operator controls what is installed — a third overlapping knob would create contradictory-config surface with no threat-model gain. (Rejected as R6, §5.)

**Sandbox/limits composition:** remote execution runs under the receiver's `ResourceLimits` (WF-2C §4.6); resumed execution restores cumulative counters (snapshot-resume §4.7.1); foreign-call wall time counts against `TimeLimited` on the executing node while foreign-runtime memory stays outside `MemLimited` accounting (ffi-rebuild §4.8.3 documented limitation — inherited here for the remote and resume cases too; the receiver's process-level supervision is the containment for foreign memory in v1, per ffi-rebuild Open Question 6). **Enforcement granularity caveat (stated, and a §4.9 matrix row):** limits are checked between VM instructions, so a foreign call that blocks or overruns on the receiver cannot be interrupted mid-call — `TimeLimited` fires at the first check *after* the call returns. For the remote path this means: the **sender's** experience is bounded by the WF-2C request timeout `T` → the Shape-level `RemoteError::Timeout { message }` naming the function and elapsed time (a sender-local read timeout — the wire enum's `RemoteErrorKind::Timeout` stays reserved and unproduced in v1, distributed §4.2; overview §4.4 tier correction); the **receiver's** worker remains occupied until the foreign call returns (never-returning call = wedged worker — documented v1 limitation; mitigations are serve's worker-pool supervision/restart and the ffi-rebuild §4.12 `request_cancel` follow-up vtable hook, which converts cooperating runtimes into interruptible ones with no ABI bump).

### 4.7 Schema identity across nodes — ids never travel

The composition-level generalization of comptime-excellence §4.3 ("ids become registry-local plumbing that never crosses a registry boundary with load-bearing meaning") and snapshot-resume's `schema_registry_hash` pinning:

- `ForeignFunctionEntry.return_type_schema_id` is **excluded from identity and re-stamped at assembly** by looking up the **hash-derived** schema name (`__ffi_h{hex16}_return`, §4.2.6 — replacing HEAD's `__ffi_{name}_return` at `functions_foreign.rs:116`) in the consuming program's registry. Hash-keying is what makes the re-stamp sound under content-hash dedup: the fn `name` is outside the hash (advisory-only, §4.1), so a name-keyed lookup could be redirected by name dedup or name tampering; the hash-keyed name cannot, and two aliases of one body correctly share the one return schema their identical `return_type` defines. The schema *definition* travels via blob `type_schemas` / the manifest's pinned schema registry — both content-addressed.
- The receiver's `run_remote_call` marshal and the extension-side `unmarshal_result` both consume registry-local ids resolved on the executing node. A name lookup that fails (schema definition genuinely absent from the transferred set) is a structured link-time error naming the schema — never a fabricated id, never a positional guess (the exact aliasing class comptime root cause B exhibited, foreclosed the same way: resolution by name in the consumer's registry).

### 4.8 The `remote::execute` source path and foreign code

`remote::execute` (source-shipping, retained per WF-2C §4.1.3) composes trivially: shipped source containing `fn python …` recompiles on the receiver, producing receiver-local entries → the receiver's own capability/permission gates apply identically (§4.3/§4.6 don't care how the program arrived). No special handling; one probe in §7 pins it.

## 5. Alternatives considered & rejected

- **R1 — Ship extension `.so`s / native libraries as blobs** ("make the receiver self-sufficient"). Rejected: executing sender-supplied native code dissolves the entire capability model (native code has process authority; the receiver's permission gates become decoration), and artifact hashes are platform-coupled. Extensions are operator-installed capabilities; refusal + remediation is the protocol (§4.3.3).
- **R2 — Extension version inside the foreign content hash** ("strongest reproducibility"). Rejected per ffi-rebuild §4.7/OQ-2 split, with the composition-side addition: it would make blob caches and snapshot stores churn on every extension patch release across a cluster, and two nodes with compatible-but-unequal patch versions could never share cached blobs. Version is a capability constraint (§4.3), not identity. (User may still fold **major** version into the hash via ffi-rebuild OQ-2 — this design works under either ruling; only the `ExtensionReq` default policy shifts.)
- **R3 — Pin `.so` content hash in the snapshot manifest** (the snapshot doc's sketched `ExtensionReq.content_hash`). Rejected → amendment A2. Same platform-coupling defect as R1's identity half; adds a false sense of attestation (hash of a local build artifact attests nothing about behavior of a *different* node's equally-valid build).
- **R4 — Run-to-completion instead of refusal when `snapshot()` fires under a live foreign frame.** Rejected: incoherent, not just inconvenient — the marker return value cannot exist inside the frame that must first unwind (§4.5). The asynchronous-interrupt case gets run-to-completion semantics naturally, covering the legitimate use.
- **R5 — Serialize foreign runtime state to lift the barrier** (pickle globals / V8 heap snapshot). Rejected by both sibling docs (ffi-rebuild R11, snapshot-resume 5.8); restated: unbounded, version-fragile, and a deserialization-equals-code-execution security hole. `state_model` declares opacity; the barrier consumes the declaration.
- **R6 — Per-extension-name/version ScopeConstraints** (third permission knob for provider identity). Rejected: overlaps capability matching (§4.3.2) + operator install control with contradictory-config surface and no added containment (§4.6).
- **R7 — Local-fallback execution when the receiver lacks the extension** ("degrade gracefully"). Rejected: silently violates placement intent, moves the computation into a *different* permission envelope than the user targeted, and turns a loud capability gap into a heisenbug. Refusal is the graceful behavior.
- **R8 — A `ForeignBlob` struct distinct from `ForeignFunctionEntry`** (new wire type wrapping the entry). Rejected: a second struct with the same fields is carrier duplication with drift risk (the parallel-implementation defection-attractor, CLAUDE.md §Forbidden); the store object *is* the entry, self-verifying via `compute_content_hash`. **Wording reconciled with §4.2.1 (a review caught the tension):** "the entry serializes deterministically" is achieved by the `foreign_entry_canonical` serde-with module, not by the bare derive (which serializes non-hash-covered fields). That module is not the rejected second struct — it has no independent field set (one struct, one hash-coverage list, one encode view, drift mechanically tested §4.2.1); what R8 rejects is a parallel *carrier* whose fields can diverge from the entry's.
- **R9 — Receiver-side auto-install of missing extensions** ("npm-like ergonomics"). Rejected: toolchain-level remote code execution triggered by network input; bypasses operator intent entirely (§4.3.3; OQ-4 offers the user the final say).
- **R10 — Eager foreign linking on remote receive / resume** (compile all entries at load). Rejected: re-introduces declare-is-fatal on paths that may never call the function, and wastes receiver work on speculative entries. Load-time **availability** verification + lazy **linking** gets the fail-early property without the cost (§4.3.2 timing).
- **R11 — In-band schema-id translation tables between node registries.** Rejected on sight — "boundary translation" per CLAUDE.md §Renames-to-refuse and exactly the shape comptime-excellence §5.3 already refused; name-resolution in the consumer's registry removes the id traffic instead of translating it (§4.7).

- **R12 — Ship foreign-function-ref closure captures in WF-2F "since the entry already travels".** Rejected (this revision — reversing an earlier draft's A3(iii)): the entry object traveling covers *code*, not the captured *value*; with no defined `SerializableVMValue` arm, no `NativeKind` story on the §2.7.8 closure-cell kind track, and no receiver rebinding rule, implementation pressure would invent an ad-hoc encoding at exactly the boundary CLAUDE.md's forbidden-pattern history warns about. The distributed doc's refusal row stays; a properly typed carrier (sketch: a dedicated serialized arm carrying the entry `content_hash`, rebound receiver-side through the assembled table via the §4.2.0 hash↔index correspondence) is Open Question 7.
- **R13 — Keep `Operand::ForeignFunction` as a program-level index and ship a per-blob index→hash side table beside the hash input.** Rejected in favor of §4.2.0's ordinal rewrite: a side table outside `FunctionBlobHashInput` leaves hashed instructions referencing unhashed mapping data (tamper surface + two sources of truth), and inside it is a redundant second encoding of what the ordered `foreign_dependencies` already states. The ordinal rewrite also fixes cross-program hash canonicalization (C10-ii), which no side-table variant does.
- **R14 — Sniff store object class from the bytes** (try blob deserialize, fall back to entry). Rejected: deserializer-guessing on a shared 32-byte keyspace is exactly the re-discrimination discipline §2.7.29 forbids for values, applied to metadata — and it breaks silently on ambiguous bytes. Keyspace separation (`ObjectClass` in the key) + explicit `missing_entries` wire classification costs one enum and removes the guessing (§4.2.5).

## 7. Acceptance tests (e2e probes; sender/executing VM under **both** `--mode vm` and `--mode jit`; receiver default tiering; real `shape serve` + real CLI, no harness shortcuts)

**Happy-path matrix (WF-2F close gate core):**

- **X1 {py, ts, C} × transfer** (corrected — an earlier draft annotated the foreign fn directly, which §4.4 itself rules a comptime target-validation error):

  ```
  fn python py_double(x: int) -> Result<int> { return x * 2 }

  @remote("127.0.0.1:PORT")
  fn double_on_node(x: int) -> Result<int> { py_double(x) }
  ```

  (and TS twin; C twin: a `@remote` Shape wrapper calling an `extern C fn` against a receiver-present fixture `.so`) — the foreign entry travels as a dependency of the wrapper's closure; executes on the receiver (server-side counter asserts remoteness), correct value, foreign exception → `Err` propagates to the sender intact. Negative twin in the same probe: `@remote("…")` placed directly on `fn python …` → the §4.4 comptime target-validation error, clean message naming the wrapper pattern.
- **X2 {py, ts, C} × snapshot→resume (same node):** program calls foreign fn, `snapshot()` between calls, killed, `shape --resume` — resumed run re-links lazily and completes; output byte-equal to the uninterrupted tail.
- **X3 {py, ts, C} × resume-other-node:** X2's snapshot copied store-to-store (manifest-enumerated objects only — proves `foreign_entries` closure completeness, extends WF-2B T14); resume on a second workdir/host-sim with the extension installed → completes identically.
- **X4 combined:** node A snapshots mid-program; node B resumes and then performs a remote foreign call to node C — the full three-node composition in one probe.

**Identity & schema:**

- **X5 hash perturbation matrix (unit):** for each §4.1 IN-field, a one-field change flips `content_hash`; for each OUT-field, it does not. Blob-level: editing a python body flips the dependent Shape blob's hash (C3 property).
- **X6 id-never-travels:** program whose `__ffi_*_return` schema would collide with a differently-numbered registry on the receiver (json-import neighbor, the comptime-B collision recipe) — remote call and resume both produce correct TypedObject fields, never garbage keys.

**Capability & permission negatives (each cell of §4.9 that refuses):**

- **M1 extension missing:** receiver without python-ext → `CapabilityUnavailable{sub_kind: MissingRuntime}` naming language + `shape ext install python`; server alive; sender renders node address. Resume twin → `SnapshotError::CapabilityMissing{sub_kind: MissingRuntime}` before any output side effect (negative assertion on re-executed effects).
- **M2 version skew:** receiver with a stub extension declaring version 0.1 against `semver_req ">=0.4"` → `CapabilityUnavailable{sub_kind: VersionSkew}` naming both versions; ABI-3 `.so` on the receiver → loader refusal surfaces as `CapabilityUnavailable{sub_kind: AbiSkew}` with the rebuild hint.
- **M3 permission:** (a) server not granting `Ffi` → `PermissionDenied{missing:[ffi]}` at load, foreign body provably not executed; (b) `ffi_languages=["python"]` → TS entry refused at call time, python succeeds in the same program; (c) resume under an Ffi-less grant → `SnapshotPermissionRefused` at verify; (d) content-hash probe: identical programs ± one foreign call differ in every ancestor blob hash and the linker union gains `Ffi`.
- **M4 tamper:** flip one byte of a wire `ForeignFunctionEntry` → `HashMismatch`, not cached, no execution; same for a store entry object at resume.
- **M5 extern C library missing on receiver:** alias unresolvable → `CapabilityUnavailable{sub_kind: MissingNativeLibrary}` naming alias + attempted paths, at load-verify time (before execution), not mid-run; symbol twin: library resolvable, declared symbol absent → `CapabilityUnavailable{sub_kind: MissingSymbol}` naming library, resolved path, and symbol, also at load-verify.
- **M6 barrier:** Shape callback invoked from python calls `snapshot()` → `SnapshotBarrier{ForeignFrame}` catchable, nothing persisted, program continues; Ctrl+C during a 3-second python `sleep` → capture lands after the call returns, resume completes (asserts deferred-capture semantics).
- **M7 deterministic:** `Deterministic` sandbox + foreign-bearing program → refusal at **load time**, before any bytecode executes (`required_permissions ∋ Ffi` is load-time-visible; §4.5 Determinism row, ffi-rebuild §4.8.3) — the probe asserts zero side effects ran; the call-time check is probed only as the defense-in-depth backstop via a fixture blob predating the rule; a deterministic snapshot/resume pair around non-foreign code stays byte-identical (composition non-interference).
- **M8 no-local-fallback:** M1's failing call must NOT have executed locally (sentinel side effect absent on the sender).
- **M9 `remote::execute` with foreign source:** shipped source containing `fn python` recompiles on receiver and obeys the same capability + permission gates (§4.8).
- **M10 dormant C-callback registrations across resume:** origin run registers a Shape callback with a fixture C library (ffi-rebuild §4.6.6 pattern), returns from the foreign call (registration dormant, no live frame — the §4.5 barrier is not implicated), snapshots, exits; manifest records `dormant_callback_registrations == 1`; resume → the one-time notice fires exactly once, naming the count, the re-register remediation, and the "FFI callbacks and resume" book anchor; suppressed under the OQ-3 knob; the resumed program itself completes correctly (loss surfaced, not fatal); control: a snapshot with zero registrations resumes with no notice.
- **M11 foreign environment missing on executing node (§4.4.4):** receiver's python lacks a module the body imports (`import not_installed_xyz`) → all load gates pass; first call surfaces the class-1 foreign exception with the Python traceback, mapped to `RemoteErrorKind::RuntimeError`, node address prefixed sender-side — asserted structured (never a panic, never a silent `None`); resume twin on a node with the module absent behaves identically at first call; diagnosability assertion: `remote::ping` capabilities include the `backend` string.

## 8. Open questions for the user

**Ratification record (2026-07-05):** all recommended defaults below were ratified by the user (consolidated as `00-priority-spine-overview.md` §3, Q48–Q54 + Q2). OQ-6's strict-empty default was confirmed as part of the Q15/Q28/Q52 permission trio — the deliberate asymmetry against ffi-rebuild's local `Ffi`-unscoped grant is the ruling. OQ-7 carries its two-part ruling inline below.

1. **Extension version matching policy (§4.3.2 step 4, §4.5).** Recommended: constraint-satisfaction — explicit `semver_req` honored; absent one, same-major as the snapshot's `observed_version` when recorded, else any provider of the language — where "same-major" carries **cargo-caret semantics for 0.x versions** (compatibility window = same-minor; `0.5 → 0.6` counts as breaking, and both shipped extensions are currently 0.x, so this sub-rule is what actually fires today). Alternative: pin-to-observed-exact by default (maximum reproducibility, brittle clusters). Interacts with ffi-rebuild OQ-2 (major-version-in-hash) — ratify the pair together.
2. **`ForeignEntryObject` hoist + one-time format touch (§4.2, A1–A3).** Entries become content-addressed store/wire objects; `CodeManifest` and `RemoteCallRequest` gain fields (additive; manifest fields ride WF-2B's **Stage-2 `SNAPSHOT_VERSION` bump** — one of the three bumps snapshot-resume §4.3.3 schedules; the constant is `SNAPSHOT_VERSION`, not FORMAT_VERSION). Ratify the hoist and the three amendments?
3. **`STATEFUL_OPAQUE` resume caveat surface + notice knob (§4.5).** Recommended: book documentation + a one-time suppressible stderr notice when a resumed VM first re-links a stateful runtime; the same notice channel and knob cover the dormant-C-callback-registration notice (§4.5, probe M10). Recommended concrete knob spelling: `--quiet-resume-notices` on `shape --resume`, twin serve-config key `resume_notices = "quiet"`. Alternatives: docs-only (quieter), or a hard opt-in flag (`--resume-foreign-state-reset-ack`) for programs that declare they rely on cross-call foreign state (loudest). Which surface, and ratify the knob spelling?
4. **No-auto-install stance (§4.3.3).** Ratify "a receiver never installs/fetches/builds extensions in response to network input; refusal + operator remediation is the protocol" as a hard security guarantee (book-documented)? A signed-registry-mediated opt-in could be designed later as its own vertical; nothing here forecloses it.
5. **extern C cross-node strictness (§4.4.3).** v1: alias-resolvability check at load, no platform-triple gate, no library shipping. Is a stricter declared-platform constraint (blob declares `linux-x86_64`, receiver refuses on mismatch before even resolving) wanted, or is resolution-failure-is-the-signal sufficient?
6. **Default `ffi_languages` for `shape serve` (§4.6).** Recommended: empty-by-default (foreign execution requires explicit opt-in on the receiver even when `Ffi` is granted broadly for local tooling reasons) — i.e. remote foreign execution is always a deliberate operator choice. Alternative: `Ffi` grant implies all languages unless scoped (consistent with unscoped-FsRead parity in ffi-rebuild §4.8.2). This is the one place this design proposes being stricter than the FFI doc's local semantics — because the caller is the network. Ratify strict default, or keep parity?
7. **Foreign-function-ref closure captures (A3(iii), R12 — defining the OQ that §4.10/§5 already referenced).** v1 KEEPS the distributed doc's refusal row: a transferred closure that captures a foreign function *as a value* is refused, because no wire representation for that value exists (no `SerializableVMValue` arm, no `NativeKind` story on the §2.7.8 closure-cell kind track, no receiver rebinding rule) — shipping it undesigned is the exact seam that decays into an ad-hoc kind-blind encoding. Ratify (a) the v1 refusal, and (b) whether to green-light the follow-up typed-carrier design (sketch: a dedicated serialized arm carrying the entry `content_hash`, rebound receiver-side through the assembled table via the §4.2.0 ordinal↔hash correspondence) as WF-2F-adjacent work or defer indefinitely.
   **→ RATIFIED 2026-07-05 (Q53): (a) the v1 refusal stands; (b) the typed-carrier follow-up is GREEN-LIT as WF-2F-adjacent work.** The carrier is the sketched serialized arm carrying the entry `content_hash`, rebound receiver-side via the §4.2.0 ordinal↔hash correspondence; the refusal row (and distributed §4.4's) remains in force until that designed carrier lands — never lifted ahead of it.
8. **Declared foreign-environment constraints (§4.4.4).** v1 surfaces foreign-body environment failures (missing python packages, deno cache misses, interpreter skew) at first call with the full foreign traceback, and ships `backend` diagnostics in `remote::ping` + the manifest — but a program cannot *declare* "needs CPython ≥ 3.12" or "needs numpy ≥ 2" for load-verify matching. Should `ExtensionReq` grow a `backend_req` (interpreter constraint, matchable against `runtime_descriptor.backend`), and/or should a per-program foreign-package requirements table exist (`[foreign.python] requires = [...]` — matched how? receiver-side package query is language-specific machinery; self-report is unverifiable)? Recommended: defer — ship diagnostics + the book caveat, revisit with real usage evidence; the alternative grows a package-manager-shaped verification surface Shape should not absorb casually.
