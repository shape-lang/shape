# v0.3.3 Let-Generalization Grounding — Strict-Flip Return-Only-Polymorphism Residuals

Status: analysis / architect call. Date: 2026-05-31.
Author context: strict-flip close-A residual-FP grounding.

## User rulings that frame this (binding)

1. **Shape does let-generalization.** An unconstrained function-return type var
   becomes an inferred generic param. `fn get_none() { return None }` is
   `∀T. () -> Option<T>` — compile-time polymorphism, runtime concrete.
2. **No subtyping.** The "`None`-singleton widens to `Option<T>`" model is OFF
   the table. None of the residuals below depend on subtyping, so this ruling
   constrains the *solution space* (we cannot widen) but does not block any of
   the candidate fixes.

## What the strict flip is, and where it lives

The strict flip is NOT on `main` (HEAD `36d917b6`). It lives on branch
`strict-flip-collection-dispatch` (tip `29c0d655`, 25 commits ahead). On `main`
the relevant inference errors are `TypeError::GenericTypeError`, which is
*filtered* by `should_emit_type_diagnostic`
(`crates/shape-vm/src/compiler/compiler_impl_initialization.rs:863-876` —
allowlist is only `UnknownProperty` + 2 comptime errors) under the default
`TypeDiagnosticMode::ReliableOnly` (`:125`). The flip makes diagnostics
strict-by-default and unfiltered (`docs/cluster-audits/v0.3.3-strict-negative-suite/BREACH-REPORT.md:122-139`),
which is exactly what converts these filtered errors into hard FPs.

Runtime-confirmed on `main` HEAD `36d917b6`:
- `fn get_none(){return None}` + `let x = get_none()` → EXIT 0 (filtered).
- `fn step1(){return Err("boom")}` + `let y = step1()` → EXIT 0 (filtered).
- `let a = []; a.length` → emits the **bytecode-compiler** semantic error
  "empty array `a` has an un-resolvable element type … add an annotation
  (`let a: Array<T> = []`)" — a *different seam* (see §Empty-array).

## The two inference seams

### Fn-boundary phantom-var reject (the return-only-polymorphism seam)

`crates/shape-runtime/src/type_system/inference/items.rs:386-401`. Fires ONLY when:
- (a) `func.return_type.is_none()` (untyped fn), AND
- (b) the inferred return contains a type var not in params/type-params
  (`allowed_vars`), AND
- (c) `matches!(inferred_return_type, Type::Generic { .. })`.

Emits `GenericTypeError "Could not infer generic return type for '<fn>'"`.

The *earlier* gate that actually rejects `get_none` first is
`infer_callable_return_type(&func.body, func.return_type.is_some())` at
`items.rs:357`: unannotated ⇒ `allow_unresolved_generic_args = false` ⇒
`combine_return_types_internal(..., false)` (`mod.rs:1127-1128`) routes the
single `Option<fresh>` candidate into `ensure_no_unresolved_generic_args`
(`mod.rs:956-990`).

Key type-shape facts:
- `None` ⇒ `Type::Generic { base: Option, args: [fresh] }`
  (`operators.rs:34-35,63-70`) ⇒ matches gate (c).
- `Err(x)` ⇒ `Type::Generic { base: Result, args: [phantom_ok, …] }` ⇒ matches (c).
- The generalize machinery the user wants is fully present:
  `env.generalize` (`environment/mod.rs:1250-1263`, quantifies free-not-in-env
  vars, no value-restriction parameter), `TypeScheme::poly`, call-site
  `scheme.instantiate` (`items.rs:139,154`), and `make_function_scheme` already
  falls through to `env.generalize(&func_type)` for untyped fns
  (`items.rs:1170-1177`). The predeclare path (`items.rs:38-65`) already
  produces `∀a. () -> a`; `infer_item` then overwrites it with the rejected
  re-inference.

### Empty-array — a separate, bytecode-compiler seam

`let x = []` ⇒ `Type::Concrete(TypeAnnotation::Array(unknown))`
(`builtins.rs:57-63`, `expressions.rs:190-194`) — **Concrete, not
`Type::Generic`** ⇒ never matches gate (c), never reaches the inference fn-seam.
The unconstrained empty-array reject is a *bytecode-compiler* semantic check
(`crates/shape-vm/src/compiler/v2_typed_emission.rs:870-929`), confirmed at
runtime. It is orthogonal to let-gen and to the value restriction. It already
ships its own remedy: `let a: Array<T> = []`.

## Let-bindings never generalize; there is no value restriction

`infer_variable_decl` (`items.rs:1181-1224`) ALWAYS binds with
`TypeScheme::mono(declared_type)` (`:1218`; destructure paths `:1220`). For an
unannotated `let x = <init>`, `declared_type` is the inferred init type as-is,
wrapped mono. So `let` is monomorphic in the init's (possibly still-unresolved)
type — Shape has no let-generalization today.

There is **no value restriction anywhere**. `generalize`
(`environment/mod.rs:1250`) takes no expression/value-form parameter and
quantifies every free-not-in-env var regardless of how the type was produced.
There is no `is_syntactic_value` / `is_expansive` / `nonexpansive` predicate in
`type_system/`. Because generalization is fn-boundary-only and `let` is
always-mono, the value-restriction question is *moot at let-bindings* — nothing
generalizes there to need restricting.

## Residual classification by FAILING-USAGE class

Three classes drive the architect call:
- **(1) CONSTRAINED-USE / explicit annotation** — a call site or a declared
  return type pins the instantiated `T`. Cleared by fn-boundary let-gen (or,
  for explicit-`-> Result` cases, already-existing declared-return handling).
- **(2) BARE-APPLICATION-CALL** — `let x = get_none()` (or bare top-level
  `get_none()`) where nothing downstream constrains `T`. The function is an
  *application*, not a syntactic value; even with the fn generalized to
  `∀T.()->Option<T>`, the call instantiates a fresh unpinned `T`, `let` binds it
  mono, and it re-trips `ensure_no_unresolved_generic_args` at the
  binding/program level. **Value restriction is the only lever.**
- **(3) BARE-VALUE-BINDING** — `let x = []`; truly-unconstrained. Concrete-Array,
  not the fn-seam; cleared by the empty-array bytecode-compiler check's remedy.

## Answers (NO subtyping is fixed)

### (1) Does fn-boundary let-gen clear all ~10?

**No — only the non-bare-application subset.** It clears **5 of 6**
fn-definition None/Err residuals (all class (1): the call site `?? / !! ?`
pins the instantiated `T`, and the 3-4 explicit `-> Result` Err cases bypass
the seam entirely). It is **irrelevant to all 4 empty-array cases** (Concrete
Array, separate bytecode-compiler seam). It leaves **exactly one** residual
rejecting: the lone class-(2) bare-application-call.

### (2) How many residuals are the bare-application-call case?

**Exactly 1**: `functions/stress_recursion.rs:393` `fn get_none(){return None}`
with bare top-level `get_none()`. The value restriction blocks generalizing an
unpinned application result, so even after fn-boundary let-gen makes
`get_none : ∀T.()->Option<T>`, the bare call instantiates a fresh `T`, `let`
binds mono, and it re-trips `ensure_no_unresolved_generic_args`
(`mod.rs:956-990`).

### (3) Relaxed value restriction — small or large, and sound here?

**It does not apply as framed, and would be a near-non-fix.** A relaxed VR
("generalize covariant-only vars even for applications") is a *let-binding*
generalization concept — but Shape has **no let-generalization at all**
(`let` is always `TypeScheme::mono`, `items.rs:1218`) and **no value
restriction to relax** (`generalize` has no value-form parameter). So adopting
a relaxed VR is not a tweak to an existing knob; it is **introducing
let-generalization wholesale** plus a covariance analysis to decide which vars
are safe to quantify under an application — a **large, new policy** with new
surface area (covariance tracking, interaction with the always-mono `let`
contract, the const-without-type rule at `items.rs:1208`).

Soundness: with no subtyping and no mutable-cell escape on these specific
shapes (`Option<T>` from a pure `None`, immutable `let`), generalizing the
covariant return var *would* be sound for this one case. But that soundness is
shape-specific; a general relaxed VR needs the full covariance/variance machine
to stay sound across the language, which Shape does not have. The cost is in the
machinery, not the soundness of the single case.

### (4) Architect call

**Fn-boundary let-gen + annotation-required for the lone bare-application
residual.** Concretely:

- **Adopt fn-boundary let-gen** (the user's ruling) — clears the 5 class-(1)
  fn-def residuals. This is a **small, focused extension**: at the
  `items.rs:357`/`386-401` reject, when `func.return_type.is_none()` and the
  only unresolved vars are covariant return-position vars the body never
  materializes, **quantify them into the scheme instead of rejecting**. The
  machinery already exists (`env.generalize` at `items.rs:1176`, `TypeScheme::poly`,
  call-site `instantiate` at `items.rs:139,154`); the predeclare path
  (`items.rs:38-65`) already builds `∀a.()->a`. The change is the
  `allow_unresolved_generic_args` flag plumbed `items.rs:357` →
  `statements.rs:71-126` → `mod.rs:1025/1113/1127`, plus letting
  `make_function_scheme` keep the now-free return vars.
- **For the lone class-(2) bare-application** (`get_none()` with nothing pinning
  `T`): **annotation-required** — `let x: Option<T> = get_none()` (or simply use
  the result somewhere that pins `T`). This is the cheapest correct rule, aligns
  exactly with the existing empty-array remedy (`let a: Array<T> = []`), and
  keeps `let` always-mono (no new let-generalization policy, no relaxed-VR
  machinery). The test `stress_recursion.rs:393` should be amended to pin `T`
  (it is a test of recursion, not of unconstrained-bare-call inference).
- **Do NOT adopt a relaxed value restriction.** It does not reach the fn-def
  residuals (they reject before any `let`), and for the one case it could reach
  it costs a wholesale let-generalization + variance subsystem to remain sound.
  Out of proportion to one test.
- **Empty-array residuals**: keep on their existing seam (bytecode-compiler
  semantic check + `.length` short-circuit + collection-method seeding). No
  let-gen / VR work needed; the truly-unconstrained two are already served by
  the `let x: Array<T> = []` remedy.

### (5) Decision left for the user

**The bare-unconstrained-application policy.** Fn-boundary let-gen is ruled and
clears 5 of 6 fn-def cases. The ONE remaining lever is for the single
class-(2) residual `let x = get_none()` (`stress_recursion.rs:393`) where the
binding never constrains `T`:

- **Option A (recommended): annotation-required.** `let x: Option<T> = get_none()`
  or pin `T` at use. Cheapest; keeps `let` always-mono; mirrors the shipped
  empty-array `let a: Array<T> = []` remedy. Requires amending one test.
- **Option B: introduce let-binding generalization** (generalize the binding's
  free covariant vars). Larger; new policy on `let`; would let
  `let x = get_none()` stand as `∀T. Option<T>` (monomorphized per use).
- **Option C: relaxed value restriction** (generalize covariant-only vars even
  for applications) — equivalent in cost to B (it presupposes let-gen) plus a
  variance subsystem; not recommended.

No-subtyping is unaffected by any option (none widen `None` to `Option<T>`).
