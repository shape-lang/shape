## §2 — `HashMap key must be a string` Throw-Site Map

**Single dispatch point** in the codebase:

- **File:** `/home/dev/dev/shape-lang/shape/crates/shape-vm/src/executor/objects/hashmap_methods.rs`
- **Function:** `fn as_string_key(slot: &KindedSlot) -> Result<&str, VMError>` (lines 485–501)
- **Error site:** Lines 496–499

```rust
_ => Err(type_error(format!(
    "HashMap key must be a string (got kind {:?})",
    slot.kind
))),
```

**Dispatch:** This function is invoked from 7 call sites in the same file (all in hashmap method handlers):
1. `v2_get` (line 557) — `HashMap.get(key) -> value`
2. `v2_has` (line 623) — `HashMap.has(key) -> bool`
3. `v2_get_or_default` (line 725) — `HashMap.getOrDefault(key, default) -> value`
4. `v2_set` (line 785) — `HashMap.set(key, value) -> HashMap` (the critical path for `set::from_array`)
5. `v2_delete` (line 1233) — `HashMap.delete(key) -> HashMap`
6. `v2_merge` (line 1337) — `HashMap.merge(other) -> HashMap`

All 7 call sites check `as_string_key(&args[1])` on the key argument before proceeding.

**No V-kind discrimination:** The `as_string_key` function does NOT distinguish between different value kinds (`V` in `HashMapKindedRef::V`). It only validates that the **key** is a string (`NativeKind::String` or `NativeKind::Ptr(HeapKind::String)`). The receiver's V-kind (what value type the HashMap holds) is orthogonal — a HashMap can hold Int64, Float64, Bool, Char, String, Decimal, TypedObject, TraitObject, or HashMap values, but all of them require string keys.

**Enforcement scope:** The check is **unconditional** — there is no "promote empty HashMap to int-key variant" path at the method level (only at the TypedObject field-write level; see W17.3-4.3 below).

## §4 — JIT Garbage-Return Root Cause

**Divergence signature (Repro 1):**
- **VM:** ec=1, clean error message from `as_string_key`
- **JIT:** ec=0, V2 bytecode verification warnings (eprintln only), garbage integer return

### Root Cause Analysis

1. **JIT compilation succeeds** but emits v2 typed opcodes (NewTypedArrayI64, TypedArrayPushI64) without corresponding FrameDescriptor entries.

2. **Bytecode verifier runs** (in `executor/vm_impl/program.rs::load_program`, lines 95–105) and reports violations via `eprintln` — but **does not block execution**. The error condition is logged but the program continues.

3. **Why the verification failures occur:** The JIT compiled the `std::core::set::len` function (which is a pure-Shape stdlib function that calls `s.len()` on a HashMap). The JIT emitted typed array operations to support this, but the v2 typed opcode register (FrameDescriptor) was not populated because the JIT compiler is not yet wired to emit FrameDescriptors for v2 typed operations (ADR-006 §2.7.24 Q25.B SUPERSEDED tracking per the comment).

4. **Execution continues despite verification failures:** With unverified typed opcodes in play, the HashMap.set() call from `from_array` still executes, but when it reaches the string-key check in `as_string_key`, the call path is not properly instrumented (the JIT-emitted code path doesn't route through the runtime method handler that does the check).

5. **Result:** Instead of surfacing the RuntimeError, the JIT-compiled code silently proceeds with invalid state, eventually returning a garbage integer when attempting to return from the function.

### Code Evidence

**V2 Bytecode Verifier** (`crates/shape-vm/src/bytecode/verifier.rs`, lines 88–96):
```rust
VerifyError::V2MissingFrameDescriptor {
    function_name,
    opcode,
    instruction_offset,
} => write!(
    f,
    "V2 typed opcode {:?} at offset {} in function '{}' has no FrameDescriptor",
    opcode, instruction_offset, function_name
),
```

**Verification is Warning-Only** (`crates/shape-vm/src/executor/vm_impl/program.rs`, lines 95–105):
```rust
#[cfg(not(debug_assertions))]
{
    if let Err(errors) =
        crate::bytecode::verifier::verify_v2_typed_opcodes(&self.program)
    {
        eprintln!(
            "V2 bytecode verification failed: {} violation(s)",
            errors.len()
        );
        for e in &errors {
            eprintln!("  - {}", e);
        }
    }
}
```

The errors are printed but do not halt execution. The program proceeds with unverified bytecode.

### JIT Compiled-Code Path Gap

The JIT compiler does not yet have the infrastructure to emit proper FrameDescriptors for v2 typed operations. This is tracked as an ADR-006 §2.7.24 SUPERSEDED item (per phase-2d-playbook.md) — the post-V3-S5 ckpt-6 STRICT closure will rebuild v2 typed-array carriers as `TypedArray<T>` (v2-raw shape per ADR-006 §2.7.5).

Until that closure lands, JIT-emitted v2 typed opcodes are incomplete (missing FrameDescriptor entry), verification warns (but doesn't block), and the unverified code path diverges from VM's interpreted path.

## §5 — Divergence-Elimination Minimum (Unconditional Gating)

**Binding requirement per Group 1 dispatch:** The JIT path that returns garbage on `set::from_array([1,2,3])` must surface-and-stop cleanly, eliminating the VM/JIT divergence.

### Minimum Fix Path (Two Options, Both Required)

#### Option A: Surface-and-Stop at Bytecode Verification (Immediate)

**Action:** Make V2 bytecode verification violations **fatal** (change eprintln to return error, halt execution).

**File:** `crates/shape-vm/src/executor/vm_impl/program.rs`, lines 95–105.

**Pseudocode:**
```rust
if let Err(errors) =
    crate::bytecode::verifier::verify_v2_typed_opcodes(&self.program)
{
    eprintln!(
        "V2 bytecode verification failed: {} violation(s)",
        errors.len()
    );
    for e in &errors {
        eprintln!("  - {}", e);
    }
    // NEW: Return error instead of continuing
    panic!("Bytecode verification failed — unverified opcodes not executable");
}
```

**Effect:** Any JIT-compiled function that emits unverified v2 typed opcodes will panic immediately, surfacing the error clearly. This eliminates the silent-garbage-return case.

**Impact:** This is a **gating fix** — it unblocks further investigation because the JIT path will now surface instead of silently diverging.

#### Option B: Disable JIT Emission of Unverified Typed Opcodes (Medium-term)

**Action:** Prevent the JIT compiler from emitting v2 typed opcodes when FrameDescriptor entries cannot be populated. Fall back to interpreted path for functions using these opcodes.

**File:** `crates/shape-jit/src/compiler/...` (codegen for v2 typed operations).

**Effect:** When JIT encounters a v2 typed operation, check if FrameDescriptor support is available. If not, emit a fallback-to-interpreter signal (existing `[jit-fallback]` path) rather than incomplete bytecode.

**Impact:** JIT will gracefully degrade, matching the interpreter's behavior.

### Minimum Closure: Both A and B Required

- **Option A** is immediate (defensive — prevent silent divergence).
- **Option B** is follow-up (corrective — emit correct code, not incomplete code).

Together, they guarantee:
1. **No silent divergence:** Unverified bytecode → error surface (Option A).
2. **No incorrect JIT output:** Missing FrameDescriptor → fallback to correct interpreter (Option B).

## §6 — Full Alignment Scope (v0.3 Piggyback vs v0.4 Standalone)

### What This Audit Does NOT Cover

1. **Setting integer keys on HashMap.** The audit empirically confirms that `HashMap().set(1, "v")` fails with the same error on both VM and JIT (aligned). This is pre-existing behavior, not a divergence.

2. **Per-container key-kind generics.** W17.3-4.3 did not add int-key support for HashMap/Set. That would require:
   - HashMap method dispatch routing to **per-key-kind** handlers (HashMap<string, V> vs HashMap<int, V> vs HashMap<bool, V>, etc.)
   - A matching **value-kind discriminator** similar to the existing V-kind enum in HashMapKindedRef (currently only strings are keys)
   - Rebuild of set.rs and all callsites to support polymorphic key types

   This is a **large workstream** (v0.4 candidate).

3. **StringV2 vs String key kind distinction.** Repro 2 shows `set::from_array(["a","b"])` fails with `(got kind StringV2)` — a different kind than the Int64 case, yet same error message. Both are rejected as non-string. This indicates the check is comparing `slot.kind` to `NativeKind::String` (inline string tag) but rejecting both `NativeKind::String` and `NativeKind::Ptr(HeapKind::String)` via the `_` wildcard arm. The distinction is pre-existing and not addressed by this audit.

### Alignment Scope Summary

| Surface | Scope | Prerequisite | Timing |
|---------|-------|--------------|--------|
| **Divergence elimination (JIT garbage → error)** | Option A (fatal verification) + Option B (fallback codegen) | Independent of key-kind support | **v0.3 gating** (unconditional) |
| **HashMap int-key support** | Full HashMapKindedRef generalization + method dispatch routing + Set stdlib rebuild | Separate workstream (not W17.3-4.3) | **v0.4 standalone** |
| **Set<int> usability via public API** | Depends on int-key support + Set module refactor | Same as above | **v0.4 standalone** |
