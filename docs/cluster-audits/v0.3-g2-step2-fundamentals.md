**Classification:** (a) — doc claims a contract the compiler explicitly
rejects with v0.4 framing.

**Edit applied (UNCOMMITTED in shape-web):** snippet relabeled
`runnable=false` with a documenting comment quoting R8 W8 Cluster A and
the v0.4 follow-up tag from `docs/v0.3-close-summary.md` §5.15.

No other (a)-class single-snippet fix surfaces in this Step 2 round. The

## §3 (b)-class — NEW v0.3-gating bugs

Each (b) below is **NEW relative to Step 1's slice-B findings** (which

### §3.B.1 Drop trait runtime: VM crash + JIT silently no-ops

**Pages affected:** `resource-management.mdx` (entire page — the central
contract that "drop runs automatically at scope exit").

**Empirical:**

Program: `resource-management/01_drop_trait.shape` (a `FileHandle` with
`impl Drop`, instantiated in a `{ ... }` block; doc claims drop runs at
block exit and emits "Closed file: ...").

- VM: `Error: Runtime error: MakeRef Local outside any call frame (line 1)`
  → exit code 1, drop never observed.
- JIT: `opened /tmp/a.txt` / `after block` → exit code 0, **drop never
  called** (no "Closed file:" output).

Program: `resource-management/02_reverse_drop_order.shape` (three
resources declared in a fn; doc claims reverse drop order across normal
exit).

- VM: `Error: Runtime error: MakeFieldRef base must reference a
  TypedObject; got Bool (line 16)` → exit code 1.
- JIT: `body running` / `done` → exit code 0, **no drops emitted**.

The book chapter `resource-management.mdx` is 100% `runnable=false`
snippets, but the page's contract is the load-bearing one: "Every `let`
binding that implements the `Drop` trait is automatically dropped when
its enclosing scope exits." Both modes break that contract in different
directions:
- VM: SURFACEs in the MakeRef / MakeFieldRef MIR-lowering path for
  Drop-bearing locals.
- JIT: silently elides the drop call entirely (consistent with the
  `runnable=false` snippets passing because nothing observable runs).

**Class:** (b) — both modes are wrong relative to the documented
contract. JIT silently-elide is the more dangerous variant (no visible
diagnostic; user assumes cleanup ran).

**Notable.** The single Drop program that DID emit drops on JIT
(`resource-management/03_drop_in_loop.shape`) only worked because the JIT
fell back to the interpreter (deopt printed in stderr) before reaching
the drop site — i.e. the for-loop body's `print` is the deopt trigger,
and the interpreter then executes the documented behaviour. Without that
deopt, JIT would no-op silently.

**Workstream tag (proposed):** `v0.3-drop-trait-runtime-vm-mir-surface +
v0.3-drop-trait-jit-elision`. Re-classifying as v0.3-gating because the
chapter is shipped at v0.3 status.

### §3.B.2 `Some(v) ?? default` returns `Some(v)` not `v`

**Pages affected:** `error-handling.mdx` (Quick Reference table, line 49:
"`a ?? b` | default for `None`"), `variables.mdx`, `operators.mdx` (line
449-455 "Coalesce (`??`)").

**Empirical:**

```shape
let maybe_name: Option<string> = Some("Ada")
let n1 = maybe_name ?? "anonymous"
print(n1)
```

- VM: `Some("Ada")` (expected: `Ada`)
- JIT: same `Some("Ada")` after `[jit-fallback]` deopt to interpreter.

The `None` arm DOES return the default correctly:

```shape
let nothing: Option<string> = None
let n = nothing ?? "default"  // → "default" ✓
```

**Class:** (b) — the doc's Quick Reference table phrasing "default for
`None`" implies `Some(v) ?? d → v`. The runtime returns the wrapped
`Option` in the `Some` arm.

**Workstream tag (proposed):** `v0.3-coalesce-some-unwrap`.

### §3.B.3 `print(None)` displays as `null`

**Pages affected:** `variables.mdx` (line 156-161 No-Null-Sentinel
section: `print(missing) // → ?`), `error-handling.mdx`,
`names-and-scope.mdx`.

**Empirical:**

```shape
let missing: Option<int> = None
print(missing)
```

- VM: `null`
- JIT: `null` (after `[jit-fallback]` deopt).

**Class:** (b) — Shape's documented stance is "Shape does not model
absence with `null`" (variables.mdx line 152). The Display for an
`Option::None` value should print `None` (matching `Some(v)` → `Some(v)`
which works correctly). The `null` output is the wire-protocol
representation leaking through `print`'s value formatter.

Both modes match, so user-visible behaviour is consistent — but it
contradicts the No-Null-Sentinel section's text exactly: print displays
the very sentinel the language claims not to have.

**Workstream tag (proposed):** `v0.3-display-option-none-prints-null`.

### §3.B.4 `let (a, b) = await join all {...}` — parse error

**Pages affected:** `async.mdx` (line 47-50, canonical example).

**Empirical:** the documented snippet:
```shape
let (a, b) = await join all {
  fa(),
  fb()
}
```
fails to parse on both modes with a span pointing at the open `(` after
`let`.

**Class:** (b) for `async.mdx` (the documented contract pattern). Note
that variables.mdx says "There is no `(a, b)` tuple syntax for values or
destructuring" — async.mdx contradicts its sibling page. Resolution
direction is a design choice for v0.3 close: either land `(a, b)`
let-destructuring (broaden the grammar) or rewrite the async-join
contract to use array/named-branch destructure consistently across the
page.

**Workstream tag (proposed):** `v0.3-async-let-tuple-destructure-grammar-gap`.

### §3.B.5 `print(s)` on `impl Content for S` renders raw struct, not Content output

**Pages affected:** `content.mdx` (line 113-115 — Sensor example
explicitly marked runnable=true: `print(s)  // → renders line chart in
terminal`).

**Empirical:**

```shape
type Sensor { name: string, readings: Array<number> }
impl Content for Sensor { method render() { ... Content.chart("line")... } }
let s = Sensor { name: "temp", readings: [20.0, 22.0, 21.0, 23.0] }
print(s)
```

- VM: `{name: "temp", readings: [20.0, 22.0, 21.0, 23.0]}`
- JIT: same (after `[jit-fallback]` deopt).

The documented contract is "Content trait dispatch checks for
user-defined implementations before falling back to built-in rendering"
(content.mdx line 118-120). At HEAD the fall-back-first path runs and
the trait dispatch never fires for `print(struct)`.

**Class:** (b) — runnable=true snippet whose stated comment ("→ renders
line chart") is empirically false.

**Workstream tag (proposed):** `v0.3-print-content-trait-dispatch`.
