## §3 (b)-class v0.3-gating list (NEW for team-lead dispatch)

Three NEW v0.3-gating items surfaced. All are JIT-side regressions; all VM
behaviour is correct or near-correct. Listed in dispatch-priority order.

### §3.B.1 **JIT-TYPED-ARRAY-PUSH-FRAMEDESCRIPTOR-MISSING** — `.push` on owned/aliased typed arrays fails V2 verification + SEGFAULTs

**Cite:** references-borrowing-s04 + variables-s05 (CoW SEGFAULT exemplars) +
references-borrowing-s08 (`&mut arr` + `arr.push(value)` verification-fail
exemplar). Single root cause: `TypedArrayPushI64` (and the related
`NewTypedArrayI64`) opcodes lack registered FrameDescriptors at certain
emission sites.

**Symptom (s04, s05):** VM does not SEGFAULT but the dev-mode last-value
print emits `{"String": "<future:108405530198528>"}` (a debug print of an
internal future-pointer). JIT SEGFAULTs (ec=139) with stderr:
```
V2 typed opcode TypedArrayPushI64 at offset NNN in function 'std::core::remote::remote___before' has no FrameDescriptor
```
(multiple offsets in `remote___before`).

**Symptom (s08):** VM hits SURFACE: `ArrayPushLocal: SURFACE — V3-S5 ckpt-5
consumer-cascade tier 3 surface` (the borrow-path push goes through a v0.3
SURFACE territory). JIT executes (ec=0 because the snippet has no top-level
print) but prints a V2 bytecode verifier complaint:
```
V2 bytecode verification failed: 4 violation(s)
  - V2 typed opcode NewTypedArrayI64 at offset 2070 in function 'append' has no FrameDescriptor
  - V2 typed opcode TypedArrayPushI64 at offset 2073 in function 'append' has no FrameDescriptor
  ...
```

**Hypothesis:** The CoW (copy-on-write) path for aliased `var` bindings
emits `TypedArrayPushI64` opcodes inside the `remote::remote___before` hot
path without registering a corresponding FrameDescriptor — the JIT
deoptimization map lookup misses, leading to abort.

**VM-side behaviour:** VM does not SEGFAULT but the dev-mode last-value
print emits `{"String": "<future:104487957735792>"}` (a debug
print of an internal future-pointer). This is a SECONDARY VM bug: the
dev-mode auto-print of the last-evaluated value should produce `()` or
nothing for a no-explicit-print snippet, not a debug-format future-ptr.

**v0.3-gating disposition:** primary surface is the JIT SEGFAULT (clear
contract violation — `var + push` is the canonical CoW demo throughout the
ownership docs). VM debug-future-print is a secondary surface; bundle if
single fix territory, otherwise separate ticket.

**Probable territory:** `crates/shape-jit/src/` FrameDescriptor registration
for stdlib hot paths (`remote::remote___before` suggests stdlib-loaded
trampolines run un-instrumented under JIT); cross-ref the V3-S5 ckpt-6 JIT
FFI territory (criterion C).

### §3.B.2 **JIT-OPTIONAL-CHAIN-SEGFAULT** — `?.` + `??` chains crash JIT (pre-existing-known)

**Cite:** operators-s26.

**Repro:**
```shape
type Server { port: int }
type Config { server: Server }
let cfg: Option<Config> = None
let port = cfg?.server?.port ?? 8080
print(port)
```

**Symptom:** VM emits `8080` (ec=0, correct). JIT dumps core (ec=139).

**Hypothesis:** chained `?.` (optional-property-access on a `None`-typed
receiver) followed by `??` (null coalesce) emits a JIT codegen path that
doesn't handle the `None`-flow short-circuit; control-flow falls through to
an unmapped slot.

**v0.3-gating disposition:** **NOT NEW** — the operators.mdx page already
marks this snippet `runnable=false` AND has a `:::caution` block (lines
470-474) explicitly citing "the `?.` operator works under the VM but
currently triggers a JIT SIGSEGV on the chained-access shape above. Use an
explicit `match cfg { Some(c) => ..., None => ... }` until the JIT close-out
lands." This is a PRE-EXISTING-AND-DOC-KNOWN issue surfaced by the
present audit; not a new finding. Tracked here for §3.B aggregation only.

**Probable territory:** `crates/shape-jit/src/` — `optional_property_access`
codegen + `??` `BinaryOp::NullCoalesce` JIT lowering.

### §3.B.3 **TARGET-SIDE-FROM-CONVERT-SURFACE** — `100.0 as Celsius` via `impl From<number>` SURFACE

**Cite:** error-handling-s09.

**Repro:**
```shape
type Celsius { degrees: number }
impl From<number> for Celsius {
    method from(value: number) -> Celsius { Celsius { degrees: value } }
}
let temp = 100.0 as Celsius   // expected: works via auto-derived Into
```

**Symptom (VM and JIT identical):**
```
Error: Runtime error: Not implemented: `Convert` opcode (TryInto/Into trait
dispatch) cascades on two still-SURFACE dependencies: (1) kinded trait-method
resolution + §2.7.11/Q12 value-call dispatch on the resolved closure,
(2) `build_any_error` AnyError TypedObject builder in
`executor/exceptions/mod.rs`. ADR-006 §2.7.4 / §2.7.11. ...
```

**Hypothesis:** The `Convert` opcode's TryInto/Into trait dispatch is
explicitly surfaced as SURFACE pending §2.7.11 / Q12 value-call dispatch +
AnyError TypedObject builder. The error message itself names the
remaining surface dependencies.

**v0.3-gating disposition:** the error-handling page presents target-side
`From`/`TryFrom` auto-derivation as a primary contract (see
"Target-Side: `From` / `TryFrom`" section, line 167). Surface is already
named in the runtime error message; gating item should fold into the
§2.7.11 value-call SURFACE close-out work (already underway under criterion
C / W17 ckpt-6 cluster).

**Probable territory:** `executor/exceptions/mod.rs` (`build_any_error`) +
trait-method dispatch resolution. Cross-references criterion C / Phase-2c
host-tier marshal/snapshot rebuild's outstanding §2.7.11 follow-ups.

**Cross-reference note:** functions-s08 (`.map` on `Vec<int>` with
