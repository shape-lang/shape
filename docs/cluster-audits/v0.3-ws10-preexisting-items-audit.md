## ITEM (a) — Bytecode verifier "16 violations on every run"

### Reproduction (HEAD `cbc020ba`, release binary)

`./target/release/shape run` on *any* program — even `print(1+1)` — emits to
stderr:

```
Bytecode verification failed: 16 violation(s)
  - Trusted opcode LoadLocalTrusted at offset 75 in function 'std::core::math::coefficient_of_variation' has no FrameDescriptor
  - Trusted opcode JumpIfFalseTrusted at offset 79 in function 'std::core::math::coefficient_of_variation' has no FrameDescriptor
  ... (14 more)
```

Then the program executes correctly (`ec=0`, correct output). All 16 violations
are `MissingFrameDescriptor` of the form `Trusted opcode <X> ... has no
FrameDescriptor`, spread over: `std::core::math::coefficient_of_variation` (4),
`Json.{get,at,is_null,keys,len}` (6, `len` ×2), `TryFrom::{string,number,int,
bool}::Json::tryFrom` (5, `number` ×2), `std::core::remote::remote___before` (1).
These are all stdlib functions linked into every program via the prelude.

### Verifier code (pinned)

- Verifier pass: `crates/shape-vm/src/bytecode/verifier.rs` —
  `verify_trusted_opcodes()` (lines 111-174). For every instruction with
  `opcode.is_trusted()`, it errors `MissingFrameDescriptor` if the enclosing
  `Function.frame_descriptor` is `None` (lines 137-145).
- Invocation: `crates/shape-vm/src/executor/vm_impl/program.rs` `load_program()`
  lines 59-106. In a `debug_assertions` build it prints
  `"Bytecode verification warning"`; in a release build it prints
  `"Bytecode verification failed"`. **In BOTH builds the result is only
  `eprintln!`'d — the verifier never aborts, never returns an error, never
  changes execution.** It is a pure-diagnostic pass with no enforcement teeth.

### Trusted-opcode definitions

Only two trusted opcodes survive at HEAD (`crates/shape-vm/src/bytecode/
opcode_defs.rs:468-482`): `LoadLocalTrusted` (0xD7) and `JumpIfFalseTrusted`
(0xD8). The trusted *arithmetic* and *comparison* opcodes (0xCA-0xDF range)
were already deleted — opcode_defs.rs lines 468-470 / 480-482 record that they
"were functionally identical to the typed variants ... in release builds."

### Trace — does the Trusted opcode need the FrameDescriptor at runtime?

**`op_load_local_trusted`** — `crates/shape-vm/src/executor/variables/mod.rs`
lines 1847-1866. The executor body, verbatim shape:

```rust
let (bits, kind) = self.stack_read_kinded_raw(slot);
crate::executor::vm_impl::stack::clone_with_kind(bits, kind);
self.push_kinded(bits, kind)
```

It sources the slot's type from `stack_read_kinded_raw` — the **ADR-006 §2.7.7
stack parallel-`Vec<NativeKind>` track** — *not* from the `FrameDescriptor`.
It is **byte-for-byte identical** to the non-trusted `op_load_local`
(same file, lines 1813-1839). The executor's own doc comment (lines 1841-1846)
states this explicitly:

> "The 'trusted' contract used to mean the compiler skipped runtime tag-bit
> validation; post-ADR-006 §2.7.7 every slot has a concrete kind in the
> parallel track, so the trusted vs untrusted distinction is no longer about
> tag dispatch — both paths read the slot's lockstep `(bits, kind)` directly."

**`op_jump_if_false_trusted`** — `crates/shape-vm/src/executor/control_flow/
mod.rs` lines 179-193. Body: `let (bits, _kind) = self.pop_kinded()?; let cond
= bits != 0;`. It pops the §2.7.7-kinded condition slot and reads the bits
directly. No `FrameDescriptor` access.

**Is the `FrameDescriptor` consulted by the VM interpreter at all?** No.
`current_frame_descriptor()` is *defined* at `crates/shape-vm/src/executor/
vm_impl/stack.rs:960` but a workspace-wide grep finds **zero call sites** in
the executor — the only other mention is a *stale doc comment* at
`variables/mod.rs:17` that still claims kind-sourcing via
`current_frame_descriptor()?.slot(idx)`, a path the executor body no longer
takes. The `FrameDescriptor` is consumed at runtime *only* by the JIT
(`shape-jit`: `worker.rs`, `osr_compiler.rs`, `mir_compiler/v2_call_abi.rs`)
for slot-kind marshaling — and the JIT already has an explicit absent-descriptor
fallback (`worker.rs:143-144`: `FrameDescriptor::default()`;
`v2_call_abi.rs:202-210`: legacy `Int64` default for "functions with no
FrameDescriptor at all").

### Why these 16 functions lack a FrameDescriptor (producer side)

`crates/shape-vm/src/compiler/helpers.rs` lines 3290-3342
(`populate_program_storage_hints`). The compiler stamps `frame_descriptor =
Some(...)` **only when every local slot's kind is proven** —
`proven_hints: Option<Vec<StorageHint>>` is built via
`collect::<Option<Vec<_>>>()` which short-circuits to `None` if *any* slot is
unproven (lines 3302-3334). When `None`, the descriptor stays unset.

The 16 functions all have at least one unprovable local slot kind, by design:

- `coefficient_of_variation(series)` — `crates/shape-runtime/stdlib-src/core/
  math.shape:64`. The `series` parameter is **unannotated** — its kind cannot
  be proven by the bytecode compiler's storage-hint pass.
- `Json.*` / `TryFrom::*::Json` — `crates/shape-runtime/stdlib-src/core/
  json_value.shape`. The `Json` enum (lines 16-24) has `Array(any)` and
  `Object(any)` variants — the `any`-typed payload makes the `self`/`value`
  local-slot kind unprovable.

The `Trusted` opcodes are still emitted because the compiler proved the
*individual operands* (e.g. `mean_val == 0` produces a `Bool`; an enum-tag
`match` produces a `Bool` discriminant for `JumpIfFalseTrusted`). Operand-level
kind proof and whole-frame kind proof are independent.

### Empirical — does the absence cause observable misbehavior?

`coefficient_of_variation` could not be exercised to completion because its
body calls `__intrinsic_std`, which itself panics with a *separate, unrelated*
`phase-1b-vm wave 5d` intrinsic-body stub (`crates/shape-vm/src/executor/
vm_impl/builtins.rs:525`) — out of scope for this audit, noted as a distinct
pre-existing stub.

`Json.is_null` was exercised directly: `Json::Null.is_null()` returns `true`
correctly. The `JumpIfFalseTrusted` at offset 10 in `Json.is_null` (one of the
16 violations) executed and produced the correct result with **no
FrameDescriptor present**. No crash, no wrong result — the verifier complaint
is **inert**.

### Classification — ITEM (a): verifier is STALE / OVER-STRICT → **v0.4**

The verifier rule "every trusted opcode must appear inside a function with a
`FrameDescriptor`" encodes the **pre-§2.7.7 trusted-opcode contract**, when
trusted opcodes skipped runtime tag-bit validation and relied on
descriptor-supplied metadata to justify the skip. The §2.7.7 migration
(`crates/shape-vm/src/bytecode/verifier.rs` last touched by `9f396786`
"phase-1b-vm Wave-ζ Z-compiler-option-cascade"; the trusted-opcode executors
rewritten in the §2.7.7 cluster-B / Wave-δ work) moved kind-sourcing to the
stack parallel-`Vec<NativeKind>` track. Post-migration, `LoadLocalTrusted` and
`JumpIfFalseTrusted` are **identical to their non-trusted twins** and do not
read the `FrameDescriptor` at all in the VM interpreter.

- The check-skipping is **NOT unfounded** — there is no check being skipped on
  the basis of the descriptor. The kind comes from the §2.7.7 lockstep track,
  which is populated by the typed producer regardless of whether the
  whole-frame descriptor was stamped.
- There is **no latent soundness gap**: the JIT — the only runtime
  `FrameDescriptor` consumer — already has an explicit, documented
  absent-descriptor fallback.
- The verifier is **stale over-strict noise**, not a correctness signal.

This is **incomplete-but-clean → v0.4**. It is NOT v0.3-gating: nothing is
known-incorrect, no soundness gap, no observable misbehavior — the opcodes are
sound without the descriptor.

**However** — the audit also flags that the verifier *currently mislabels its
own output*. In a release build it prints `"Bytecode verification FAILED"` for
what is, post-§2.7.7, not a failure. The honest v0.4 fix is one of:
(1) drop the `MissingFrameDescriptor` rule for the two surviving trusted
opcodes (their contract no longer depends on the descriptor), or
(2) downgrade the wording to a non-alarming diagnostic and stop printing it on
every run. Either way the verifier should not be telling users "verification
failed" on a clean prelude. This is a v0.4 verifier-rule-refresh item, logged
here so it is not lost as "noise."

## ITEM (b) — the 314 `cargo test -p shape-vm --lib` failures

### Reproduction

`direnv exec /home/dev/dev/shape-lang cargo test -p shape-vm --lib` at HEAD
`cbc020ba`:

```
test result: FAILED. 1596 passed; 314 failed; 26 ignored; 0 measured; 0 filtered out
```

Exactly **314 failures**, confirmed. `just check-clean` (the canonical
workspace gate) is green — these are test-*run* failures, not build failures.

### Bucket-by-panic-message (all 314)

Every failure's `stdout` block was extracted (314 sections) and bucketed by
panic message:

| Count | Bucket |
|------:|--------|
| **285** | `phase-2c` host-tier-stub (`not yet implemented: phase-2c — see ADR-006 §2.7.4`) |
| **29**  | NON-`phase-2c` (broken out below) |

The 285 `phase-2c` failures all cite the same root-cause family —
`ADR-006 §2.7.4 host-tier eval/marshal API rebuild` (deleted
`ValueWord` / `Constant::Value(ValueWord)` / host-tier carriers; the test
harnesses call a deleted host-tier eval/marshal API). Sub-wording variants
within the family (all `phase-2c`): `host-tier eval/marshal API rebuild` (×67),
`...deleted ValueWord/Constant::Value carrier` (×130), `...deleted host-tier
carriers` (×32), `...deleted helper` (×16), `KindedSlot heap accessors pending`
(×8), and ~10 smaller-count variants (`NativeScalar`/`TypedTable`/`RowView`/

`set_ops` ×19, `v2_handlers::integration_tests` ×18, `channel_ops` ×14, ...).
Uniform class.

### Classification — ITEM (b): all 314 are pre-existing relative to round-6

The mission asked: are all 314 the `phase-2c` class, or is a round-6 regression
hiding inside the red?

**Finding:** The mission's *as-stated* claim ("all 314 are confirmably the
phase-2c host-tier-stub class") is **inaccurate** — only 285 are `phase-2c`;
29 are a different panic. **BUT** the regression risk this audit exists to
catch is **NOT present**: the set-diff against the round-6 baseline shows
**zero new failures**. All 314 — the 285 `phase-2c` *and* the 29 non-`phase-2c`
— were already failing at `3f227c63`, before any round-6 WS work landed. None
is a round-6-introduced regression. None is a soundness failure observed in
running user code (every one is a *test-harness* panic against deleted/stubbed
APIs or a pre-existing inference/REPL/parse defect).

Classification per the no-known-incorrectness binding:

- **285 `phase-2c` host-tier-stub** — incomplete-but-clean. The test harnesses
  call a deliberately-deleted host-tier eval/marshal API (`ADR-006 §2.7.4`);
  the surface-and-stop is honest (`unimplemented!("not yet implemented:
  phase-2c ...")`), not a wrong-result. **→ v0.4** — the known
  ADR-006 §2.7.4 host-tier-rebuild cluster.
- **29 non-`phase-2c`** — all pre-existing at the round-6 baseline, none a
  round-6 regression. Disposition split:
  - 8 `TypedArrayData consumer-cascade SURFACE` + 4 arg-count-kind + 2
    Option-as-cast-lift + 2 DataTable.select-lambda — honest
    `NotImplemented(SURFACE)` / clean `RuntimeError`, no wrong-result; the
    `V3-S5 ckpt-5` surfaces are the documented `TypedArrayData` /
    `TypedBuffer<T>` deletion-cascade follow-up. **→ v0.4** (incomplete-but-clean),
    unless an owning workstream re-scopes a specific one.
  - 2 `Queryable<T>` parse — the parse defect explicitly named in CLAUDE.md
    Known Constraints. **→ v0.4** (documented known constraint).
  - 5 + 2 REPL cross-cell persistence, 1 trait-return-backfill, 1 io-export,
    1 const-fn-specialization, 1 runtime-error-payload — pre-existing test
    failures not in round-6 territory. None observed as a wrong-result in
    running user code from this audit; each is a test-harness assertion or a
    pre-existing inference/REPL gap. **→ v0.4** as pre-existing, **with the
    caveat** that the REPL-persistence cluster (7 tests) and the
    runtime-error-payload test assert *user-visible* behavior and warrant a
    targeted owning-workstream look before v0.3 ship — they are flagged here
    so they are not lost. They are NOT v0.3-gating *as a round-6 regression*
    (the set-diff proves they predate round-6), but the supervisor may elect
    to scope the REPL-persistence regression-vs-pre-existing question
    separately.

**Bottom line for ITEM (b):** the round-6 merge is clean — 0 regressions,
verified by exact set-diff against `3f227c63`. The "all 314 phase-2c" wording
is wrong (285/314), but the buckets are all pre-existing and the only
v0.3-gating-eligible question (a round-6 regression hiding in the red) is
answered NO.
