## §2 Root-cause investigation: per-trigger analysis

### Trigger KC #6(b) — stack overflow in typed_closure_in_array_map

**Analysis:**

The closure `|x| x * 2` is passed to `.map(|x| body)`, which has generic signature `fn map<T>(self: Array<T>, f: (T) -> T2) -> Array<T2>`. The closure param `x` should infer as `int` from the array element type.

The stack overflow occurs during **compilation** (not runtime), evidenced by the `V2 bytecode verification failed` warnings. The error stack trace is not captured in the test output, but the symptom pattern — stack overflow + `NewTypedArrayI64`/`TypedArrayPushI64` frame-descriptor violations — suggests:

1. **Inference recursion loop:** The closure param `x` starts as a fresh type variable.
2. Bidirectional inference (CLAUDE.md line 200; `check_expr(..., CheckMode::Synth(expected_ty))` at `expressions.rs:419`) binds `x` to the expected type from the method signature.
3. However, if the method signature lookup or parameter unification is **cyclic** (the closure's inferred return type unifies with the param type, creating a cycle like `TypeVar(n) ~ Function(TypeVar(n) -> ...)` or similar), the constraint solver enters an infinite loop.

**Suspected site:** 
- `crates/shape-runtime/src/type_system/inference/expressions.rs:396-411` (method signature lookup + expected_arg_types computation).
- `crates/shape-runtime/src/type_system/inference/bidirectional.rs:62-68` (check_expr with Synth mode).
- The constraint solver in `crates/shape-runtime/src/type_system/inference/mod.rs` (cycle detection / fixpoint checking).

The closure inference code at `expressions.rs:744-788` (`Expr::FunctionExpr` arm) builds the param type from either (i) explicit annotation or (ii) freshly-generated type var, then refines via `refine_callable_param_types_from_local_constraints`. If the constraint graph is **cyclic**, the refinement may iterate indefinitely without detecting the cycle.

### Trigger KC #6(c) — bubble_sort (Sub: unknown/int)

**Analysis:**

The expression `n - 1 - i` is parsed as `(n - 1) - i` (left-associative). The left operand `n - 1` is a binary op whose left operand `n` is `sorted.length`.

However, `sorted` has been reassigned multiple times in the loop body:
```
sorted = sorted.slice(0, j).concat([sorted[j + 1]]).concat([temp]).concat(sorted.slice(j + 2, n))
```

Each reassignment returns a new array. The type inference must track that `sorted` remains `Array<int>` throughout. The `.length` property access should resolve to `int`.

**Issue:** Either (a) the `.length` property on the reassigned `sorted` is not inferring as `int`, or (b) the `Sub` operator's left operand (the `n - 1` subexpression) is not being typed correctly.

The error message says "operand types are `unknown` and `int`", which suggests the **left** operand (`n - 1` result) is unknown. This points to a **type loss in the property-access chain**:
- `sorted` → type should be `Array<int>`
- `sorted.length` → type should be `int`
- But after the reassignments, the type may degrade.

**Suspected site:**
- `crates/shape-runtime/src/type_system/inference/access.rs` (property access inference, especially field access on reassigned variables).
- `crates/shape-runtime/src/type_system/inference/expressions.rs` (assignment handling; flow-sensitive narrowing).
- The type refinement after reassignment may not propagate the array-element type correctly when the RHS is a chain of `.slice().concat().concat()...` calls.

### Trigger KC #6(f) — sort with closure params (Sub: unknown/unknown)

**Analysis:**

The closure `|a, b| a - b` is an argument to `.sort()`. The method signature should be something like:
```
fn sort<T: Ord>(self: Array<T>, comparator: (T, T) -> int) -> Array<T>
```

Bidirectional inference should bind `a` and `b` to the expected closure-param types derived from the method signature. At `expressions.rs:396-411`, the code calls:
```rust
let gsig_opt = type_name
    .as_ref()
    .and_then(|tn| self.method_table.lookup_generic_signature(tn, method).cloned());
let expected_arg_types: Option<Vec<Type>> = gsig_opt.map(|gsig| {
    let method_vars: Vec<Type> = (0..gsig.method_type_params)
        .map(|_| self.fresh_type_var())
        .collect();
    gsig.param_types
        .iter()
        .map(|pt| {
            MethodTable::resolve_type_param_expr(
                pt,
                &receiver_type,
                &receiver_params,
                &method_vars,
            )
        })
        .collect()
});
```

Then at line 419, the closure is checked with:
```rust
self.check_expr(arg, CheckMode::Synth(expected_ty.clone()))
```

**Issue:** If the method signature **is not registered** in `method_table` for the `.sort()` method, `gsig_opt` is `None`, and `expected_arg_types` defaults to `None`. In that case, the closure is inferred via bare `infer_expr(arg)` (line 427), which generates fresh type vars for the params and has **no hint** to bind them to the array element type.

**Suspected site:**
- `crates/shape-runtime/src/type_system/inference/expressions.rs:396-411` (method signature lookup may be failing to find the `.sort()` entry in `method_table`).
- Alternatively, `MethodTable::resolve_type_param_expr` may be returning `unknown` / `Type::Variable` instead of the concrete array element type.
- `crates/shape-runtime/src/type_system/checking/method_table.rs` (method registry + signature lookup).

## §3 Family hypothesis test

### Q1: Are all 3 triggers caused by the same inference-layer site?

**Answer: PARTIALLY.**

All three failures occur **during type inference for closure parameters**, but they implicate **different inference-layer paths**:

- **KC #6(b)** (stack overflow): Likely a **cyclic-constraint defect** in the closure-param type refinement loop. The cycle may be triggered by a specific method-signature shape (e.g., `map` with a closure param that returns the same type as the input param).

- **KC #6(c)** (Sub unknown/int): Likely a **flow-sensitive type loss** in property access on reassigned variables. The `.length` on a repeatedly-reassigned variable may not maintain its `int` type across the chain. This is orthogonal to closure inference — the closure is not involved.

- **KC #6(f)** (Sub unknown/unknown): Likely a **method-signature lookup failure** or **type-param resolution failure** in `MethodTable::resolve_type_param_expr`. The closure params don't receive the expected type hint because the method signature is not found or cannot be resolved to the array element type.

**Refined hypothesis:** The three triggers are NOT a single root cause; they form **TWO distinct families**:

1. **Family D-α.1 (closure-param-specific):** KC #6(b) + KC #6(f) — both involve closure params in method calls (`.map`, `.sort`). The defect may be in the bidirectional-inference plumbing or method-signature resolution for closures specifically.

2. **Family D-α.2 (flow-sensitive property loss):** KC #6(c) — no closure involved. The defect is type loss on property access through a reassignment chain.

---

### Q2: Is KC #6(b) a closure-inference recursive loop?

**Tentative: YES.**

The stack overflow symptom + `NewTypedArrayI64`/`TypedArrayPushI64` frame-descriptor violations suggest the type checker is recursively **calling itself** (or a transitive dependency) in an undetected cycle. The `.map` signature likely declares a constraint like:

```
fn map<T, T2>(self: Array<T>, f: (T) -> T2) -> Array<T2>
```

When the closure `|x| x * 2` is checked against the expected type `(T) -> T2`, the inference engine:
1. Binds `x` to `T` (the array element type).
2. Infers the body `x * 2` to derive the return type `T2`.
3. The return type may cycle back (e.g., if type unification tries to solve `T2 ~ T` or creates a self-referential constraint).

**Distinct from KC #6(c)/(f):** This is a **constraint-solver cycle**, not an inference-loss issue. The inference system **enters infinite recursion**; the typing is not wrong, it's non-terminating.

---

### Q3: Is KC #6(c) closure-param inference at all?

**Answer: NO.**

KC #6(c) has **no closure** in the failing expression. The bubble_sort test uses a `while` loop with simple variable reassignment. The defect is:
- **Type loss on property access through reassignment chain.**
- **Type loss on binary-op left operand across multiple reassignments.**

This is a **flow-sensitive type narrowing / tracking defect**, NOT a closure-param-inference class.

## §6 ADR amendment shape

**Does any new invariant need to be added, or does the fix operate within existing ADR-005 / ADR-006 contracts?**

### D-α.1 (closure-param inference)

The fix likely adds **cycle detection to the constraint solver** or **early-exit logic to bidirectional inference when a cyclic type is detected**. This is a **mechanical improvement** within the existing type system, not a new invariant. No ADR amendment required.

**Possible scope creep risk:** If the fix requires special-casing closure-param unification (e.g., "don't unify param types with themselves" or "never instantiate a closure param as a function type"), that may warrant an ADR note in §2.7.12 (Q13 — new surface area if added). The fix likely improves **type tracking through reassignment chains** (e.g., ensure that `let mut x = arr; x = x.slice(...).concat(...)` preserves the element type of `x`). This operates within existing ADR-005 / ADR-006 (variable typing + flow-sensitive narrowing), no new invariant needed.
