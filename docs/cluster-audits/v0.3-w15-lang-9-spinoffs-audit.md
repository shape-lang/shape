## §2 Root cause classification

### §2.1 F1/F1'/F1'' — identity-closure return-type inference gap (NEW territory)

**NOT same root cause as LANG-9.** LANG-9 was a producer-side stamp gap at the
**array literal** site (`array_element_types[span]` empty for inline-array
receivers). The fix populated that side-table at `compile_expr_array`.

F1's root cause is at the **closure-return-inference** site, downstream of
LANG-9's fix. Even when `array_element_types[span]` is populated (verified by
the LANG-9 baseline working with `|x|x*2`), the inline-array receiver shape
`.map(|x|x).sum()` still hangs.

Evidence:

- The bound form `let xs = [1,2,3,4,5]; xs.map(|x|x).sum()` ALSO hangs.
  LANG-9's commit message asserts the bound form "succeeded because
  `identifier_concrete_type` reads from `local_array_element_types`" — that
  assertion is FALSE for identity-closure body. Both inline and bound forms
  share the same downstream gap.
- `.map(|x|x*2).sum()` (LANG-9 baseline) WORKS at HEAD.
- `.map(|x|x*1).sum()` and `.map(|x|x+0).sum()` WORK.
- Only the bare-`Expr::Identifier(param)` body shape hangs.

Suspected gap: `resolve_with_closure_return_inference`
(`crates/shape-vm/src/compiler/monomorphization/type_resolution.rs:984-1089`)
calls `infer_closure_body_return_type_name`
(`crates/shape-vm/src/compiler/expressions/closures.rs:265`). For bare-identifier
body, the inner `expr_type` walker at `closures.rs:422` resolves
`Expr::Identifier(name)` against `param_types[name]`. The lookup succeeds in
isolation, but the closure-body extraction path (the `Statement` → terminal-
expression reduction) does not surface the bare-identifier body as a
terminal expression that `expr_type` can resolve in this code path.

The hang is the LANG-9 fall-through signature: generic `Vec.map` stub
(entry_point=0) → infinite loop on inline-array receiver. Same observable
symptom; distinct producer-site (closure-return inference vs array-literal
element type).

**Producer-site shape (ADR-006 §2.7.5 stamp-at-compile-time):** the closure's
bare-identifier body's static type IS the proof — `param_types[ident_name]`
already holds the type. The fix is to ensure `infer_closure_body_return_type_name`
returns `Some("int")` (or whatever the param's resolved type is) for a body
that reduces to a single `Expr::Identifier` referencing a known param.

### §2.2 F3/F3b — `.first()` VM/JIT divergence (NEW territory)

**NOT same root cause as LANG-9.** F3 and F3b expose a **VM/JIT semantic
divergence** in `.first()` method dispatch:

- F3 `print([1,2,3,4,5].first())`:
  - VM: `TypeError: expected object, array, string, or other heap value, got scalar`
  - JIT: prints `1`
- F3b `print([1,2,3,4,5].map(|x|x*2).first())`:
  - VM: prints `2`
  - JIT: prints `None`

Both are **soundness bugs** (VM/JIT result divergence under nominal-execution
inputs). F3 additionally shows the VM cannot even dispatch `.first()` on an
inline typed-array literal (the receiver flow expects a heap value but
receives a scalar slot). F3b shows the JIT cannot resolve the chained
receiver's element-access semantics post-`.map`.

The two failures are **distinct dispatch-path bugs**, not the LANG-9
compile-time side-table gap. Investigation requires:

- F3: VM-side `.first()` dispatch — verify the inline-array receiver
  recovery path delivers a typed-array heap pointer to the method handler,
  not a scalar slot.
- F3b: JIT-side `.first()` — verify the post-`.map` typed-array result is
  recognized as a receiver with element-access semantics (currently
  returning `None` suggests JIT treats the receiver as `Option<_>::None`
  or the wrong heap kind).

### §2.3 F2c — `.reduce()` closure type inference gap (DIFFERENT territory)

`print([1,2,3,4,5].map(|x|x*2).reduce(0,|a,b|a+b))` fails at compile time:

```
error[SEMANTIC]: Cannot infer types for binary operation `Add`: operand types
are `unknown` and `unknown`. Strict typing requires both operands to have a
known concrete type at compile time. Add a type annotation to disambiguate.
```

This is the strict-typing rule biting `reduce`'s 2-param closure. The two
closure params `a` and `b` lack annotated types and the type-inference engine
cannot resolve them from the call site (the accumulator-initial `0: int` and
the receiver element type `int` should both flow to `a` and `b`).

**Distinct territory:** this is `reduce` parametric-closure-type-inference,
not the LANG-9 array-literal side-table or the F1 closure-return inference.
The producer site is `resolve_with_closure_return_inference`'s 2-param
closure-arg-type seeding for `reduce`-shaped methods.

### §2.4 F2b, F4 — V3-S5 ckpt-5/ckpt-6 SURFACE (EXPLICITLY UNREACHABLE)

Both surface with the documented V3-S5 SURFACE diagnostic referencing
`W12-typed-array-data-deletion audit §3.5` and `ADR-006 §2.7.24 Q25.A
SUPERSEDED`. The diagnostic explicitly states:

## §3 Disposition

**AUDIT-ONLY DELIVERABLE + SURFACE split into 3 follow-up sub-clusters.**

Rationale:

- F1/F1'/F1''/F2a covers the inline-array-method family at HEAD; F2a works,
  F1 family hangs. The F1 hang is a **distinct producer-site gap** at the
  closure-return inference layer (downstream of LANG-9's array-literal fix).
- F3 and F3b are **VM/JIT semantic divergence** in `.first()` — this is a
  **soundness bug** affecting result correctness, not a hang or a compile
  error. Investigation requires VM-side and JIT-side dispatch-path triage.
- F2c is a **reduce parametric-closure-inference gap** — separate from F1
  (single-param vs two-param closure inference shapes).
- F2b, F4 are V3-S5 territory — REFUSED ON SIGHT per W12 audit.

Three distinct root causes (F1, F3, F2c) plus one VM/JIT divergence pair (F3
& F3b are closely related but at different dispatch sites). Each requires
its own producer-site investigation + fix. Combined scope **exceeds
single-wave ceiling** (per playbook: "if 2-4 distinct root causes within
ceiling-c: FIX IN SCOPE" applies when they share enough investigation
infrastructure to land together; here each requires a different
investigation territory).

**Refuse #10 (anti-deferral within wave scope) is NOT triggered:** the
split-mandate is the sanctioned exception when distinct root causes
require distinct investigation territories. Each follow-up below has a
crisp territory definition + close-gate shape.

### §7.2 Root cause of audit-framing falsification

The §4.3 compile-error was driven by `concrete_type_for_expr`'s pre-Surface-1B
shape: at the audit commit `35cb6aa4`, `concrete_type_for_expr` returned
`None` for `Expr::MethodCall` receivers (no MethodCall arm), so the chained
`[1,2,3,4,5].map(|x|x*2).reduce(0, |a,b|a+b)` receiver couldn't be resolved
to `Array<int>`, the `install_pending_closure_param_types_for_hof` hints
were never installed, the closure's `a` and `b` stayed untyped, and the
binary op `a + b` failed strict-typing at compile time.

Between audit commit `35cb6aa4` and current HEAD `5d842283`, **Surface-1B
(merge `f37476f7`, close commit `05eb1d6d`) added the `Expr::MethodCall`
arm to `concrete_type_for_expr`** at `crates/shape-vm/src/compiler/monomorphization/type_resolution.rs:1423-1425`,
chaining through `specialized_call_return_concrete_type`. That arm now
returns `Array<int>` for the receiver, the existing
`install_pending_closure_param_types_for_hof` 2-param branch at
`crates/shape-vm/src/compiler/expressions/function_calls.rs:1591-1597`
already produces `vec![Some(int_ann), Some(int_ann)]` for reduce-shaped
HOFs (homogeneous-fold assumption — `a` and `b` both elem-type), and the
closure's `a + b` resolves at compile time.

**No new producer-site work remains for the §4.3 territory.** The 2-param
closure-arg-type seeding for `reduce`-shaped methods is in place at HEAD
via `install_pending_closure_param_types_for_hof`'s `is_reduce` branch;
the Surface-1B `Expr::MethodCall` arm unblocked it for chained-receiver
shapes.
