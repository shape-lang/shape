### G.2 Step 2 methodology (distinct from G.1 Step 1)

G.1 Step 1 audited individual ` ```shape ` fenced blocks under a cumulative-prelude harness. **G.2 Step 2** is a higher-bar test: for each .mdx page, write **2-3 USER-followable example programs** that exercise the core API surface end-to-end, then run them under both `--mode vm` and `--mode jit`.

A "USER-followable" program is one a reader could copy from terminal to terminal — a complete `fn main() { ... } main()` script with all required imports, with no sibling-snippet context dependency. This catches surface bugs that the G.1 snippet harness papers over via cumulative prelude.

## §3 — Per-doc finding notes (the (a)-class doc fixes — UNCOMMITTED)

These would be applied as doc edits to `shape-web/book/book-site/src/content/docs/stdlib/...`, but are NOT committed per dispatch §STEP-5 binding. Recorded here for the team-lead's shape-web pass.

### §3.archive — archive.mdx (a)
The doc declares `archive::zip_create(entries: Array<{name,data}>) -> Array<int>` and `archive::tar_create(...)`. At HEAD, `use std::core::archive` + `archive::zip_create(...)` compiles to `module 'archive' has no export 'zip_create'`. The export name is not wired to the runtime registry. **Doc-fix candidate:** add `<Aside type="caution">` noting `zip_create` / `tar_create` / `zip_extract` / `tar_extract` are not bound at HEAD (matches the `parallel.mdx` aside template).

### §3.http — http.mdx (a) + (c) mixed
- (a) http-1/-2 `'await' can only be used inside async function`: the doc shows top-level `await http::get(...)`. Top-level await is only allowed in script-mode files without `fn main() { }`. Wrapping in `async fn main() { ... } main()` is what the example tries; the await still rejects. **Doc-fix candidate:** show two patterns — top-level script (no main, no async wrapper) vs explicit async runtime.
- (c) http-3 `unexpected '}'` on nested-object literal `{ headers: { ... }, timeout: 5000 }`: the parser refuses this shape (likely the `}\n}` close requiring a comma context). Tracking with the broader object-literal pre-existing limitation set.

### §3.io — io.mdx (a) + (b)
- (a) `io::join(a, b, ...)` doc claims varargs path-join; stdlib declares `pub builtin fn join(parts: string) -> string;` (single-string sig) and the export is **not** wired at runtime (`module 'io' has no export 'join'`). Doc + stdlib + runtime registry triple-drift. **Doc-fix candidate:** drop `io::join/dirname/basename/extension/resolve` from doc until runtime wiring lands, OR document that path utilities are not wired at HEAD.
- (b) `io::open(path, "w")` + `io::write(f, "...")` + reopen + `io::read_to_string` panics at `marshal.rs:284: FromSlot<Arc<IoHandleData>>: slot bits decoded to HeapValue::String, not IoHandle. Marshal kind contract violated by caller.` **see §4 io-handle-marshal-kind-contract**.

### §3.json — json.mdx (a) + (c)
- (a) The doc's "Importing" snippet is `from std::core::json use { parse, stringify, is_valid }`, but `json::parse(...)` calls after a `from ... use { parse }` import fail with `Unknown qualified call 'json::parse'. Module namespace calls require an explicit 'use'`. The doc-form import is `from std::core::json use { ... }` but the canonical call form `json::parse(...)` requires `use std::core::json` (namespace import). **Doc-fix candidate:** clarify "import the module namespace (`use std::core::json`) when you call as `json::parse(...)`; import named symbols (`from std::core::json use { parse }`) when you call bare `parse(...)`".
- (a) Doc uses `(data.get("name") as? string)?`. The `as?` operator is a parse error on this construction. The compiler accepts `as` (infallible) and offers no `as?` operator at HEAD per CLAUDE.md known constraints. **Doc-fix candidate:** show pattern-match or `try_into` instead.

### §3.iot — iot.mdx (b)
- (b) iot-1/-3 `Undefined function: now` — calls into `std::iot::types::sensor_reading(...)` reach a stdlib-source body that calls `now()` (timestamp builder) without an explicit prelude binding. **see §4 iot-stdlib-now-undefined**.

### §3.finance — finance.mdx (b)
- (b) finance-1/-3 `Failed to load module 'std::finance::risk'/'std::finance::types': expected something else, found '}'/'/'` — the stdlib-source files themselves don't parse. finance-2 references `@warmup` which is unknown. **see §4 finance-stdlib-parse-failure**.

### §3.physics — physics.mdx (b)
- (b) `Add`/`Sub` inference failure on tuple-/struct-field arithmetic — the doc's example `{ x: 0.0, y: 0.0, vx: 10.0, vy: 20.0, t: 0.0 }` passed to `projectile_step(state, dt)` reaches a stdlib body where arithmetic on the state fields can't infer types. Overlaps with G.5 Cluster B (generic-arithmetic type annotations applied in 5 files) — physics not yet covered. **see §4 physics-generic-arithmetic**.

### §3.parallel — parallel.mdx OK
The doc's `<Aside type="caution">` already states the API is "not wired at HEAD". Empirical: import compiles; first call yields exactly the documented error message. No doc change.

### §3.simulation — simulation.mdx (c)
The doc's `simulate()` example shows `{ ...state, position: 1, threshold: 100.0 }`. The compiler refuses `...state` spread when `state` lacks a compile-time-known schema, which the doc's example (generic handler param) doesn't have. (c) pre-existing language limitation: spread over typed schemas works, spread over inferred-generic state does not. **Doc-fix candidate:** show explicit-typed initial-state schema in the example.

## §4 — NEW v0.3-gating (b)-class items for team-lead dispatch

### §4.io-handle-marshal-kind-contract — `marshal.rs:284` IoHandle kind contract violation

**Symptom.** `let f = io::open(path, "w"); io::write(f, "data"); ...` panics at `crates/shape-runtime/src/marshal.rs:284:26: FromSlot<Arc<IoHandleData>>: slot bits decoded to HeapValue::String, not IoHandle. Marshal kind contract violated by caller.`

**Repros.** io-1.shape, io-3.shape (both VM and JIT).

**Discipline note.** This is a **panic** — internal contract violation, not a clean compile error. Per CLAUDE.md (a)/(b) rule, panics in a documented happy-path API call are (b)-class regardless of follow-up tracker. Class label: NEW v0.3-gating.

**Suggested ownership.** Marshal layer kind-contract audit for IoHandle (and likely sibling handle types: TCP/UDP/Process — io-1/-3 only exercise the file path).

### §4.xml-stringify-hashmap-marshal — `marshal.rs:761` HashMap-as-Decimal kind contract violation

**Symptom.** `xml::stringify({ name: "root", attributes: { ... }, children: [...] })` panics at `marshal.rs:761:26: FromSlot<Vec<(Arc<String>, Arc<HeapValue>)>>: slot bits decoded to HeapValue::Decimal, not HashMap. Marshal kind contract violated by caller.`

**Repro.** xml-3.shape (both VM and JIT, four-run stability check 4/4).

**Discipline note.** Same marshal-kind-contract panic class as §4.io-handle-marshal-kind-contract. Class label: NEW v0.3-gating.

**Suggested ownership.** Same marshal layer audit. The "decoded to HeapValue::Decimal" surface suggests a kind tag is being miswritten on object-literal construction with nested attributes/children.

### §4.time-instant-elapsed-return-kind — `Instant.elapsed()` return-kind not tracked

**Symptom.** `let t0 = time::now(); ...; let e = t0.elapsed(); print(e >= 0)` fails at compile time: `Cannot infer types for binary operation 'GreaterEq': operand types are 'unknown' and 'int'. Strict typing requires both operands to have a known concrete type at compile time.`

**Repros.** time-1.shape, time-2.shape (both VM and JIT, same compile error).

**Discipline note.** The doc's API reference says `instant.elapsed() -> number`. The compiler's type-tracker doesn't propagate this — the result is `unknown`. Class label: NEW v0.3-gating.

**Suggested ownership.** Method-registry return-kind audit for `Instant.elapsed()`. Likely a one-line annotation in `crates/shape-vm/src/executor/objects/method_registry.rs` or the Instant PHF entry.

### §4.iot-stdlib-now-undefined — `iot::sensor_reading` stdlib body calls undefined `now`

**Symptom.** `let r = sensor_reading("dev-001", 23.5, "C", 0.95)` fails: `Undefined function: now. Function names resolve from module scope, explicit imports, type-associated scope, and the implicit prelude.`

**Repros.** iot-1.shape, iot-3.shape (both VM and JIT).

**Discipline note.** The doc claims `sensor_reading(device_id, value, unit?, quality?)` "Create a sensor reading with current timestamp." The stdlib body presumably calls a `now()` for the timestamp without importing `time::now()`. Class label: NEW v0.3-gating.

**Suggested ownership.** stdlib-source fix at `crates/shape-runtime/stdlib-src/iot/types.shape` (or equivalent) — add the missing `from std::core::time use { now }` import.

### §4.finance-stdlib-parse-failure — `std::finance::risk` / `std::finance::types` stdlib parse failures

**Symptom.** `from std::finance::risk use { sharpe_ratio, max_drawdown }` fails at module-load: `Failed to load module 'std::finance::risk': Module error: Failed to parse module: std::finance::risk: expected something else, found '}'`. Same shape for `std::finance::types` ("expected something else, found '/'") and for `std::finance::indicators::moving_averages` (`@warmup` unknown annotation).

**Repros.** finance-1.shape, finance-2.shape, finance-3.shape (both VM and JIT).

**Discipline note.** stdlib-source itself doesn't parse at HEAD. Doc presents these as production-ready user-facing APIs. Class label: NEW v0.3-gating.

**Suggested ownership.** stdlib-source repair pass on `crates/shape-runtime/stdlib-src/finance/*.shape`. Likely a 2026-05-22..24 reorg drift; the three distinct parse errors (`}` mid-module, `/` mid-module, `@warmup`) suggest multiple incomplete edits.

### §4.physics-generic-arithmetic — generic numeric arithmetic on physics types

**Symptom.** `projectile_step({ x: 0.0, y: 0.0, vx: 10.0, vy: 20.0, t: 0.0 }, 0.1)` reaches a stdlib body where `Add`/`Sub` on state fields fails inference: `Cannot infer types for binary operation 'Add': operand types are 'unknown' and 'unknown'. Strict typing requires both operands to have a known concrete type at compile time. Add a type annotation to disambiguate.`

**Repros.** physics-1.shape, physics-2.shape, physics-3.shape (both VM and JIT).

**Discipline note.** Overlaps in shape with G.5 Cluster B (5 stdlib files annotated for generic-arithmetic) and G.5 Cluster C (empty-array element-type annotations, 2 files). Physics module not yet swept. Class label: NEW v0.3-gating.

**Suggested ownership.** Apply the G.5 Cluster B annotation playbook to `crates/shape-runtime/stdlib-src/physics/*.shape`.
