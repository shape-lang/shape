## 0. TL;DR

`[1,2,3].map(|x| x*2).filter(|x| x>4)` SURFACEs with the V3-S5 ckpt-2
native-stub error; the let-bound form `let m = arr.map(...); m.filter(...)`
works (`[6]`). **This is NOT the native ckpt-2 consumer-cascade rebuild and NOT
a type-inference-proper bug.** It is a one-arm gap in the bytecode compiler's
*receiver-extend-type recovery* (`resolve_receiver_extend_type`), which gates
whether a chained `.filter`/`.map` UFCS-routes to the pure-Shape `Vec.filter` /
`Vec.map` extend method (works) or falls through to the native PHF handler
(`handle_filter_v2` / `handle_map_v2`, both deliberate ckpt-2 SURFACE stubs).

The element type is **not** lost in the type system — the inner `.map`
monomorphizes and records its site, and `concrete_type_for_expr(self, arr.map(f))`
already returns `Some(ConcreteType::Array(...))` via the `Expr::MethodCall` arm
added by the LANG-W13-3 double-filter-chain fix (`type_resolution.rs:1558-1560`).
The proof is recoverable; the dispatch fork simply never asks for it because
`resolve_receiver_extend_type` returns `None` for a `MethodCall` receiver and the
entire UFCS branch (including its monomorphization probe) is skipped.

**Fix: small compiler-side fix. Size S. `is_compiler_inference_fix = true`.**

## 1. Root cause — both sides converge on ONE seam (dispatch-routing, compiler side)

The "inference side" and "dispatch side" of the inbound trace are the **same
single defect**: the receiver-extend-type recovery never consults the
already-recorded monomorphization site for a `MethodCall` receiver.

### 1.1 The fork (dispatch decision, COMPILE-TIME)

`crates/shape-vm/src/compiler/expressions/function_calls.rs:2921-2934` —
`compile_expr_method_call` computes:

```rust
let extend_func_idx = receiver_extend_type.as_deref().and_then(|type_name| {
    let qualified = format!("{}.{}", type_name, method);   // "Vec.filter"
    self.find_function(&qualified).or_else(|| { ... })
});
```

`receiver_extend_type` is the single `Option<String>` that decides the fork:
- `Some("Vec")` → `find_function("Vec.filter")` resolves the pure-Shape extend
  method (`vec.shape:46`), UFCS branch at :2984 fires, emits `Call` → pure-Shape
  push-loop. **Works.**
- `None` → the `"Vec.filter"` lookup is never attempted; `find_function("filter")`
  alone is `None` (filter is registered ONLY as the qualified `Vec.filter` extend
  method — verified `vec.shape:46` inside `extend Vec<T>`); the UFCS branch is
  skipped; dispatch falls through to native `CallMethod` → runtime PHF
  `method_registry.rs:263 "filter" => handle_filter_v2` →
  `array_transform.rs:337 ckpt2_surface`. **SURFACEs.**

### 1.2 The recovery gap (the actual bug)

`receiver_extend_type` comes from `resolve_receiver_extend_type` at
`crates/shape-vm/src/compiler/helpers.rs:4201-4242`. It keys on only three
channels:

1. `last_expr_numeric_type` (helpers.rs:4210) — scalar receivers only; an array
   receiver is not numeric → None.
2. `receiver_type_info.type_name`, stripping `"Vec<int>" → "Vec"`
   (helpers.rs:4223-4228).
3. A receiver-expression shape match (helpers.rs:4232-4241): `Expr::Literal`
   (String/Bool) and `Expr::Array(..) → "Vec"`. Everything else, **including
   `Expr::MethodCall`, falls to `_ => None`** (helpers.rs:4240).

For inline `arr.map(f).filter(g)`, the `.filter` receiver is the
`Expr::MethodCall` node `arr.map(f)`. Its `last_expr_type_info` was cleared to
`None` by the inner `.map`'s own UFCS branch
(`function_calls.rs:3063-3067`): `map` is NOT in the type-preserving allowlist
(`is_type_preserving_table_method`, helpers.rs ≈ filter/where/head/tail/slice/
reverse/concat/orderBy/sort), so the `else` arm sets `last_expr_type_info = None`.
Therefore channel 2 yields None and channel 3 hits `_ => None`. Result:
`receiver_extend_type = None`, the UFCS branch is skipped, and dispatch lands on
the native ckpt-2 stub.

### 1.3 The element type is NOT lost — the proof is already recorded

The "inference is fine, dispatch is the problem" claim is verified:

- The inner `.map(f)` monomorphizes and records
  `monomorphized_method_call_sites[(span, current_fn)] = specialized_idx`.
- `concrete_type_for_expr(self, receiver)` has an `Expr::MethodCall` arm at
  `crates/shape-vm/src/compiler/monomorphization/type_resolution.rs:1558-1560`
  (the LANG-W13-3 double-filter-chain fix) that calls
  `specialized_call_return_concrete_type` (type_resolution.rs:1794-1816), which
  reads `monomorphized_method_call_sites` and reduces the specialized callee's
  substituted `Vec<U>` return annotation to `ConcreteType::Array(U)`.
- `try_monomorphize_method_call` (function_calls.rs:4187) already calls exactly
  this — `concrete_type_for_expr(self, receiver)` — and is proven to return
  `Some(Array(...))` for the inline map MethodCall. It is simply never reached,
  because the UFCS branch (and its inner monomorphization probe at :2955-2983) is
  gated behind `receiver_extend_type` being non-None.

So both inbound trace sides are correct and describe the **same seam**:
`resolve_receiver_extend_type` (helpers.rs:4201, the recovery) feeds the fork
(function_calls.rs:2921, the dispatch). There is no separate "inference proper"
bug and no native-handler bug to fix.

### 1.4 Why the let-bound form works (the load-bearing asymmetry)

`let m = arr.map(...)` runs a SEPARATE re-stamp at
`crates/shape-vm/src/compiler/statements.rs:5394-5424`
(cluster-2-cw-IC-class-c): it calls `specialized_call_return_concrete_type` to
recover `ConcreteType::Array(elem)` and then `set_local_type_info(local_idx,
"Vec<elem>")`. Loading the identifier `m` then re-loads that stamped type via
`identifiers.rs:362` (`self.last_expr_type_info = local_type`), so at the
`m.filter(...)` site channel 2 of `resolve_receiver_extend_type` returns
`Some("Vec")` → UFCS → pure-Shape `Vec.filter`. The explicit-annotation form
`let m: Vec<int> = ...` works the same way.

**The inline-chain MethodCall receiver has no equivalent re-stamp.** That — and
only that — is the gap. The recovery channel for the `let`-binding path
(`specialized_call_return_concrete_type`) is identical to the one the fix needs;
it just isn't wired into the receiver-shape match.

## 2. Minimal fix — small compiler-inference/dispatch-routing fix (NOT the native rebuild)

**Site:** `crates/shape-vm/src/compiler/helpers.rs:4232-4241`
(`resolve_receiver_extend_type`, channel 3).

Add an arm for `Expr::MethodCall` (and ideally any non-Array/Literal receiver)
that, when channels 1-2 produced nothing, calls the EXISTING
`crate::compiler::monomorphization::type_resolution::concrete_type_for_expr(self,
receiver)` and maps the result:

- `ConcreteType::Array(_) => Some("Vec")`
- `ConcreteType::HashMap(..) => Some("HashMap")` / `String => Some("String")`
  / etc. (mirror of the existing channel-2 base-name reduction)
- anything unresolvable → `None` (surface-and-stop preserved)

This is the same call `try_monomorphize_method_call` (function_calls.rs:4187) and
the `let`-binding re-stamp (statements.rs:5394) already make, and it is already
proven to return `Some(Array(_))` for the inline map MethodCall. With "Vec"
recovered, the UFCS branch at function_calls.rs:2984 fires, the inner
monomorphization probe at :2955-2983 specializes `Vec.filter` on the now-known
element type, and dispatch reaches the pure-Shape `Vec.filter` push-loop — exactly
as the let-bound and explicitly-annotated forms already do.

**Borrow/signature compatibility (verified):** `resolve_receiver_extend_type` is
`&self` (read-only); `concrete_type_for_expr` takes `&BytecodeCompiler` (also
read-only). No borrow conflict, no signature change.

**ADR-006 §2.7.5 stamp-at-compile-time discipline preserved:** the specialized
callee's substituted return annotation IS the proof. No runtime tag decode, no
`is_heap()` probe, no Bool-default, no fabricated kind. When the monomorphization
site is absent the helper returns `None` and dispatch surfaces — no silent
fallback.

**Forbidden-pattern hygiene (CLAUDE.md):** the fix routes to the EXISTING
pure-Shape `Vec.filter` / `Vec.map` extend method. It does NOT soften the native
`ckpt2_surface` stub, does NOT add a native handler, does NOT add a
`Convert<X>To<Y>` opcode, does NOT add a dynamic fallback or any
bridge/probe/helper/hop/translator/adapter/shim. It extends a first-class
compiler type-recovery channel that is already used on two other paths. No
defection-attractor framing required.

> Alternative (equivalent, slightly larger): instead of clearing
> `last_expr_type_info` for non-type-preserving HOFs at function_calls.rs:3063-3067,
> re-stamp it from the specialized callee's `Vec<U>` return annotation via
> `specialized_call_return_concrete_type` (the same source statements.rs:5394
> uses). This fixes the symptom at the producer rather than the recovery; the
> helpers.rs arm is narrower and the recommended shape because it touches one read
> site and cannot regress the `last_expr_type_info` contract for other consumers.

## 4. Affected inline-chain shapes + WHY the survive/SURFACE split

**Invariant (run-verified, `--mode vm`, debug HEAD):** any inline chain whose
OUTER receiver is an `Expr::MethodCall` loses the extend-type tag at
`resolve_receiver_extend_type`, so the outer call falls to native PHF dispatch.
Whether it SURFACEs then depends solely on whether the native PHF handler for the
outer method is a working v2 handler or a ckpt-2 SURFACE stub.

The native ckpt-2 SURFACE stubs are exactly the closure-callback transforms that
emit a new array of unknown element kind. Verified at
`array_transform.rs` `ckpt2_surface(` call sites (lines 320/337/492/509/526):

**`map`, `filter`, `flatten`, `flatMap`, `groupBy`** → native handler is a
ckpt-2 SURFACE stub → inline-chain consumer SURFACEs.

Every other consumer has a WORKING native v2 handler, so the fall-to-native is
harmless:

**`sum`, `reduce`, `len`/`count`, `slice`, `take`, `drop`, `concat`, `sort`,
`reverse`** → working native handler → inline-chain consumer survives.

| Shape | Result | Route |

The `filter().*` vs `map().*` asymmetry the original report observed is a red
herring of WHICH inner op happened to be chained: `filter` is in
`is_type_preserving_table_method` (so it forwards `last_expr_type_info`), `map`
is not. The true invariant is the §4 one: an `Expr::MethodCall` outer receiver
loses the extend-type tag whenever the inner op is non-type-preserving (e.g.
`map`), and then SURFACEs iff the outer op's native handler is a ckpt-2 stub.

## 5. Size + lane

- **Size: S.** Single arm added to `resolve_receiver_extend_type`
  (helpers.rs:4232-4241), reusing the existing, already-proven
  `concrete_type_for_expr` recovery. One read site, read-only `&self`, no
  signature change, no ADR amendment. Self-contained `--mode vm` reproductions
  + the let-bound working baseline give a tight regression-verification surface.
- **Lane:** NEW seam, but folds naturally into the **v0.3.3 compiler
  inference/dispatch lane** alongside the c8 (closures-S1) and PB2 (`?`-inference)
  type-stamp-propagation fixes — all three are compile-time type-recovery-publish
  gaps, though at three distinct seams. It does NOT fold into the native V3-S5
  ckpt-2 consumer-cascade rebuild and must be kept distinct from it (the fix
  routes AROUND the native stub to the existing pure-Shape method).

## 6. Compiler-inference-fix flag

`is_compiler_inference_fix = true`. The let-bound-works / annotated-works
evidence (§1.4, §4.2) proves the pure-Shape `Vec.filter` / `Vec.map` carrier is
fully capable; the only defect is the inline-chain receiver losing the (already
recorded, already recoverable) `Vec<elem>` type at the dispatch-routing helper.
No native handler rebuild is needed — the fix is a small compiler-side
type-recovery-channel extension that propagates the inner `map<U>` return element
type to the chained receiver so dispatch reaches the existing pure-Shape method.
