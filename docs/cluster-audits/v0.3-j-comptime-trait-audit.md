Comptime trait primitive: `comptime trait Name { ... }` + `comptime impl Trait for Type { ... }` parser + type-checker (enforce methods comptime-only; clean compile error on runtime call) + comptime-evaluator dispatch. ### §1.C Comptime evaluator infrastructure

**File:** `crates/shape-vm/src/compiler/comptime.rs`

**Existing mini-VM executor (lines 1–160+):**
- Comptime execution result carrier: `ComptimeExecutionResult { value: KindedSlot, directives: Vec<ComptimeDirective> }`
- **COMPTIME_BUILTIN_FORWARDERS table (lines 21–40):** Pre-registered comptime builtins:
  - `implements(trait, type)` → comptime dispatches to `__comptime__.implements`
  - `warning(msg)`, `error(msg)` → directives
  - `build_config()` → builds config object at comptime
  - `type_info(T)` (W7 2026-05-17) → typed return (kind, name, fields, params, annotations, captures)
- **Dynamic closure over existing dispatch:** these forwarders are pre-compiled into the comptime environment and use QualifiedFunctionCall dispatch (`__comptime__::method_name`)

**What's NOT implemented:**
- User-defined comptime traits — no trait-method dispatch in the mini-VM yet
- Comptime method calls on comptime-trait implementations
- Compile-error when calling a comptime-trait method outside comptime context

### §1.D Type-checker: trait registration and impl validation

**File:** `crates/shape-runtime/src/type_system/inference/items.rs`

**Lines 532–537:** `register_trait(trait_def)` — registers trait into environment
**Lines 538–800+:** `register_impl(impl_block)` — registers impl, validates methods against trait signature (arity check at lines 553–578)

**Current validation:**
- Method arity must match trait signature (checked via `TraitMember` name + param count)
- No current check for `is_comptime` flag (doesn't exist yet on trait/impl)

**What's missing:**
- After impl registration, if `impl_block.is_comptime`, mark all methods in that impl as comptime-only
- Method-call type-checker must check: if receiver type is a comptime-trait method, reject call outside comptime context
- Integration point: `method_table.resolve_method_call()` (line 432 of expressions.rs)

### §1.E Method dispatch via method_table

**File:** `crates/shape-runtime/src/type_system/environment/registry.rs` and `crates/shape-vm/src/executor/objects/method_registry.rs`

**Method registry structure:**
- PHF maps per type (String, Array, HashMap, DateTime, user types, etc.)
- Per-method: name + arity → `MethodFnV2` (the compiled handler)
- **No current "is_comptime" metadata on method entries**

**Runtime dispatch (shape-vm):** `op_call_method` → `dispatch_method` → PHF lookup → handler call

**What's needed:**
- Mark comptime-trait methods in the registry as compile-time-only
- **Or** (simpler): skip runtime registry entirely; comptime-trait methods only exist at compile time
- Type-checker blocks runtime calls before reaching the runtime

### §1.F Existing comptime field support (structural pattern to mirror)

**File:** `crates/shape-ast/src/ast/types.rs` lines 665–668

```rust
pub struct StructField {
    pub is_comptime: bool,  // ← exists
    // ... other fields
}
```

**How it works:**
- Parser: optional `comptime` keyword before field name (line 140 of shape.pest)
- Type-checker: marks field as compile-time-only
- Compiler: field is evaluated at compile time; value baked into type metadata (used for `type_info` reflection)

**This pattern is exactly what trait/impl need.**

## §2 Per-territory analysis

### §2.A Parser gap — shape.pest

**Current state:**
- Line 195: `trait_def = { annotations? ~ "trait" ~ ident ~ ... }`
- Line 220: `impl_block = { "impl" ~ type_name ~ "for" ~ ... }`
- Neither has optional `comptime` keyword prefix

**Required change:**
1. Add optional `comptime_keyword?` before `"trait"` in trait_def rule
2. Add optional `comptime_keyword?` before `"impl"` in impl_block rule
3. The `comptime_keyword` rule (line 143) already exists and is correct

**Effort estimate:** <1h (2-line changes + test cases for parse tree structure)

**Gap severity:** BLOCKS everything downstream — parser must succeed first.

### §2.B AST structures — shape-ast crate

**Required changes:**
1. Add `pub is_comptime: bool` field to TraitDef (line 507)
2. Add `pub is_comptime: bool` field to ImplBlock (line 533)
3. Both follow the pattern from FunctionDef.is_comptime (serde default = false)

**Parser integration points:**
- Parser's `parse_trait_def()` must capture optional comptime keyword → set is_comptime
- Parser's `parse_impl_block()` must capture optional comptime keyword → set is_comptime

**Effort estimate:** ~1–2h (2 struct fields + parser wiring)

**Gap severity:** CRITICAL — without AST representation, comptime traits can't flow through the compiler.

### §2.C Type-checker: marking methods as comptime-only

**File:** `crates/shape-runtime/src/type_system/inference/items.rs`

**Current flow:**
1. `register_impl()` is called for each impl block (line 538+)
2. For each method in the impl, trait signature is validated (line 557+)
3. Method is registered into `self.method_table` via something like `register_method(method_name, handler_sig, ...)`

**Required extension:**
- After line 547 (start of register_impl), check `impl_block.is_comptime`
- If true: mark all methods in that impl as "comptime-only"
- **Mechanism:** Add a parallel metadata map in MethodTable: `HashMap<(TypeName, MethodName), bool>` tracking comptime-status, OR add `is_comptime` field to method registry entry (per §1.E)

**Consumer: method-call type-checker** (expressions.rs:432):
- When resolving a method call, check if the method is comptime-only
- If yes AND we're NOT in a comptime context → emit clean semantic error: "Cannot call comptime-trait method outside comptime block"
- If yes AND we ARE in a comptime context → allow it (add to comptime dispatch)

**Effort estimate:** 3–5h (trait method metadata + type-checker call-site validation)

**Gap severity:** HIGH — without this, the type-checker won't enforce the "comptime-only" constraint.

### §2.D Comptime evaluator: trait method dispatch

**File:** `crates/shape-vm/src/compiler/comptime.rs`

**Current state:**
- The comptime executor is a mini-VM that runs bytecode at compile time (lines 1–400+)
- COMPTIME_BUILTIN_FORWARDERS (lines 21–40) pre-registers specific builtins
- Method calls inside comptime blocks use the normal interpreter dispatch + a wrapper layer

**Required extension:**
1. **Trait method registration in comptime environment:** When the main compiler processes `comptime impl Foo for Bar { ... }`, insert those method implementations into the comptime VM's type environment
   - This mirrors what happens for non-comptime impls, but the comptime VM needs access to them
2. **Method-call dispatch at comptime:** When the mini-VM encounters `my_bar_instance.foo_method()` (where foo_method is a comptime-trait method), dispatch it the same way as any other method — but the handler is only available in comptime, not at runtime
3. **Carve-out: NO new dispatch path.** Comptime-trait methods use the same `MethodFnV2` dispatch as regular methods; the difference is *when* they're available, not *how* they're called

**Effort estimate:** 4–6h (environment wiring + dispatch integration)

**Gap severity:** MEDIUM-HIGH — without this, comptime-trait methods can be parsed and type-checked but won't actually execute.

### §2.E Runtime method registry: clean separation

**File:** `crates/shape-vm/src/executor/objects/method_registry.rs`

**Key insight from ADR-005 §1 + ADR-006:**
- Single-discriminator principle: HeapValue is canonical
- Comptime-only methods should NOT appear in the runtime method registry at all
- Clean separation: compile-time-only methods live ONLY in the comptime environment; runtime registry is unaware of them

**Required action:**
- **No changes to the runtime method registry structure** — it's correct as-is
- **Compiler responsibility:** Do NOT register comptime-trait methods into the runtime PHF maps
- **Type-checker responsibility:** Prevent any code path that would try to call them at runtime (§2.C handles this)

**Effort estimate:** ~0h (validation only — no code changes needed)

**Gap severity:** LOW (risk is high if done wrong, but no active coding needed; validation at §2.C type-checker ensures clean separation)

## §4 ADR amendment shape

**Assessment:** NO amendment needed.

**Rationale:**
- ADR-005 §1 (single-discriminator): comptime-trait methods don't change HeapValue dispatch; they live compile-time-only, separated by type-checker validation.
- ADR-005 §2 (String exception): unchanged.
- ADR-005 §4 (uniform slot ABI): unchanged.
- ADR-006 §2.3 (HeapValue payloads carry typed Arc): unchanged.
- ADR-006 §2.7.5 (stamp-at-compile-time): unchanged; comptime traits follow same stamping discipline as comptime functions.
- ADR-006 §2.7.7 (parallel-kind invariant): unchanged.
- ADR-006 §2.7.10 (MethodFnV2 ABI): unchanged; comptime-trait methods use same ABI, just not registered at runtime.

**Existing ADR coverage:** comptime-fn exists in ADR-006 (comptime functions follow the same pattern; just extending to traits is additive, not architectural).

**Conclusion:** The feature is an orthogonal addition to existing comptime infrastructure. No invariants are violated; no new layer structure is needed. Audit-day confirms no ADR text amendment required.

1. **Const-fn markers** — e.g., "should we annotate comptime functions as const?" — NO. Out of scope; v0.4.

## §8 Comptime infrastructure readiness verdict

**READY FOR DISPATCH: YES, with minor structure additions.**

### Existing strengths
- ✅ **Comptime-fn already proven:** Pattern is established; we're extending to traits
- ✅ **Comptime evaluator is robust:** Handles expressions, statements, dispatch to __comptime__ builtins
- ✅ **Type-checker integration exists:** Trait/impl registration works; just needs comptime metadata
- ✅ **Method dispatch is clean:** No tagged fallback; single-discriminator HeapValue + PHF lookup
- ✅ **AST structure is sound:** TraitDef and ImplBlock are well-designed; just need is_comptime field

### Gaps (all solvable within ~1–2 sessions)

- ❌ **AST:** Missing is_comptime bool on TraitDef/ImplBlock (straightforward field addition)
- ⚠️ **Type-checker:** No current metadata tracking comptime-method status; needs method-call validation

- ✅ **ADR-006 §2.7.5 (stamp-at-compile-time):** Maintained — comptime-trait methods stamped at compile time, not runtime
- ✅ **All forbidden patterns (CLAUDE.md):** Not violated — no tagged dispatch, no dynamic fallback, no ValueWord resurrection

### Scope discipline assessment
- ✅ **User binding is clear:** "JUST primitive + dispatch + error"
- ✅ **Refusal #10 applies:** Scope creep (const-fn, compile-time-generics, etc.) is explicitly forbidden
- ✅ **No half-baked paths:** Comptime-trait methods either work cleanly or are rejected at type-check time

## Conclusion

The Shape v0.3 comptime infrastructure is **mature and ready for trait-primitive extension.** The feature fits cleanly into the existing comptime-fn pattern; the needed changes are localized to parser (add keyword), AST (add field), type-checker (add validation), and evaluator (add registration). No architectural changes required; all four ADRs remain satisfied.

**Estimated total effort:** 6–12h across 4 sub-clusters; ~1–2 sessions with parallelization. The 4 empirical gates (parse, type-check, evaluate, error) are all achievable via straightforward integration.

**Risk assessment:** LOW. This is an additive feature that reuses proven patterns (comptime-fn, trait registration, method dispatch). The only novel piece is the type-checker validation blocking runtime calls to comptime-trait methods — a clean semantic check with no runtime cost.
