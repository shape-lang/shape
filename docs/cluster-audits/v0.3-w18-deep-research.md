## §0 Audit scope

**USER HYPOTHESIS** (to verify or refute):

1. **NORMAL FORMATTING via f-strings**: interpolation + smart inline styling (e.g. `f"hello {name:bold,red}"`)
2. **RICH OUTPUT via BUILDER PATTERN**: tables, charts, structured docs (e.g. `Table::new().headers(...).row(...).build()`)

```rust
    self.infer_interpolation_specifications(value, *mode, *span)?;

```

f-strings infer to type `string`.

### Compiler lowering

**File:** `crates/shape-vm/src/compiler/string_interpolation.rs` lines 159-217.

**Strategy:**
1. Parse interpolation parts
2. For each literal part: `PushConst(text)`
3. For each expression part: compile expression → `FormatValueWithMeta(1)` (or `FormatValueWithSpec` if format spec present)
4. Concatenate all with `StringConcat`

**Output:** Stack produces a single `string`.

### Inline styling support today

**Current f-string format specifiers:** (lines 85-92 of interpolation.rs)

```rust
pub enum InterpolationFormatSpec {
    Fixed { precision: u8 },          // f"{value:fixed(2)}"
    Table(TableFormatSpec),            // f"{table:table(...)}"
    ContentStyle(ContentFormatSpec),   // Defined but...
}
```

**ContentFormatSpec structure:** (lines 106-143)
- `fg`/`bg`: `Option<ColorSpec>` (Named or RGB)
- `bold`, `italic`, `underline`, `dim`: bool
- `chart_type`, `x_column`, `y_columns`: chart hints
- `fixed_precision`, `border`, `max_rows`, `align`: table/layout hints

**BUT:** Line 133-146 of string_interpolation.rs shows the comment:

```rust
Some(InterpolationFormatSpec::ContentStyle(_)) => {
    // Content style specs are handled at the content rendering level,
    // not during string interpolation compilation.
    // For now, treat as plain format (no spec).
    let count = self.program.add_constant(Constant::Int(1));
    // ... fall through to FormatValueWithMeta
}
```

**Empirical status:** `ContentStyle` is parsed, threaded through the type system, but **currently ignored at compile time**. f-strings with styling syntax parse successfully but strip styling at lowering.

**Test:** `f"hello {name:bold,red}"` compiles to plain string concatenation (styling lost).

### Gap from current to proposal

The user vision calls for `f"hello {name:bold,red}"` to:
1. **Parse** ✓ (already works)
2. **Infer type** as `string` (remains true)
3. **Compile** to bytecode that tags each interpolated span with style metadata
4. **Dispatch through renderer** per `RenderContext` adapter (TERMINAL → ANSI, HTML → `<span>`, etc.)

**Current gap:**
- Compiler discards `ContentStyle` specs (line 133-146)
- IR carries no per-interpolation style metadata
- Renderer layer has no input hook (f-strings produce bare strings, not styled `ContentNode`)
- f-string is **output-agnostic** — same string on terminal and JSON

### Stdlib / test / book f-string call sites

**Prevalence:** f-strings are heavily used throughout the stdlib and tests (estimate >500 call sites). All current usage is `f"{expr}"` with no format specs or styling.

## §D Output-awareness mechanism

### Adapter selection: static vs runtime-switchable

**Current:** TERMINAL is hardcoded in `printing.rs:349`.

```rust
let adapter = shape_runtime::content_dispatch::adapters::TERMINAL;
```

**Detection method:** TTY detection via `terminal_width()` (detects COLUMNS env var, defaults to 80). No per-invocation switch.

### RenderContext propagation

**Scope:** Stays within the executor's print path. Does not propagate through intermediate formatter calls.

**Implication:** If a nested function calls `print()`, it sees the same TERMINAL adapter. No way to request "give me HTML output instead".

### Design space for runtime-switchable adapter

**Current blocking issue:** `print()` is a hardcoded global builtin. No parameter for adapter selection.

**Options:**

1. **Extend print signature:** `print(value, adapter: "terminal" | "html" | "markdown" | "json" | "plain")`
   - Requires parser/compiler work
   - Breaks existing `print(value)` call sites

2. **Per-function print variant:** `print(...)`, `print_html(...)`, `print_markdown(...)`
   - Function overloading (naming convention)
   - Stdlib-tier wrapper layer

3. **Global render-context thread-local:** Set `RenderContext::set_global_adapter(adapter)` at runtime startup
   - No per-call control
   - Simplest to implement

4. **Capture adapter from execution context:** VM carries a `current_adapter: &str` field
   - Requires VM plumbing
   - Per-context switchability

## §E Existing builder-pattern surface

### Search for Builder pattern in stdlib

**Query:** `find crates/shape-runtime/stdlib-src -name "*.shape" | xargs grep -l "Builder\|\.build()\|\.new()"`

**Result:** **No builder-pattern API exists in Shape user code.**

**Rust-side builder:** `ContentNode` methods exist (`ContentNode::plain()`, `.with_bold()`, `.with_fg()`, etc. at lines 264-346 of content.rs). These are Rust convenience methods, not exposed to user code.

### ContentNode construction in user code

**Current mechanism:** No direct user access. c-string compiler emits the `MakeContentText` / `MakeContentFragment` / `ApplyContentStyle` builtin calls. User cannot construct `ContentNode` directly.

**Implication:** Users cannot build tables, charts, or key-value structures at runtime. All rich content must come from c-strings.

### Design space for builder API

**Option 1: Per-type constructors**

```shape
type Table { ... }
impl Table {
    static method new() -> TableBuilder { ... }
}

type TableBuilder { ... }
impl TableBuilder {
    method headers(names: Array<string>) -> TableBuilder { ... }
    method row(cells: Array<string>) -> TableBuilder { ... }
    method build() -> content { ... }
}

// Usage:
let t = Table::new().headers(["A", "B"]).row(["1", "2"]).build()
print(t)
```

**Option 2: Free-function constructors**

```shape
fn table(headers: Array<string>) -> TableBuilder { ... }
fn chart(type: string) -> ChartBuilder { ... }

// Usage:
let t = table(["A", "B"]).row(["1", "2"]).build()
```

**Option 3: Trait-based**

```shape
trait ContentBuilder {
    method build() -> content;
}

impl ContentBuilder for Table { ... }

// Usage:
let t: ContentBuilder = Table::new()...
let content = t.build()
```

**Option 4: Macro-based** (requires annotation/comptime expansion)

```shape
let t = table! { headers: ["A", "B"], rows: [["1", "2"]] }
```

### Trade-offs

| Design | Verbosity | Type-safety | IDE discoverability | Error messages |
|--------|-----------|-------------|-------------------|-----------------|
| Per-type | Medium | High | Excellent (method chain) | Clear (type mismatch) |
| Free-fn | Medium | Medium | Good (function list) | Good |
| Trait | Low | Medium | Poor (trait name req) | Generic |
| Macro | Low | High | Excellent (IDE support) | Opaque |

**Recommendation for MVP:** Per-type constructors. Mirrors Rust builder pattern; familiar to users; strong IDE support.

## §F User-facing Display surface

### Current display.shape

**File:** `crates/shape-runtime/stdlib-src/core/display.shape` lines 1-23.

```shape
/// Convert a value into a human-readable string representation.
trait Display {
    /// Render `self` as a human-readable string.
    method display() -> string;
}
```

**Signature:** Returns `string` (not `ContentNode`).

**Usage:** Applied in print path when type implements Display. Compiler resolves method at compile time (trait lookup).

### Deleted chain (per W18 audit)

W18.0 enum-variant-display (commit `445eac72`) rebuilt the enum Display path to show `Color::Blue(42)` instead of internal `{__variant: 2, __payload_0: 42}`. This is the user-facing Display surface **for enum types specifically**.

Pre-W18: User types rendered via fallback printer (schema walk → `{field: value, ...}`). Post-W18: Enum variant names are resolved and displayed correctly.

**Question:** Does this mean custom Display impls on user types are now honored? **Investigation pending.**

### Gap: What should Display.display() return?

**Current signature:** `method display() -> string`

**Under the proposal:**

- **If return is `string`:** User impl writes formatting logic. Renderer cannot propagate inline styling (styling lost when converting to string). Output is **adapter-agnostic** (same string on terminal and HTML).

- **If return is `ContentNode`:** User impl builds styled content tree directly. Renderer receives full styling + structure. Output is **adapter-aware** (styling rendered per adapter). Requires exposing ContentNode as a user type.

- **If return is styled-f-string equivalent:** User impl returns a structured interpolation result (spans with style metadata). Hybrid approach: less expressive than ContentNode, more expressive than plain string.

**Method name implications:**
- `display()` → convention for `string` return
- `render()` → convention for `ContentNode` return
- `format()` → convention for format-with-specifier pattern

**Design decision needed:** Is Display intended for simple string formatting (keep `string` return) or rich output (switch to `ContentNode` return, rename to `Render` trait)?

## §H Architectural proposal (synthesis)

### 1. F-string extension: styled-text with renderer dispatch

**Grammar:** Already parses `f"{expr:bold,red,fg(red)}"` syntax. Extend type system to propagate `ContentFormatSpec` through to compiler (currently discarded).

**AST + type inference:** No change needed.

**Compiler lowering:** Modify `compile_interpolated_string_expression` to:
- Track each interpolation part's style metadata
- Emit instructions to build `ContentNode::Text(StyledText)` with per-span styling
- Change return type from `string` to `content` (breaking change)

**Alternative (preserve `string` return):** Compile to inline ANSI escape sequences in the string. Terminal-only, not adapter-aware, but less disruptive.

**IR form:** Either:
- (A) `PushConst(text)` → `ApplyContentStyle(style_args)` → `MakeContentText(1)` + Fragment (mirrors c-string lowering)
- (B) Extend `Constant::String` to carry optional ANSI codes

**Renderer dispatch:** Route through 6 renderers per `RenderContext` adapter.

**Effort:** 8-12 hours. **Decision surface:** Return type (string vs content) and term (does `f"..."` become an `content` type?).

### 2. C-string retirement

**Path:** Either (i) hard deletion at v0.3 close or (ii) soft deprecation (warning + continued support in v0.4).

**Rationale for retirement:** Grammar + type system complete; runtime is `todo!()`; no existing call sites; styled f-strings subsume use case.

**If retired at v0.3:**
- Delete `ContentString` variant from `Literal` enum
- Remove `compile_content_string_expression` from compiler
- Deprecation period: none (no shipped usage)

**If soft-deprecated (v0.4 candidate):**
- Add `#[deprecated]` attribute to c-string parsing (if possible at grammar level)
- Document as "use f-string with styling instead"
- Implement runtime builtins in v0.4

**Estimated effort (full retirement):** 4-6 hours (cleanup, tests).

### 3. Builder API: Table + Chart minimum shippable form

**Minimum for v0.3:** Table builder (most requested).

**Scope (Table):**
```shape
type TableBuilder { ... }
impl TableBuilder {
    static method new() -> TableBuilder;
    method headers(names: Array<string>) -> TableBuilder;
    method row(cells: Array<ContentNode>) -> TableBuilder;
    method border(style: BorderStyle) -> TableBuilder;
    method sortable(yes: bool) -> TableBuilder;
    method build() -> content;
}
```

**Effort:** 8-10 hours (5 hours builtin impl + 3 hours tests).

**Chart builder (v0.4 candidate):** Deferred; more complex (typed channels, ECharts integration).

### 4. Display trait integration

**Mechanism:** Wire Display trait lookup into `ValueFormatter::format_kinded` (before fallback printer).

**Signature:** Keep `method display() -> string` for backward compatibility.

**Implication:** User types can override display but cannot produce styled output (styling lost when converting to string).

**Future:** After styled f-strings stabilize, consider `Render` trait with `method render() -> content` return.

**Effort:** 4-6 hours (compiler + tests).

### 5. Output-awareness (RenderContext propagation)

**v0.3 scope:** Keep TERMINAL hardcoded as default for `print()`.

**v0.4 plan:** Extend print signature or introduce `print_html()` / `print_json()` variants.

**Current blocking:** No parameter on builtin print. Requires compiler + stdlib modification.

**Effort estimate:** 6-8 hours per adapter variant (5 new builtins).

### Effort partition: v0.3 close vs v0.4 deferral

**v0.3 critical path (W18-deep-research followup clusters):**
1. **C-string runtime impl (W18.3):** 6-8 hours (implements todo!() at line 774)
2. **F-string styling (W18.4):** 10-14 hours (extend compiler + renderer dispatch)
3. **Table builder MVP (W18.5):** 8-10 hours (builtin + tests)
4. **Display trait integration (W18.6):** 4-6 hours (compiler + tests)

**Total v0.3 effort estimate:** 28-38 hours (4-5 sub-clusters, ~8 hours each).

**v0.4 deferral candidates:**
- Chart builder + TypedChart API
- Multiple renderer output modes (`print_html()`, `print_json()`)
- `Render` trait with `ContentNode` return
- Per-adapter output-context API
- GridSpec / LayoutNode for multi-panel layouts

**Risk inventory:**

| Component | Risk | Mitigation |
|-----------|------|-----------|
| f-string return-type change (`string` → `content`) | Breaking; requires all f-string consumers updated | Alternative: inline ANSI codes, preserve `string` |
| C-string hard retirement (v0.3 close) | No existing usage, but signal that runtime capability incomplete | Document deprecation; leave grammar in place; soft-warn |

## §J Key decision surfaces for user + supervisor

### 1. Return type for styled f-strings

**Question:** Do `f"{expr:bold,red}"` and `c"hello {world:bold}"` return `string` or `content`?

**Option A (return `string`):**
- Embed ANSI codes inline (terminal-only, not adapter-aware)
- Preserve existing f-string return type
- Simple to implement; backward-compatible
- No HTML/JSON rendering of styled text

**Option B (return `content`):**
- Route through 6 renderers
- Terminal → ANSI, HTML → `<span>`, JSON → structured styling
- Breaking change (all f-string consumers must update)
- Full proposal alignment
- More complex (compiler + runtime)

**Recommendation:** Option A for v0.3 (preserve compatibility); Option B in v0.4 after migration period.

### 2. C-string retirement timing

**Option A (hard retirement at v0.3 close):**
- Remove `ContentString` from Literal enum
- No code to migrate (0 call sites)
- Signal: runtime capability complete or abandoned
- Safe because parser already replaced by f-strings

**Option B (soft deprecation for v0.4):**
- Implement runtime builtins (completes the w5e todo!())
- Add deprecation warning in compiler
- One migration cycle for users
- More cautious signal

**Recommendation:** Hard retirement (Option A). No user impact; grammar removed; doc updated to say "use c-strings via f-string styling instead."

### 3. Display trait: method signature and name

**Option A (keep as-is: `method display() -> string`):**
- No change; backward compatible
- User impls cannot produce styled output
- Display is purely string-formatting

**Option B (introduce parallel `Render` trait: `method render() -> content`):**
- Opt-in for user types that want styling
- Parallel API surface (naming confusion?)
- Requires both traits in stdlib

**Recommendation for v0.3:** Keep Display as-is (Option A). Add Render trait in v0.4 after f-string styling stabilizes.

### 4. Builder API shape

**Option A (per-type constructors):**
```shape
let t = Table::new().headers([...]).row([...]).build()
```

**Option B (free-function constructors):**
```shape
let t = table([...]).row([...]).build()
```

**Recommendation:** Per-type (Option A). Matches Rust ecosystem; IDE-discoverable; aligns with planned `Chart::new()` etc.

### 5. v0.3 close vs v0.4 deferral

**Proposal scope for v0.3:**
- W18.3: C-string runtime (or hard retirement)
- W18.4: F-string styling extension (or defer to v0.4)
- W18.5: Table builder MVP (or defer)
- W18.6: Display trait integration (keep as-is for now)

**Effort: 28-38 hours.** Feasible if spread over 4-5 sub-clusters (8h each). Exceeds single-cluster capacity.

**Deferral options if scope overflows:**
- W18.4 (styled f-strings) → v0.4 (complex, requires return-type decision)
- W18.5 (Table builder) → v0.4 (polish, not critical)
- W18.3 (C-string impl) → v0.3 close (complete w5e todo!())
