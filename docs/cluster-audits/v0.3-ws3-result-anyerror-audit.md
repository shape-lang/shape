## §1 — F1 · JIT typed-array index silently elides the bounds check

### §1.1 Reproduction (HEAD `3f227c63`)

`/tmp/ws3/f1.shape`:
```
let xs = [1,2,3]
print(xs[10])
```
| mode | ec | output |
|---|---|---|
| vm  | 1 | `Error: Runtime error: Index 10 out of bounds (length 3) (line 2)` |
| jit | 0 | `0` |

Negative index `xs[-1]`: vm ec=1 `Index -1 out of bounds`; jit ec=0 `0`.
`Array<number>` OOB `xs[10]` on `[1.0,2.0,3.0]`: vm ec=1 clean error; jit ec=0 `0.0`.

**Classification: v0.3-gating.** Silent-wrong-result + VM/JIT divergence + the
JIT silently produces a fabricated value for a memory-unsafe access the VM
correctly rejects.

### §1.2 Pinned source site — the JIT codegen path

`crates/shape-jit/src/mir_compiler/v2_array.rs:838` — `MirToIR::v2_array_get`.
The helper emits a Cranelift bounds-check branch:

```
v2_array.rs:858-872   cmp = icmp UnsignedLessThan(index, len)
                      brif cmp -> in_bounds_block, oob_block
v2_array.rs:874-879   oob_block:  default_val = emit_default(elem_type)
                                  jump merge_block(default_val)
```

`emit_default` (`v2_array.rs:82`) yields `iconst 0` / `f64const 0.0`. So the
OOB branch is present but, instead of trapping or raising a runtime error, it
**jumps to a merge block that produces the element-type zero**. The VM path
(`crates/shape-vm/src/executor/v2_handlers/typed_array_elem.rs:112`
`op_get_elem_i64`, and `crates/shape-vm/src/executor/dispatch.rs:1080` for the
generic `Index` opcode) raises `VMError::IndexOutOfBounds`. The two tiers
disagree by construction.

`v2_array_set` (`v2_array.rs:930`) has the matching defect: OOB index silently
skips the store (`brif` falls through to `continue_block`).

### §1.3 Exact JIT condition under which the bounds check is elided

The divergence is **conditional** on the JIT routing the index through
`v2_array_get` rather than `inline_array_get`. The dispatch is at
`crates/shape-jit/src/mir_compiler/places.rs:989-997` (`Place::Index` arm):

```
places.rs:992   if let Some(elem_kind) = self.v2_typed_array_elem_kind(base) {
places.rs:996       let elem_val = self.v2_array_get(arr_ptr, idx_i32, elem_kind);
```

`v2_array_get` is selected **iff the base local holds a v2 typed-array pointer**
— i.e. the bytecode compiler recorded an `Array<scalar>` `ConcreteType` for the
slot (top-level `let xs = [1,2,3]` does this). When the slot is NOT a recorded
typed array (the non-annotated NaN-boxed legacy path), `places.rs:1016`
`inline_array_get` is used instead; that path emits a checked OOB branch
(`places.rs:594` `inline_array_get` vs the bounds-elided
`inline_array_get_unchecked` at `places.rs:655`, gated by the `bounds_elision`
plan). The JIT therefore elides the bounds-check trap **for exactly the v2
typed-array fast path** — which the F1 reproducer hits.

The defect is also baked into JIT tests: `crates/shape-jit/src/mir_compiler/
v2_array_tests.rs:182` `v2_array_f64_out_of_bounds_returns_zero` and `:196`
`v2_array_i64_out_of_bounds_returns_zero` **assert** OOB returns zero, with a
comment claiming "The legacy path returns 0 as well, so both paths behave
identically in user space" — which is false against the VM (`dispatch.rs:1080`
raises). These two tests are wrong-behaviour-locking-in tests; the fix-dispatch
must update or delete them.

### §1.4 Note on the mission's stated F1 conditional

The WS-3 mission states "OOB inside a Result-returning function errors VM==JIT
— the JIT gap is CONDITIONAL". This is **NOT what HEAD `3f227c63` does**.
Re-verified:

- `let y = xs[10]` inside ANY function body (Result-returning or plain `-> int`)
  returns `{ "Bool": false }` in BOTH vm and jit (`/tmp/ws3/f1c.shape`,
  `f1d.shape`). Even the **in-bounds** `xs[1]` inside a function body returns
  `{ "Bool": false }` (`/tmp/ws3/f1e.shape`) — array indexing inside a function
  body is broken outright, both tiers, in-bounds and OOB alike. The verifier
  emits `LoadLocalTrusted ... slot 0 has Unknown kind`.

That function-body breakage is a **kind-tracking defect in the array-index
emit/dispatch path, NOT a Result/AnyError defect** — it is array-territory
(WS-1 / array-index). It is recorded here only to correct the mission's stated
F1 conditional. The genuine F1 finding is the **top-level** typed-array JIT
bounds-elision divergence pinned in §1.2/§1.3.

### §1.5 F1 fix plan

1. In `v2_array_get` (`v2_array.rs:838`): replace the `oob_block` →
   `emit_default` jump with a real OOB raise. The JIT already has a runtime-
   error escape path; the OOB block must call into it (same surface the VM
   `IndexOutOfBounds` produces) rather than fabricating a zero. `v2_array_set`
   (`v2_array.rs:930`) gets the matching change (OOB store must raise, not
   silently skip).
2. Update/delete the two wrong-behaviour tests `v2_array_tests.rs:182` and
   `:196` so they assert the OOB raise, not OOB-returns-zero.
3. The function-body array-index breakage (§1.4) is OUT OF WS-3 SCOPE — refer
   to the array-index workstream.

## §2 — F2 · the `?` operator loses the unwrapped value's type

### §2.1 Reproduction (HEAD `3f227c63`)

`/tmp/ws3/f2.shape`:
```
fn p(s: string) -> Result<int, string> { Ok(42) }
fn main() -> Result<int, string> { let v = p("x")?; let w = v + 1; print(w); Ok(0) }
```
Compile error (tier-independent — surfaces in vm and jit):
```
Cannot infer types for binary operation `Add`: operand types are `unknown`
and `int`. Strict typing requires both operands to have a known concrete type
at compile time. Add a type annotation to disambiguate.
```

Err-propagation of `?` itself works; only the **type of the unwrapped Ok value**
is lost.

**Classification: v0.3-gating.** A spurious compile error rejecting a valid
program (`?` followed by typed use of the unwrapped value). The user did
nothing wrong; the compiler cannot prove a type it should be able to prove.

### §2.2 Pinned source site — the lost type

The runtime type-inference engine handles `Expr::TryOperator` **correctly**:
`crates/shape-runtime/src/type_system/inference/expressions.rs:871` calls
`try_unwrap_inner_type` and returns the unwrapped `int`. The defect is in the
**bytecode compiler's** parallel type tracker.

`crates/shape-vm/src/compiler/expressions/advanced.rs:32`
`compile_expr_try_operator`:
```
self.compile_expr(inner)?;
self.emit(Instruction::simple(OpCode::TryUnwrap));
Ok(())
```
After emitting `TryUnwrap` it does **not** set `last_expr_type_info` /
`last_expr_numeric_type` / `last_expr_schema` to the unwrapped inner type. So
when `let v = p("x")?` records the local slot's type via
`propagate_initializer_type_to_slot`, there is no type info to propagate — slot
`v` is recorded with no `type_name`.

Downstream, `v + 1` reaches `strict_typing_binop_error`
(`crates/shape-vm/src/compiler/expressions/binary_ops.rs:160`). It calls
`infer_expr_type(left)` for the bare `Identifier("v")`. At
`crates/shape-vm/src/compiler/expressions/mod.rs:1352` the identifier path
queries `tracker_type_name_for_identifier` — which returns `None` (no
`type_name` recorded) — then falls through to
`mod.rs:1533 self.type_inference.infer_expr(expr)`. The runtime engine ran on
the original program AST and does not see the function-body `let v` binding,
so it returns `unknown`. The binop fails strict typing.

**Pinned defect: `compile_expr_try_operator` at `advanced.rs:32` does not stamp
the compile-time tracker with the `?`-unwrapped inner type.**

Confirmation: `let v: int = p("x")?` (explicit annotation, `/tmp/ws3/f2b.shape`)
compiles cleanly — the annotation seeds the slot's `type_name` directly,
bypassing the missing propagation.

### §2.3 F2 — second defect: SIGSEGV on the `?` runtime path

Once the F2 compile error is worked around with `let v: int`, the `?` operator
produces the **correct runtime value** but the program then crashes:

| reproducer | output | ec |
|---|---|---|
| `/tmp/ws3/r3x.shape` — `let v: int = p()?; print(v)` | `42` then SIGSEGV | 139 |
| `/tmp/ws3/c2.shape` — `print(p()?)` inline, no binding | `42` then SIGSEGV | 139 |
| `/tmp/ws3/c3.shape` — `?` on `Err("e")` (propagation) | SIGSEGV | 139 |
| `/tmp/ws3/c1.shape` — Result bound, NOT unwrapped | clean | 0 |
| `/tmp/ws3/r5x.shape` — `match` on Result (no `?`) | `42`, clean | 0 |

The crash is isolated to the `TryUnwrap` opcode path
(`crates/shape-vm/src/executor/exceptions/mod.rs:662` `op_try_unwrap`). Both the
Ok-unwrap leg and the Err-propagate leg crash; a Result that is never `?`-ed,
and the `match`-discriminated path, are clean. The likely fault is a
strong-count double-claim in `op_try_unwrap`'s share-accounting: the Ok leg does
`rd.payload.clone()` then `drop(value)`; the Err leg does
`std::mem::forget(value)` then `return_value_inner(result_bits, result_kind)`.
The `read_result` borrow (`exceptions/mod.rs:914`) returns `&ResultData`
borrowed through the live carrier; `rd.payload.clone()` bumps the inner share,
then `drop(value)` retires the wrapper which transitively retires the inner —
the net accounting must be verified against `ResultData`'s `Clone`/`Drop`
(`crates/shape-value/src/heap_value.rs:2231`).

**Classification: v0.3-gating** (memory-unsafety / SIGSEGV).

### §2.4 F2 fix plan

1. **Type loss (compile):** in `compile_expr_try_operator` (`advanced.rs:32`),
   after `compile_expr(inner)`, query the inner expression's type, unwrap the
   Result/Option wrapper to the success type, and stamp `last_expr_type_info` /
   `last_expr_numeric_type` / `last_expr_schema` so the `let`-binding's
   `propagate_initializer_type_to_slot` records the unwrapped type on slot `v`.
   The unwrap logic already exists in the runtime engine
   (`try_unwrap_inner_type`, `expressions.rs:877`) — mirror it for the tracker.
2. **SIGSEGV (runtime):** audit `op_try_unwrap`'s share-accounting against the
   `read_result` borrow lifetime + `ResultData::Clone`/`Drop`. The Ok leg's
   `rd.payload.clone(); drop(value)` and the Err leg's
   `mem::forget(value); return_value_inner(...)` must each balance exactly one
   strong-count share. Surface to the user if a genuine ABI gap is found — do
   NOT paper over it with a fallback.

## §3 — F3 · the `!!` error-context operator does not type-check

### §3.1 Reproduction (HEAD `3f227c63`)

`/tmp/ws3/f3.shape`:
```
fn boom() -> Result<int, string> { Err("bad") }
fn main() -> Result<int, string> { let v = boom() !! "ctx"; print(v); Ok(0) }
```
Compile error (tier-independent):
```
Cannot infer types for binary operation `ErrorContext`: operand types are
`Result<int, string>` and `string`. Strict typing requires both operands to
have a known concrete type at compile time.
```
`let v: int = boom() !! "ctx"` (annotated, `/tmp/ws3/f3y.shape`) **also fails**
to compile — the rejection is the `ErrorContext` binop dispatch itself, not the
binding's type.

**Classification: v0.3-gating.** `!!` is a documented core operator (CLAUDE.md
"Language Features" + "Forbidden Patterns" reference `!!` error-context). A core
operator that cannot be compiled at all rejects every valid program using it.

### §3.2 Pinned source site

`crates/shape-vm/src/compiler/expressions/binary_ops.rs:853`
`compile_expr_binary_op` has dedicated arms for `And`, `Or`, `NullCoalesce`,
`Pipe`, `Add`, and a generic `_ =>` arithmetic/comparison arm at
`binary_ops.rs:1527`. **There is no `BinaryOp::ErrorContext` arm.** `ErrorContext`
falls into the `_ =>` arm, which runs the strict-arithmetic operand-type gate;
that gate rejects `Result<int, string>` because it is not a numeric type, and
emits `strict_typing_binop_error` (`binary_ops.rs:160`).

The opcode itself exists: `crates/shape-vm/src/compiler/literals.rs:93` maps
`BinaryOp::ErrorContext => OpCode::ErrorContext`, and the executor handler
`op_error_context` is implemented (`crates/shape-vm/src/executor/exceptions/
mod.rs:566`). The runtime inference engine also handles it correctly:
`crates/shape-runtime/src/type_system/inference/operators.rs:444` returns
`Result<T>`. The ONLY missing piece is the **bytecode-compiler dispatch arm** —
`ErrorContext` never gets to `op_emit_binary_op`/`literals.rs:93` because the
`_ =>` arm rejects it first.

**Pinned defect: `compile_expr_binary_op` (`binary_ops.rs:853`) has no
`BinaryOp::ErrorContext` arm; the operator falls into the strict-arithmetic
`_ =>` arm and is rejected before reaching its opcode emission.**

### §3.3 F3 fix plan

Add a dedicated `BinaryOp::ErrorContext` arm to `compile_expr_binary_op`
(`binary_ops.rs:853`), sibling of the `NullCoalesce` arm. The arm:
- compiles `left` then `right` (`!!` is left-then-right: value, then context),
- emits `OpCode::ErrorContext` (the existing `op_error_context` handler
  consumes `[value, context]`),
- sets `last_expr_*` so the result types as `Result<T>` per the runtime
  engine's `operators.rs:444` rule, so downstream uses of the binding resolve.

This is a self-contained ~1-arm fix; no opcode or handler work needed (both
already exist). After the arm lands, the F4 caveat in §4.4 applies (the
`!!`-on-Err leg of `op_error_context` calls `handle_exception`, which can reach
the §4 uncaught-exception path when there is no enclosing try-block).

## §4 — F4 · the uncaught-exception path dumps internal jargon

### §4.1 What the F4 stub actually is (correcting the mission's framing)

The WS-3 mission states "the AnyError-TypedObject builder is STUBBED". At HEAD
`3f227c63` this is **no longer accurate**: `build_any_error`
(`crates/shape-vm/src/executor/exceptions/mod.rs:440`) is fully implemented
(W14-variant-codegen close) — it constructs a real `Arc<TypedObjectStorage>`
matching the AnyError 6-field schema. `op_throw` (`mod.rs:371`),
`normalize_err_payload` (`mod.rs:517`), the trace-info builders, and the
`Ok`/`Err`/`Some` constructors (`crates/shape-vm/src/executor/vm_impl/
builtins.rs:537-593`) are all implemented.

**The genuine F4 jargon-dump is the uncaught-exception path**, not the builder.
The internal-jargon string `PHASE_2C_EXCEPTION_OBJECT_SURFACE`
(`exceptions/mod.rs:112`) has **exactly one live use site**:
`exceptions/mod.rs:245-248`, the no-handler branch of `handle_exception`:

```
} else {
    // No handler — propagate as a runtime error.
    let kind = payload.kind();
    drop(payload);
    Err(VMError::RuntimeError(format!(
        "Uncaught exception (kind {:?}): {}",
        kind, PHASE_2C_EXCEPTION_OBJECT_SURFACE
    )))
}
```

The literal that reaches the user (verified, `/tmp/ws3/f4a.shape`):
```
Error: Runtime error: Uncaught exception (kind Ptr(TypedObject)): phase-2c —
exception object machinery (AnyError TypedObject build, trace-frame build,
cause-chain format) pending re-emission on the kinded Arc<TypedObjectStorage>
model. Depends on D-raw-helpers cleanup of heap-decode primitives and
cross-cluster cascade in dispatch.rs / control_flow/mod.rs /
builtins/type_ops.rs migrating ValueWord-typed arguments to (u64, NativeKind).
See ADR-006 §2.7.4 / playbook §10 E-exceptions row. (line 3)
```

This is internal jargon (ADR section numbers, cluster names, deleted-symbol
references) presented as a **user-facing error**. Per the §0 binding, an
internal-jargon stub is NOT "clean" → **v0.3-gating**.

### §4.2 Why it is stubbed / what a real handler needs

The `handle_exception` no-handler branch is the "an exception unwound past
every `try` block" terminus. Today it has nothing structured to say: the
intended behaviour (per the docstring) is to format the AnyError cause chain —
walk `payload`'s AnyError TypedObject `cause`/`message`/`trace_info` fields,
render a backtrace, and surface a clean uncaught-exception report. That
cause-chain formatter + frame-walk is the "Phase-2c surface" the literal names.

A real handler does NOT need the full frame-walk to be clean. The minimal
correct behaviour: read the AnyError TypedObject's `message` field (the
`build_any_error`/`normalize_err_payload` path always populates it — verified:
`print(Ok(42))` round-trips a TypedObject through `op_get_prop`) and surface
`Uncaught error: <message>`. The `trace_info` field is empty today
(`trace_info_full`/`trace_info_single` return empty-string slots,
`mod.rs:397-403`); a clean message simply omits the trace until the frame-walk
lands. No fabricated dispatch, no jargon.

### §4.3 F4 user-reachability map — every user-program shape that reaches the stub

`handle_exception`'s no-handler branch is reached when an exception unwinds with
`self.exception_handlers` empty. The exception sources:

| # | Source | Compiler emit site | Reach condition |
|---|---|---|---|
| R1 | Non-exhaustive `match` **expression** | `crates/shape-vm/src/compiler/expressions/advanced.rs:152` (`OpCode::Throw` after the "No match arm matched the value" const) | a `match` expression at runtime where no arm matches and there is no enclosing `try` |
| R2 | `let`-binding `Typed` pattern failure | `crates/shape-vm/src/compiler/patterns/binding.rs:75` (`Throw`, "Pattern match failed") | `let <name>: <type> = <value>` where the runtime `TypeCheck` fails |
| R3 | `let`-binding `Literal` pattern failure | `binding.rs:123` (Bool literal), `binding.rs:148` (other literal) | `let <literal-pattern> = <value>` mismatch |
| R4 | `let`-binding `Array` pattern length failure | `binding.rs:175` (`Throw`, "Array pattern requires at least N elements") | `let [..] = <value>` with too few elements |
| R5 | `let`-binding `Constructor` pattern failure | `binding.rs:248` (`Throw`, "Pattern match failed") | `let Some(v) = <value>` / enum-variant pattern mismatch |
| R6 | Destructure type-check failure | `crates/shape-vm/src/compiler/patterns/helpers.rs:149` (`Throw`, "Cannot destructure non-array value as array" / "non-object value as object") via `emit_destructure_type_check` (`helpers.rs:124`) | ANY `let`-destructure whose runtime `TypeCheck` returns false — **see §5** |
| R7 | `!!` operator on `Err` / `None` with no enclosing `try` | `exceptions/mod.rs:597,610,617` (`op_error_context` calls `handle_exception` directly) | `<Err-value> !! "ctx"` outside a `try` block |
| R8 | `op_throw` (`OpCode::Throw`) generally | `crates/shape-vm/src/executor/exceptions/mod.rs:371` | any `Throw` opcode reaching `handle_exception` with no handler |

Shape has **no `throw` keyword** (correct — Shape uses Result, not exceptions);
`OpCode::Throw` is purely a compiler-internal mechanism for pattern-match
failures (R1-R6) and the `!!` runtime assertion (R7). Note: the runtime-error →
exception conversion at `dispatch.rs:246` only routes into `handle_exception`
**when a handler exists** (`!self.exception_handlers.is_empty()`); a plain
runtime error with no handler returns via `enrich_error_with_location`
(`dispatch.rs:267`) and does NOT hit the F4 jargon. So the F4 stub is reached
**only via the `OpCode::Throw` family above**, not via ordinary runtime errors.

Verified live: R1 (`/tmp/ws3/f4a.shape`, non-matching `match`) and R6
(`/tmp/ws3/rest3.shape`, plain array-destructure) both surface the jargon
verbatim, in BOTH `--mode vm` and `--mode jit` (`Throw` is interpreter-side; JIT
falls back to the interpreter for these).

**WS-4 overlap (recorded explicitly):** R6 includes the VM-mode object-destructure
`let {…} = obj` path. Per the WS-3 mission, the object-destructure pattern path
is **WS-4 territory** — a parallel WS-4 audit owns it. WS-3 owns the F4 stub
**characterization itself** (this §4) and the array-rest sub-item (§5). The
clean territory split: **WS-3 owns the §4.4 fix to the `handle_exception`
no-handler message** (the single jargon site, shared by every reach path) and
the §5 array-rest clean-error spec; **WS-4 owns the object-destructure pattern
path** (the `DestructurePattern::Object` arm and its `TypeCheck`-against-"object"
failure). The §4.4 message fix is the shared terminus and benefits every reach
path R1-R8 at once.

### §4.4 F4 fix plan

In `handle_exception`'s no-handler branch (`exceptions/mod.rs:243-248`): replace
the `PHASE_2C_EXCEPTION_OBJECT_SURFACE` interpolation with a clean
user-facing message. The minimal correct form:
- when `payload` is an AnyError TypedObject (the normal case post
  `normalize_err_payload`): read its `message` field via the existing
  `TypedObjectStorage` field access and surface `Uncaught error: <message>`;
- otherwise: surface `Uncaught error: <stringified payload>`.

This replaces the internal jargon with a clean message for ALL of R1-R8 in one
edit. The `trace_info` frame-walk remains a genuine v0.4 follow-up (the
`trace_info_*` builders return empty strings today, `mod.rs:397-403`) — a clean
message simply omits the trace; that is v0.4-OK incompleteness, not a v0.3
blocker. The jargon literal `PHASE_2C_EXCEPTION_OBJECT_SURFACE`
(`exceptions/mod.rs:112`) becomes dead and should be deleted with the fix.

`PHASE_2C_VARIANT_CODEGEN_SURFACE` (`exceptions/mod.rs:175`) is already
`#[allow(dead_code)]` — the 8 variant-discriminator opcodes it documented were
filled by W14-variant-codegen. The fix-dispatch should delete it too (dead
jargon literal).

## §5 — Array rest-pattern `[a, ...rest]` — clean-error fix spec

### §5.1 Scope (user 2026-05-21)

`[a, ...rest]` array rest-pattern destructuring is **v0.4-OUT-OF-SCOPE** as a
feature. But at HEAD it does NOT error cleanly — it dumps the F4 jargon. The
WS-3 deliverable is to spec the SMALL clean-error fix.

### §5.2 Reproduction (HEAD `3f227c63`)

`/tmp/ws3/rest1.shape`:
```
fn run() {
  let xs = [1,2,3,4]
  let [a, ...rest] = xs
  print(a)
}
run()
```
→ ec=1, the full F4 jargon-dump (`Uncaught exception (kind Ptr(TypedObject)):
phase-2c — exception object machinery ...`). Same for the top-level form
`/tmp/ws3/rest2.shape`.

**Classification: v0.3-gating** (internal-jargon stub per §0).

### §5.3 Root cause — and the broader array-destructure breakage

`DestructurePattern::Array` is compiled at
`crates/shape-vm/src/compiler/patterns/destructure.rs:146`, and the `Rest`
sub-pattern **is** handled (`destructure.rs:159-176`, emits `SliceAccess`). The
rest pattern is not unimplemented at the compiler level.

The jargon-dump comes one step earlier. `destructure.rs:152`
`emit_destructure_type_check(value_local, "array", "Cannot destructure
non-array value as array")` emits `OpCode::TypeCheck` against
`TypeAnnotation::Basic("array")` (`patterns/helpers.rs:124-140`). The
`op_type_check` matcher `type_check_kinded` (`exceptions/mod.rs:988`) handles
`TypeAnnotation::Basic` only for `"int" | "number" | "float" | "bool" |
"string" | "char"` — **the bare name `"array"` is not in the list**, so it hits
`_ => false`. `TypeCheck` returns `false`, the `JumpIfTrue` does not jump, and
`Throw` fires → F4 jargon.

Array types are normally `TypeAnnotation::Generic { name: "Array", .. }`, which
`type_check_kinded` DOES handle (`exceptions/mod.rs:1025`). The destructure path
passes the **bare `"array"` string**, which no arm matches.

**This breaks plain array-destructure too**, not just rest: `/tmp/ws3/rest3.shape`
`let [a,b,c] = xs` (no rest) dumps the identical F4 jargon. The defect is the
`"array"` (and `"object"`) bare-name gap in `type_check_kinded`, shared by every
`emit_destructure_type_check` caller.

### §5.4 Array-rest clean-error fix spec

The user ruling: array rest-pattern is v0.4-out-of-scope and should produce a
**plain "array rest-pattern not supported" message — NOT the F4 jargon**.

Spec:
1. In the `DestructurePattern::Array` arm (`destructure.rs:146`), when a
   `DestructurePattern::Rest` sub-pattern is present (`destructure.rs:159`),
   emit a **compile-time** `ShapeError::SemanticError` with the message
   `array rest-pattern (\`[a, ...rest]\`) is not supported` and the pattern's
   span — instead of compiling the `SliceAccess` rest path. A compile-time
   error is clean, surfaces at the right line, and never reaches `handle_exception`.
2. This fix folds into the WS-3 fix-dispatch as a small dedicated sub-item.

**Note for the fix-dispatch — adjacent v0.3-gating defect, same family:** the
`"array"` / `"object"` bare-name gap in `type_check_kinded` (§5.3) breaks
**non-rest** array-destructure `let [a,b,c] = xs` outright. That is not the
array-rest sub-item, but it is the same root-cause function and is v0.3-gating
(jargon-dump on a valid program). The non-rest array-destructure fix is to add
`"array"` (matching `NativeKind::Ptr(HeapKind::TypedArray)`) — and `"object"`
(`HeapKind::TypedObject`) — to the `TypeAnnotation::Basic` arm of
`type_check_kinded` (`exceptions/mod.rs:994`). The non-rest **array** half is
WS-3-adjacent; the **object** half overlaps WS-4 (see §4.3). The fix-dispatch
should land the `"array"` Basic-name arm under WS-3 and coordinate the
`"object"` arm with WS-4 (it is one match-arm; whichever workstream lands
`type_check_kinded` should land both names together to avoid a split edit).

## §8 — Forbidden-pattern discipline

This audit introduces no source changes. The fix plans above introduce no
dynamic-dispatch path, no `ValueWord`, no generic opcode, no
`Convert<X>To<Y>` opcode, no `SlotKind::Dynamic`, and no feature flag. Every fix
extends an existing typed path:
- F1 routes the JIT OOB block into the existing runtime-error escape (the same
  surface the VM `IndexOutOfBounds` already produces) — not a new opcode.
- F2a mirrors the existing `try_unwrap_inner_type` logic onto the compile-time
  tracker — not a new inference mode.
- F2b is a refcount-accounting correction within the existing `KindedSlot` /
  `ResultData` carrier — not a new carrier.
- F3 adds a dispatch arm routing to the already-existing `OpCode::ErrorContext`
  + `op_error_context` handler — not a new opcode.
- F4 reads the already-built AnyError TypedObject `message` field — not a new
  builder.
- Array-rest and the `type_check_kinded` arm emit a clean error / extend an
  existing match — no fabricated runtime contract.

No "bridge / probe / helper / hop / translator / adapter / shim" descriptor is
used for any deleted-dispatch role. The deleted `ValueWord` / `raw_helpers` /
`tag_bits` machinery is referred to by name where it appears in HEAD docstrings
(`exceptions/mod.rs:112` jargon literal) and by deletion-fate elsewhere.
