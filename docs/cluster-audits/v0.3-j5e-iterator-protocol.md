## §3 Iterator-protocol design scope estimate

**Scope: Separate from J.5a–c; candidate for v0.3 OR v0.4 deferral depending on supervisor decision (see §4).**

### §3.1 Per-element-kind source reconstruction (ckpt-4 blocker resolution)

**Effort:** ~16–20 hours (per upstream cascade close in ckpt-2/3)

- **`IteratorSource` enum migration:** Add per-element-kind `Array<T>` variants (f64, i64, i32, u8, StringV2, DecimalV2, TypedObject, BigInt, etc.). One-to-one mapping with `TypedArray<T>` monomorphizations from W12 deletion scope (~22 variants eventually; v0.3 likely starts with scalar 4–8).
  - **Implementation:** New enum arms; `len()` method dispatch per arm (read flat-struct `len` field); source-element-fetch helper per arm (read via `TypedArray<T>::get`).
  - **Testing:** Unit test per variant (allocate source, wrap in IteratorState, verify len/fetch).

- **`IteratorState` constructor (shape-value iterator_state.rs):** Already exists; re-instate once `IteratorSource::Array<T>` variants land. No design change needed.

- **Integration with receiver-decode path (iterator_methods.rs `handle_array_iter`):** Receiver-type check → construct appropriate `IteratorSource::Array<T>` variant → wrap in `IteratorState` → return as `KindedSlot { kind: Ptr(Iterator), .. }`.

### §3.2 Pipeline executor kernel (ckpt-6 core)

**Effort:** ~24–32 hours (significant implementation; shared loop structure)

- **Pipeline materialization loop (new `iterator_state.rs` or `executor/iterator_kernel.rs`):**
  - **Core shape:** `fn materialize_iterator(vm, state: Arc<IteratorState>) -> Result<(Vec<u64>, NativeKind), VMError>`
  - **Algorithm:** Initialize source cursor; for each source element:
    1. Fetch element (kind-generic dispatch per source-variant)
    2. Apply each stage in `state.stages` in order:
       - `.map(closure)`: call closure, capture return-kind (error if kind mismatch across elements — see §5)
       - `.filter(predicate)`: call closure, skip if `false`
       - `.take(n)` / `.skip(n)` / `.enumerate()`: pure transforms (no closure)
       - `.flatMap(closure)`: call closure (expect `Iterator<T'>` result), consume inner iterator, append all elements
       - `.chain(other_iter)`: after self fully consumed, materialize other iterator recursively
    3. Accumulate into result buffer with per-element kind-dispatch
  - **Result-kind threading:** Depends on terminal operation (see §3.3). For `.collect`, result kind is "element kind after all transforms".

- **Kind-mismatch error handling:** J.5b-style design question at iterator level. Recommend: if any `.map` closure returns a different kind than the first, return structured `VMError::RuntimeError("Iterator.map: inconsistent element kind across iterations")` — surface-and-stop at materialization time, not silently coerce or materialize heterogeneous.

- **Terminal operations (6 method implementations):**
  - `.collect()`: materialize pipeline; wrap result in `Array<element-kind>` HeapValue; return `KindedSlot`.
  - `.forEach(closure)`: materialize pipeline; for-each call closure; return unit.
  - `.reduce(reducer, initial)`: materialize pipeline; fold with reducer closure; return accumulated value.
  - `.count()`: materialize pipeline; return length as `i64`.
  - `.any(predicate)` / `.all(predicate)`: materialize pipeline; fold with short-circuit; return `bool`.
  - `.find(predicate)`: materialize pipeline; find first match; return `Option<T>` or `T?`.

### §3.3 Closure-callback ABI threading

**Effort:** ~4–6 hours (mostly integration; ABI design frozen per ADR-006 §2.7.11/Q12)

- **Closure-call pattern (identical to J.5b HOF builders):** `vm.call_value_immediate_nb(closure_kinded_slot, arg_kinded_slot) -> Result<KindedSlot, VMError>`
  - Closure is stored in `IteratorTransform::Map/Filter/FlatMap(Arc<HeapValue>)` (per iterator_state.rs lines 128, 132, 142).
  - At materialization time, recover as `KindedSlot` via `Arc::as_raw` → `Arc::from_raw` (share bump in `clone_with_kind`).
  - Call closure with element as arg; unpack result `KindedSlot` (bits + kind).
  - For `.map` / `.filter` / predicate operations, validate result kind (expect `Bool` for predicates; for `.map`, result kind determines output array kind).

- **No new ABI design needed.** Reuse existing Q12 machinery.

### §3.4 Total effort estimate (iterator-protocol core, v0.3 scope)

- Source reconstruction (ckpt-4 resolve): ~16–20h
- Pipeline kernel + terminals: ~24–32h
- Closure integration: ~4–6h
- Testing (unit + integration): ~8–12h
- **Subtotal: ~52–70 hours (conservative estimate for full v0.3 iterator protocol)**

**Note:** Effort assumes J.5a/J.5b design decisions finalized (KIND-mismatch error semantics, closure-return-kind threading). If deferred to v0.4, effort zero for v0.3.

## §4 Design decisions blocking iterator-protocol v0.3 vs v0.4 boundary

**User/supervisor decision required (non-blocking audit surface):**

1. **Iterator-protocol scope for v0.3:** Should iterator factories + lazy transforms + eager terminals land in v0.3, or defer to v0.4?
   - **Option A (v0.3):** Implement full 19-site protocol (~52–70h effort). Lands post-J.5a/J.5b/J.5c closure design decisions + ckpt-2/3/4 cascade closes.
   - **Option B (v0.4):** Surface-and-stop all 19 sites as documented deferral. Unblocks J.5a–c (array primitives, not iterator-dependent). Allows focused v0.3 window on array-layer operations.

2. **Iterator kind-rejection semantics** (coupled with J.5b HOF builder design):
   - **Scenario:** `.map(|x| x * 2)` on `Iterator<i64>` where closure returns `i64` for first 3 elements, then `Bool` (type-narrowing edge case).
   - **Option (i):** Structured error on first mismatch (recommended; aligns with J.5b typed-slot discipline).
   - **Option (ii):** Coerce (forbidden per CLAUDE.md §Type System Rules).
   - **Option (iii):** Materialize as heterogeneous `Array<Any>` (requires v0.3 design extension; costly).

3. **`.chain()` enum variant presence:** Current `IteratorTransform` enum is incomplete (line 150 in iterator_state.rs names Chain but struct definition cuts off). Is `Chain` a v0.3 or v0.4 feature?
   - **Recommend:** v0.4 deferral (lower-frequency operation; orthogonal to map/filter/take/skip core).

## §6 Conclusion

All 19 iterator-protocol methods are classified as **(d) new iterator-protocol territory**, distinct from J.5a–c primitives-layer operations. Iterator-level lazy evaluation and transform composition require a separate executor kernel + source-variant reconstruction, not array-primitive reuse.

**Key architectural insight:** Iterator protocol and array primitives are orthogonal design tracks:
- **J.5a–c:** Array-to-array eager transformations (reverse, concat, slice, filter-to-array, equality checks).
- **J.5e:** Iterator-to-iterator lazy transformations + eager terminals (map/filter/take/skip chaining; materialize-on-demand).

Both eventually depend on common closure-callback ABI (ADR-006 §2.7.11/Q12) and per-element-kind dispatch, but at different semantic levels.

**Recommendation:** Proceed with J.5a–c implementation independently. Schedule J.5e protocol design + implementation as a follow-up scope decision (§4) — v0.3 aggressive scope (full 52–70h protocol core) OR v0.4 deferral (zero v0.3 effort; all sites remain documented SURFACE).
