## §2 Root cause — the bool `.len()` (and `last/slice/reverse/...`) VM/JIT divergence

### §2.1 The method-dispatch registry topology

VM method dispatch flows: `op_call_method`
(`crates/shape-vm/src/executor/objects/mod.rs:381`) →
`dispatch_method_kinded` (`:513`) → `resolve_method_handler` (`:670`).
For a `NativeKind::Ptr(HeapKind::TypedArray)` receiver, the resolver
(`mod.rs:737`) detects the element type via
`as_v2_typed_array` and calls `typed_array_method_registry`
(`mod.rs:202-237`):

```
V2ElemType::I64 | I32 | I8 | U8 | I16 | U16 | U32 => TYPED_INT_ARRAY_METHODS
V2ElemType::F64 | F32                            => TYPED_NUMBER_ARRAY_METHODS
V2ElemType::Bool                                 => BOOL_ARRAY_METHODS
V2ElemType::Char | String | Decimal | TypedObject => None  (→ ARRAY_METHODS)
```

The three relevant PHF registries
(`crates/shape-vm/src/executor/objects/method_registry.rs`):

- **`TYPED_INT_ARRAY_METHODS`** (`:755`) — `len`/`length`/`first`/`last`/
  `get`/`set`/`push`/`pop`/`sum`/… → REAL handlers in
  `typed_int_array_methods.rs` (e.g. `len` at `typed_int_array_methods.rs:112`
  returns `KindedSlot::from_int(view.len)`).
- **`TYPED_NUMBER_ARRAY_METHODS`** (`:782`) — mirror for `f64`, REAL
  handlers in `typed_number_array_methods.rs`.
- **`BOOL_ARRAY_METHODS`** (`:798`) — `len`/`length` → **`typed_array_methods::v2_len`**;
  `count`/`any`/`all` → `v2_bool_*`; `toArray` → `handle_bool_to_array`.
  NO `first`/`last`/`slice`/`reverse`/`pop`/`indexOf` entries.

`typed_array_methods::v2_len` (`typed_array_methods.rs:134-140`) is a
**ckpt-3 surface-and-stop stub** — its whole body is
`Err(ckpt3_surface("len", args))`. There is NO `typed_bool_array_methods`
module; `typed_int_array_methods.rs` and `typed_number_array_methods.rs`
exist, the bool sibling does not.

### §2.2 The exact VM-side SURFACE sites

The bool `.len()` divergence is pinned to TWO sites:

1. **`crates/shape-vm/src/executor/objects/method_registry.rs:799-800`** —
   `BOOL_ARRAY_METHODS` maps `"len"`/`"length"` to
   `crate::executor::objects::typed_array_methods::v2_len`, a SURFACE
   stub, instead of a real handler analogous to
   `typed_int_array_methods::len`.

2. **`crates/shape-vm/src/executor/objects/typed_array_methods.rs:134-140`** —
   `pub fn v2_len(...) { Err(ckpt3_surface("len", args)) }`. The
   `ckpt3_surface` builder is at `typed_array_methods.rs:79`.

For `bool.last()` / `.slice()` / `.reverse()` the resolved handler is
`ARRAY_METHODS["last"|"slice"|"reverse"]` →
`array_basic.rs::handle_last_v2` (`:142`) / `array_transform.rs` /
`array_basic.rs::handle_reverse_v2` (`:151`) — all `ckpt5_surface`
stubs (`array_basic.rs:91`). [Empirically the `bool.last()` SURFACE
prints the `ckpt-3 len` message text rather than `Array.last`; the
exact resolution chain that re-routes `last` through `v2_len` was not
fully isolated and is left for the fix-dispatch — it does not change
the verdict: the cell SURFACEs jargon on the VM.]

### §2.3 Why the JIT runs them — `mir_compiler/v2_array.rs`

The JIT, when `--mode jit` JIT-compiles the toplevel, lowers v2-typed-
array methods natively in
`crates/shape-jit/src/mir_compiler/v2_array.rs`:

- `"length" | "len"` arm at `v2_array.rs:583`.
- `"first"` arm at `v2_array.rs:646` — explicit allowed-kind set
  `Int64|UInt64|Int32|UInt32|Int16|UInt16|Int8|UInt8|Float64|Float32|Bool`.
- `"last"` arm at `v2_array.rs:673` — SAME allowed-kind set, INCLUDING
  `NativeKind::Bool`.

These arms emit `v2_array_get` / `v2_array_len` IR directly (data+0 /
data+(len-1)*size loads) — no PHF dispatch, no FFI hop. `Bool` is in the
set; `String`/`Decimal`/`Char` are excluded → those `Ok(None)` and fall
through. The JIT v2 FFI allocators / accessors for bool
(`jit_v2_array_new_bool`, `jit_v2_array_get_bool`, `jit_v2_array_len_bool`
in `crates/shape-jit/src/ffi/v2/mod.rs`) back this.

**Net root cause of the bool divergence: the JIT has a complete native
v2-typed-array method codegen path that includes `NativeKind::Bool`; the
VM's parallel path is the PHF method registry, and the bool slot of that
registry (`BOOL_ARRAY_METHODS`) was left wired to ckpt-3/ckpt-5 SURFACE
stubs while the `int`/`number` slots got real handlers
(`typed_int_array_methods` / `typed_number_array_methods`). No bool
sibling module was ever built.** The W12 typed-array-data deletion
cascade broke the shared `Arc<TypedArrayData>` receiver-recovery; the
int/number consumers were rebuilt onto the v2-raw `TypedArray<T>`
carrier, the bool (and string) consumers were not.

### §2.4 Sub-finding — `bool.first()` works, `bool.last()` SURFACEs

`bool.first()` runs OK on inline literals AND `let`-bound locals, but
SURFACEs (`Array.first` ckpt-5) when the array comes from a function
return (`fn mk() -> Array<bool>`). `bool.last()` SURFACEs in every form.
The provenance-sensitivity means a typed compile-time emission path is
in play for `first` on a statically-tracked typed-array slot that is
absent for `last`. The exact compiler arm was not isolated (the
`try_compile_typed_slot_method` fast path at
`function_calls.rs:2975-3185` handles only `len`/`get`/`has`/`set`/`push`
— not `first`). This is a WORKS cell, not a SURFACE/DIVERGE cell, so it
does not block the audit; the fix-dispatch should treat `first`/`last`
uniformly when building the bool consumer set (§4 tier ii).

## §3 Classification of `.contains()` — a registration gap, NOT the cascade

`["a","b"].contains("a")`, `[true,false].contains(true)`, AND
`[1,2,3].contains(2)` ALL fail with `no method 'contains' on receiver
kind Ptr(TypedArray)` — on EVERY element kind, including `int` which is
otherwise fully working.

**Root cause:** `"contains"` is not a registered array method name in
ANY array PHF registry. `ARRAY_METHODS`
(`method_registry.rs:259-331`) — the 47-method generic registry — has
`includes` and `indexOf` but **no `contains` key**. `contains` is
registered only for `STRING_METHODS` (`method_registry.rs:928`,
`v2_string_contains`) and `RANGE_METHODS` (`:1040`, `range_contains`).
The array membership-test method in Shape is `includes` (JS naming);
`contains` simply is not an array method.

**Verdict:** the `.contains()` failure is a **distinct registration
question, NOT part of the V3-S5 ckpt-N consumer cascade.** It is not a
cascade SURFACE (no `ckpt[2-5]_surface` text, no `TypedArrayData`
narrative). The error `no method 'contains' on receiver kind
Ptr(TypedArray)` is itself comparatively clean (it is the standard
unknown-method diagnostic). Two dispositions for the fix-dispatch /
supervisor:

- (a) `contains` is correct-by-design absent — arrays use `includes`;
  `contains` failing cleanly is acceptable. v0.4-OK (clean error).
- (b) Add `"contains"` as an alias key for `includes` in `ARRAY_METHODS`
  + the typed registries (one-line-per-registry PHF addition). Small.

The `no method` diagnostic could be made friendlier ("arrays use
`.includes()`; `.contains()` is for strings/ranges") but that is cosmetic
polish, not v0.3-gating. **Registration site for the fix:**
`crates/shape-vm/src/executor/objects/method_registry.rs` —
`ARRAY_METHODS` (`:259`), and if typed-registry coverage is wanted,
`TYPED_INT_ARRAY_METHODS` (`:755`) / `TYPED_NUMBER_ARRAY_METHODS`
(`:782`) / `BOOL_ARRAY_METHODS` (`:798`).

## §4 Proposed fix partition — three tiers

The (ii)-vs-(iii) line is the supervisor's call after this map; the
partition below is the recommendation, not an assumption.

### §4.i Tier (i) — binding-minimum: eliminate every divergence + de-jargon every SURFACE

**Goal:** every cell is either OK or a CLEAN user-facing error; ZERO
VM/JIT divergence; ZERO jargon-dump.

**Site list — the divergences (must close):**

| Divergent cell | Pin | Disposition |
|---|---|---|
| bool `.len()` | VM `BOOL_ARRAY_METHODS["len"]` → `v2_len` stub (`method_registry.rs:799`, `typed_array_methods.rs:134`) | rebuild bool `len` handler on v2-raw `TypedArray<u8>` (mirror `typed_int_array_methods::len:112`) |
| bool `.last()` | VM `ARRAY_METHODS["last"]` / `BOOL_ARRAY_METHODS` miss → ckpt SURFACE | add bool `last` handler |
| bool `.slice()` | VM ckpt-3 SURFACE | add bool `slice` handler |
| bool `.reverse()` | VM ckpt-3 SURFACE | add bool `reverse` handler |
| bool `.pop()` | VM Stack-overflow ≠ JIT `Array.pop` ckpt-5 | add bool `pop` handler; also fix the VM stack-overflow (separate VM defect surfaced by this cell) |
| bool `.indexOf()` | VM `no method 'len' on Bool` ≠ JIT `indexOf` ckpt-3 | add bool `indexOf` handler |
| decimal `arr[i]` / `for x in arr` | JIT reads `0.0` (silent wrong-answer) — JIT `mir_compiler/v2_array` decimal path + likely the broader JIT-decimal-scalar defect | confirm whether subsumed by the JIT-decimal-scalar fix; if not, dedicated arm |
| decimal `.len()` | VM ckpt-5 SURFACE ≠ JIT OK | rebuild decimal `len` handler |

**Site list — the jargon-dump → clean-error conversion (must de-jargon):**
every cell in §1 marked SURF-jargon. The producer sites are the
`ckpt[2-5]_surface` builders:

- `array_basic.rs:91` `ckpt5_surface` — feeds `Array.len/first/last/
  reverse/push/pop/zip/clone` (`:124-187`).
- `typed_array_methods.rs:79` `ckpt3_surface` — feeds `len` +
  `Vec<bool>.count/any/all` etc.
- `array_query.rs:65` `ckpt3_surface` — `forEach/includes/indexOf/find/…`.
- `array_transform.rs` / `array_sets.rs` / `array_sort.rs` /
  `array_aggregation.rs` / `concat.rs` / `iterator_methods.rs` /
  `property_access.rs` / `array_ops.rs` / `loops/mod.rs` ckpt builders
  (per W16 audit §1.B 14-file inventory).

Tier (i)'s de-jargon requirement: any SURFACE that is NOT going to be
implemented in tier (ii) must be replaced with a clean
`VMError::RuntimeError` carrying a one-line user-facing message (e.g.
"`Array<string>.sort()` is not yet supported"). The multi-paragraph
`TypedArrayData enum DELETED … REFUSED ON SIGHT` text is an
implementer-facing audit note that must NOT reach a user terminal.

**Two real bugs that tier (i) must also close (they are gating bugs,
not incomplete features):**

- `Array<string>` closures (`.find/.some/.every`, `.push`) →
  `TypeError: expected string, got string` — a `StringV2` vs `string`
  NativeKind confusion. The two strings ARE the same type; the error is
  a kind-tracker mismatch.
- `["a","b"].includes("x")` inline literal → returns WRONG `false`
  (a present element reports absent); `let`-bound form SURFACEs. The
  inline path produces a silent wrong-answer.

**Effort estimate (tier i):** medium. The 8 divergence rows are the bulk
— each needs a real bool/decimal handler (the `typed_int_array_methods`
shape is the template; ~1 small module + PHF rewiring). The de-jargon
sweep is mechanical (replace `ckptN_surface(...)` call-sites with a
clean-error builder where tier-ii is not landing the real impl) but
spans ~10 files. The 2 bugs are localized. Rough: **1 medium
sub-cluster** (bool+decimal handler rebuild) **+ 1 small sub-cluster**
(de-jargon sweep + the 2 bugs), or one combined wave.

### §4.ii Tier (ii) — basic-method consumer set for string + bool arrays

**Recommendation:** fully implement, for `Array<string>` AND
`Array<bool>`, the basic method set: `.len()`, indexing `arr[i]`
(already OK), `.first()`, `.last()`, `.contains()`-or-`.includes()`,
`for x in arr` (already OK). This is the set a user hits on day one.

**Site list:**

- New `typed_bool_array_methods.rs` module (mirror
  `typed_int_array_methods.rs`) — handlers `len/first/last/get/set/

### §4.iii Tier (iii) — genuine long-tail → v0.4 clean-error
