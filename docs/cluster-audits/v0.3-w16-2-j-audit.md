## §2 Per-territory analysis

### §2.A PHF registry collapse

**Mechanical shape:** Collapsing per-kind registries into generic `vec.shape` is mechanical:

1. Delete `TYPED_INT_ARRAY_METHODS` + `TYPED_NUMBER_ARRAY_METHODS` from `method_registry.rs`.
2. Delete the two per-kind handler files (`typed_int_array_methods.rs`, `typed_number_array_methods.rs`, 667 LoC total).
3. Wire dispatch to `vec.shape` generic implementations via the existing monomorphization self-call guard (already proven in W16.1).

**Invariants preserved:**
- ADR-006 §2.7.10: `MethodFnV2` ABI preserved (the signature never changes).
- ADR-006 §2.7.5: compile-time type proof (each monomorphized call is type-checked at compile time).
- Single-discriminator (ADR-005 §1): HeapValue dispatch via `as_heap_value()` for heap-element kinds.

**Atomic landing unit:** §2.A can land independently IF the compiler's monomorphization self-call guard already covers the `vec.shape` methods (empirically verified via W16.1 close — yes). So §2.A is independent of §2.B/§2.C/§2.D.

**Estimated scope:** Small (mechanical deletion + registry rewiring in dispatcher).

---

### §2.B ckpt cascade deletion

**Mechanical shape:** Each ckpt-N surface is a placeholder for a downstream handler. Deletion requires:

1. Implement the actual handler logic in the per-territory file (e.g., `typed_array_methods.rs` for query ops, `array_transform.rs` for map/filter).
2. Replace `Err(ckpt3_surface(...))` with the handler body.
3. No new ADR amendments (ckpt helpers are purely internal wiring).

**Invariants preserved:**
- ADR-006 §2.7.10: every replacing handler must follow the `MethodFnV2` ABI.
- ADR-006 §2.7.14: no Bool-default fallback for unknown element kinds (surface-and-stop only).

**Atomic landing unit:** §2.B is NOT independent of §2.A. The PHF registries must collapse first (or at least, the per-kind registry lookups must route to generic handlers) so that array construction reaches the downstream handlers that currently SURFACE.

§2.B itself can be partitioned by helper (ckpt2_surface zones, ckpt3_surface zones, etc.) into sub-clusters, but each sub-cluster requires §2.A to land first.

**Estimated scope:** Large (120 sites × handler implementation per-territory + potential kind-tracker extensions).

---

### §2.C Opcode arm macro-generation

**Mechanical shape:** Generate `NewTypedArray<kind>`, `GetTypedArray<kind>`, `PushTypedArray<kind>`, `SetTypedArray<kind>` via macro_rules! or build.rs.

**Two macro strategies:**

1. **macro_rules! (simpler, inlinable):** Define a macro that expands a template per-kind. Trade-off: macro code is harder to read in expansion.
2. **build.rs codegen (more explicit):** Pre-generate the match arms at build time. Trade-off: binary bloat + less type-checking at macro-expansion time.

**Invariants preserved:**
- ADR-006 §2.7.5: each arm stamps the element-type metadata at the producer site (no fabrication at runtime).
- Zero-tag runtime discipline (the kind is encoded in the opcode name, not decoded at runtime).

**Atomic landing unit:** §2.C is independent of §2.A (the opcode structure doesn't depend on the method registries). But §2.C DEPENDS on §1.C's completion — i.e., all 14 TypedArrayKind variants must be defined in `compiler/v2_typed_emission.rs` BEFORE we can macro-generate the arms that operate on them.

**Estimated scope:** Medium (define template + generate 56 arms + test coverage for each generated arm).

---

### §2.D JIT FFI macro-generation mirror

**Mechanical shape:** Mirror §2.C in the JIT layer. Generate `jit_v2_array_new_<kind>`, `jit_v2_array_get_<kind>`, `jit_v2_array_set_<kind>` per-kind.

**Coverage gap:** Currently only 4 kinds (f64, i64, i32, bool) have JIT FFI. Full coverage requires 14 kinds × 3 ops (new/get/set) = 42 new FFI symbols (currently 13 exist, so ~29 new).

**Invariants preserved:**
- ADR-006 §2.7.5: allocators must stamp the element-type metadata in the HeapHeader `_pad` field at offset 7 (per W11-fup-C close).
- Zero-tag runtime: element-type byte is written at allocation time, read at element-access time.

**Atomic landing unit:** §2.D is independent of §2.A/§2.B but can land in parallel with §2.C (both are opcode/FFI codegen). §2.D DEPENDS on the same §1.C (all 14 kinds must be defined) before we can generate 42 FFI symbols.

**Estimated scope:** Medium (42 new FFI symbols + element-type stamping logic per-kind + test coverage).

## §4 ADR amendment shape

**Likely amendment needed:** ADR-006 §2.7.24 (Q25.A SUPERSEDED "typed-carrier monomorphization bundle") OR a new § describing the new layer structure post-collapse.

**Amendment SHAPE (to be drafted by supervisor):**

The post-W16.2-J architecture partitions Array method dispatch into THREE layers:

1. **Compile-time producer layer** (`compiler/v2_typed_emission.rs`): Compiler proves element type, emits typed `NewTypedArray<kind>` opcode + element-kind metadata stamped at the stack/heap boundary (§2.7.5 producer-side stamp).

2. **Generic monomorphized layer** (`stdlib-src/core/vec.shape`): User-written methods dispatch via compile-time generic instantiation (the `Vec<T>` extend block). The compiler monomorphizes each method per-concrete-type-argument, so the runtime dispatcher never sees a `Vec<Any>` or type-erased container.

3. **Opcode executor + FFI layer** (`executor/v2_handlers/array.rs` + `shape-jit/src/ffi/v2/mod.rs`): Macro-generated per-kind arms (or manually unrolled equivalents) for primitive operations (New/Get/Push/Set). No per-kind PHF registries; dispatch is O(1) opcode-name-indexed, not PHF-lookup.

The per-kind PHF registries (§1.A) are deleted entirely. The ckpt cascade (§1.B) is eliminated by implementing actual handler bodies in the per-territory files (array_query.rs, array_transform.rs, etc.) that previously surfaced.

**Concrete changes to §2.7.24 text:**
- Strike the "specialized monomorphization inside `TypedArrayData`" framing (that was Phase 2d; Phase 3d / v0.3 retires it).
- Introduce the three-layer partition above.
- Cite W16.2-J close audit as the realization of the three-layer discipline.
- Clarify that heap-element kinds (TypedObject, TraitObject, DateTime, etc.) follow the same producer→opcode→executor flow (no special nested-carrier machinery; a `TypedArray<*const TypedObjectStorage>` is just a v2-raw flat struct, same as `TypedArray<f64>`).

**No NEW `NativeKind` variants, no NEW `HeapKind` variants, no NEW carrier types introduced.** Just reorganization of the dispatch layer and retirement of dead code.

### §6.A Items requiring NO escalation
