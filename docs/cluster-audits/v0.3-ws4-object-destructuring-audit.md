**4a hypothesis empirical result:** CONFIRMED with refinement. The dispatch text
hypothesised "the VM object-destructure path is unimplemented, raises, and the
raise routes through a stubbed AnyError builder". The empirical bisect shows the
VM destructure path *is* implemented — field access and `GetFieldTyped` extraction
work (verified: `p.x`/`p.y` print `1`/`2` in VM mode). The single VM-side defect
is the missing `"object"` arm in `type_check_kinded`, which makes the
`emit_destructure_type_check("object")` guard throw unconditionally. Once that arm
is added, the destructure guard passes and **no exception is raised at all** — the
F4 AnyError stub is never reached for object destructuring. So 4a is resolvable
WITHOUT the F4 AnyError-builder rebuild.

## 1. Sub-problem 4a — VM `let {…} = obj` always throws; VM/JIT divergence

### 1.1 Reproduction (HEAD `ec27b1ef`)

```shape
type Point { x: int, y: int }
let p = Point { x: 1, y: 2 }
let { x, y } = p
print(x)
print(y)
```

- `--mode vm`: `ec=1`. `Error: Runtime error: Uncaught exception (kind
  Ptr(TypedObject)): phase-2c — exception object machinery (AnyError TypedObject
  build, …) … See ADR-006 §2.7.4 / playbook §10 E-exceptions row. (line 3)`
- `--mode jit`: `ec=0`, prints `1` then `2`.

VM/JIT divergence confirmed.

### 1.2 Empirical bisect — where the VM destructure path raises

The bytecode compiler lowers `let { x, y } = p` (top-level form) through
`compile_destructure_pattern_global`, `DestructurePattern::Object` arm at
`crates/shape-vm/src/compiler/patterns/destructure.rs:388-447`. That arm emits, in
order:

1. `emit_destructure_type_check(value_local, "object", "Cannot destructure
   non-object value as object")` — `destructure.rs:395`.
2. For each field: `LoadLocal` + `GetFieldTyped` (correct `TypedField` operand
   with the schema's `field_type_tag`) — `destructure.rs:416-429`.

`emit_destructure_type_check` (`crates/shape-vm/src/compiler/patterns/helpers.rs:124-152`)
emits `LoadLocal; TypeCheck(Basic("object")); JumpIfTrue ok; PushConst msg;
Throw`. So a destructure ALWAYS executes a `TypeCheck` against `Basic("object")`,
and on a `false` result it `Throw`s.

The VM's `TypeCheck` opcode handler is `op_type_check`
(`crates/shape-vm/src/executor/exceptions/mod.rs:301-337`), which delegates the
actual match to `type_check_kinded`
(`crates/shape-vm/src/executor/exceptions/mod.rs:988-1038`):

```rust
TypeAnnotation::Basic(name) => match name.as_str() {
    "int" => ...,
    "number" | "float" => ...,
    "bool" => ...,
    "string" => ...,
    "char" => ...,
    _ => false,                       // <-- "object" lands here
},
...
_ => false,
```

`"object"` is a `TypeAnnotation::Basic`, so it hits the inner `_ => false` at
`exceptions/mod.rs:1016`. **`type_check_kinded` returns `false` for `"object"`
against any value, including a valid `Point` TypedObject.** The destructure guard
therefore fails its `JumpIfTrue` and falls into `Throw`.

The pinned raise site: `crates/shape-vm/src/compiler/patterns/helpers.rs:149`
(`OpCode::Throw` emitted by `emit_destructure_type_check`), executed because
`type_check_kinded` (`crates/shape-vm/src/executor/exceptions/mod.rs:1016`,
`_ => false`) cannot recognise `"object"`.

### 1.3 Why the JIT does not diverge

The JIT path lowers destructuring through MIR
(`crates/shape-vm/src/mir/lowering/stmt.rs:772-784`, `DestructurePattern::Object`
arm) using `projected_field_place` — a direct field projection with **no
`"object"` type-check guard at all**. The JIT's own `TypeCheck` FFI helper
`jit_type_check` (`crates/shape-jit/src/ffi/conversion.rs:82-150`) *does* handle
`"object"`:

```rust
"object" => is_heap_kind(value_bits, HK_TYPED_OBJECT),   // conversion.rs:150
```

So the JIT is doubly insulated: it does not emit the guard, and even if it did,
its checker recognises a TypedObject as `"object"`. The VM emits the guard and its
checker does not. This producer/consumer asymmetry is the entire 4a divergence.

### 1.4 The F4 AnyError stub — display vehicle, not root cause

When the destructure `Throw` fires with no enclosing handler, the VM unwinds via
`handle_exception` (`crates/shape-vm/src/executor/exceptions/mod.rs:206-250`). The
no-handler branch at `exceptions/mod.rs:237-248` returns a `VMError::RuntimeError`
whose text is the constant `PHASE_2C_EXCEPTION_OBJECT_SURFACE`
(`exceptions/mod.rs:112-119`) — the "phase-2c — exception object machinery …"
jargon dump the user saw.

This jargon dump is emitted for **every** uncaught exception regardless of root
cause: the no-handler branch always substitutes the placeholder string instead of
reading the real AnyError payload. Note `build_any_error`
(`exceptions/mod.rs:440-506`) is in fact NOT a `todo!()` — it constructs a real
AnyError `TypedObject` with `category`/`message`/`payload` String fields. The
no-handler formatter simply does not read it.

For 4a specifically, once the `"object"` arm is added (§1.5), the destructure
guard passes and no `Throw` ever fires — so `handle_exception` is never reached
and the F4 jargon is irrelevant to this scenario. The F4 stub still needs an
honest formatter for genuine uncaught exceptions, but that is **WS-3 territory**
(see §5).

### 1.5 Fix plan — 4a

1. **VM `type_check_kinded`** (`crates/shape-vm/src/executor/exceptions/mod.rs`,
   the `TypeAnnotation::Basic` arm at `:994-1017`): add `"object"` matching
   `NativeKind::Ptr(HeapKind::TypedObject)`. For parity with the JIT
   (`jit_type_check` recognises `"function"`, `"void"`, `"any"`, `"null"` etc.)
   also add `"array"` → `NativeKind::Ptr(HeapKind::TypedArray)`, since
   `compile_destructure_pattern` emits the same guard with `"array"` for array
   destructuring (`destructure.rs:137-141`, `:346-350`). This is a kind-tag match
   on the existing per-slot `NativeKind` — no tag decode, no fabrication; the
   kind is stamped at compile time and already carried in the `KindedSlot`. It is
   the same shape as the existing `"string"` arm
   (`exceptions/mod.rs:1011-1014`).
2. **Parity check.** After the fix, `let { x, y } = p` must run identically VM and
   JIT (`ec=0`, prints `1`/`2`). Add a VM-mode regression to a `#[cfg(test)]`
   module covering both the local-scope (`compile_destructure_pattern`) and
   global-scope (`compile_destructure_pattern_global`) destructure forms, plus the
   `match p { { x, y } => … }` object-pattern-in-match form (which hits the same
   `emit_destructure_type_check("object")` guard via `Pattern::Object` in
   `compiler/patterns/checking.rs:174`).

**Scope estimate:** ~1 source file, ~2 small match arms. The destructure codegen
and `GetFieldTyped` extraction are unchanged.

## 2. Sub-problem 4b — JIT/VM lose the destructured binding types

### 2.1 Reproduction (HEAD `ec27b1ef`)

```shape
type Point { x: int, y: int }
fn s(p: Point) -> int { let { x, y } = p; x + y }
print(s(Point { x: 6, y: 8 }))
```

- `--mode vm`: `ec=1`. `error[SEMANTIC]: Cannot infer types for binary operation
  `Add`: operand types are `unknown` and `unknown`. … --> <input>:2:43`.
- `--mode jit`: `ec=1`. `Bytecode compilation failed: Semantic error: Cannot
  infer types for binary operation `Add` …`.

Both modes fail. (The top-level form `let { x, y } = p; print(x + y)` fails
identically — 4b is not function-scoped.)

### 2.2 Root cause — compiler type-tracker, not type inference

The error string "Cannot infer types for binary operation `Add`" is emitted by
the **bytecode compiler**, not the type-inference engine:
`crates/shape-vm/src/compiler/expressions/binary_ops.rs:176`. It fires when
`prove_native_kind()` cannot determine a kind for an operand. So 4b is a
compiler-side type-tracker gap: the destructured bindings `x`, `y` have no proven
compile-time kind.

In `compile_destructure_pattern` / `compile_destructure_pattern_global`, the
`DestructurePattern::Object` arm extracts each field with `GetFieldTyped` (which
DOES carry the field's `field_type_tag` in its operand) but then:

```rust
self.emit(Instruction::new(OpCode::GetFieldTyped, Some(operand)));
// Clear schema after field extraction — the extracted value is a
// scalar (number, string, etc.), not the parent TypedObject.
self.last_expr_schema = None;
self.last_expr_type_info = None;
self.compile_destructure_pattern(&field.pattern)?;
```

(`crates/shape-vm/src/compiler/patterns/destructure.rs:221-226`, and the
global-scope twin at `:429-434`.)

It **clears** `last_expr_schema` / `last_expr_type_info` and never sets
`last_expr_numeric_type` to the field's actual `FieldType`. The recursive
`compile_destructure_pattern(&field.pattern)` then reaches the
`DestructurePattern::Identifier` arm (`destructure.rs:99-128`), whose binding-kind
decision is `let_decl_storage_hint()`
(`crates/shape-vm/src/compiler/helpers_binding.rs:421-433`). That helper reads
`last_expr_numeric_type` and `last_expr_type_info` — both unset/cleared — so it
returns `None`, and the binding local gets no recorded type. When `x + y` is later
compiled, `prove_native_kind()` finds no kind for either local → the `Add` error.

### 2.3 Why the enum struct-variant match path works (the correct mechanism)

`match E::V { x, y }` for `enum E { V { x: int, y: int } }` works in both VM and
JIT (verified: prints `14` for `fn s(e:E)->int { match e { E::V{x,y} => x+y } }`).
The reason is that the match-path enum-struct-variant codegen explicitly
propagates field types:
`crates/shape-vm/src/compiler/patterns/binding.rs:565-577`
(`compile_typed_enum_binding`, `Struct` arm) calls `set_local_type_info(field_local,
&tn)` for each variant struct field. The plain struct/object match path does the
same — `binding.rs:376-394` looks up the schema field's `FieldType` and calls
`set_local_type_info`. **The object-destructure path (`destructure.rs`) is the
only one of the three pattern paths missing this propagation.** (Confirming the
asymmetry: `match E::V(x)` for an enum *tuple* variant fails with `unknown` —
tuple-variant payloads are stored as `__payload_N: Any` and have no
declared-type-name propagation; that is a separate gap, out of WS-4 scope.)

### 2.4 The type-inference side (secondary, surfaces if §2.2 alone is fixed)

`bind_decl_pattern` in the inference engine
(`crates/shape-runtime/src/type_system/inference/items.rs:1158-1187`),
`DestructurePattern::Object` arm at `:1176-1181`, binds each field's pattern to a
`fresh_type_var()` and ignores the source struct type passed in `fallback_type`.
For the 4b reproducer the bytecode-compiler error fires first, so the inference
gap is not the reported symptom — but the inference engine SHOULD also resolve
field types so a `let`-bound destructured field's type is sound for downstream
inference (e.g. a method call on `x`). The correct shape: when `fallback_type`
resolves to a known struct (`struct_type_defs` lookup) or TypedObject schema, look
up each field's declared `TypeAnnotation` and bind the field pattern to that type
— mirroring the `Decomposition` arm at `items.rs:1163-1169` which already resolves
field annotations via `resolve_type_annotation`. The match-arm twin
`bind_pattern_vars` (`crates/shape-runtime/src/type_system/inference/expressions.rs:1188-1241`,
`Pattern::Object` arm at `:1217-1221` and `Pattern::Constructor`/`Struct` arm at
`:1232-1236`) has the identical gap and should be fixed in the same change so the
match struct-pattern (4c) is type-sound once it is no longer rejected.

### 2.5 Fix plan — 4b

1. **Bytecode compiler** (`crates/shape-vm/src/compiler/patterns/destructure.rs`,
   both `DestructurePattern::Object` arms — local `:201-227` and global
   `:409-435`): before the recursive `compile_destructure_pattern(&field.pattern)`
   call, look up the schema field's `FieldType` (via the same
   `schema_registry().get_by_id(schema_id).get_field(key)` path already used by
   `resolve_typed_field_operand_destructure`) and propagate it. Reuse the exact
   `FieldType` → tracked-type-name mapping already in the match path at
   `compiler/patterns/binding.rs:383-393` (`I64`→`int`, `F64`→`number`,
   `Bool`→`bool`, `String`→`string`, `Decimal`→`decimal`). When the field pattern
   is an `Identifier`, set `last_expr_numeric_type` for scalar int/number/width
   fields so `let_decl_storage_hint()` resolves; for nested struct fields, set
   `last_expr_schema` / `last_expr_type_info` to the nested schema instead of
   clearing them. Do NOT clear unconditionally.
2. **Type-inference engine** — fix both `bind_decl_pattern`
   (`type_system/inference/items.rs:1176-1181`) and `bind_pattern_vars`
   (`type_system/inference/expressions.rs:1217-1221` and `:1232-1236`) to resolve
   field types from the source struct/TypedObject type instead of binding
   `fresh_type_var()`. This is required for 4b soundness in the inference pass and
   is a prerequisite for 4c's struct pattern to type-check.
3. **Parity check.** `fn s(p: Point) -> int { let { x, y } = p; x + y }` returns
   `14` in VM and JIT; the top-level `let { x, y } = p; print(x + y)` form too.
   Add regressions for int, number, and nested-struct field destructure.

**Scope estimate:** 2 source files (`destructure.rs`, plus the inference engine's
`items.rs` + `expressions.rs`). The `FieldType` → type-name mapping already
exists; this is propagation wiring, not new machinery.

## 3. Sub-problem 4c — `match` struct-pattern misclassified

### 3.1 Reproduction (HEAD `ec27b1ef`)

```shape
type Point { x: int, y: int }
match Point { x: 3, y: 4 } { Point { x, y } => print(x + y) }
```

- `--mode vm` and `--mode jit`: `ec=1`. `error[E0001]: unexpected `}`, expected
  something else --> <input>:2:26` — a **parse error**.

This is NOT the classification error the dispatch text described. The dispatch
text's "treated as an enum-variant pattern" symptom only surfaces once the parse
ambiguity is removed. With a parenthesised or variable scrutinee:

```shape
type Point { x: int, y: int }
let p = Point { x: 3, y: 4 }
match p { Point { x, y } => print(x + y) }
```

→ both modes: `ec=1`, `Error: Semantic error: Bare enum variant patterns require
type-resolved enum context. Generic fallback is disabled.`

So 4c is **two distinct defects** stacked.

### 3.2 Defect (i) — parse ambiguity on a bare struct-literal scrutinee

Grammar (`crates/shape-ast/src/shape.pest:1188-1192`):

```
match_expr        = { "match" ~ match_scrutinee ~ "{" ~ (match_arm ~ …)? ~ "}" }
match_scrutinee   = { match_scrutinee_ident | expression }
match_scrutinee_ident = { ident ~ &"{" }
```

The `match_scrutinee_ident` fast-path was added (per the grammar comment at
`shape.pest:1189-1190`) so `match x { … }` does not let `expression` greedily
parse `x { … }` as a struct literal. But for `match Point { x: 3, y: 4 } { … }`
the scrutinee *is itself* a struct literal. `match_scrutinee_ident` matches
`Point` (an `ident` followed by `&"{"`) and consumes only `Point` as the
scrutinee. The `match_expr` rule then expects `~ "{"` and binds `{ x: 3, y: 4 }`
as the match body; the first `match_arm` tries to parse `x: 3` and fails at the
closing `}` → `unexpected }`.

This is an inherent ambiguity: `match T { … } { … }` cannot be disambiguated
left-to-right because `T { … }` (struct literal) and `T` + `{ … }` (scrutinee +
body) share a prefix. Pinned site: `crates/shape-ast/src/shape.pest:1191-1192`.

### 3.3 Defect (ii) — bare struct pattern rejected as enum-variant pattern

Once the scrutinee is unambiguous (parens or a variable), the pattern `Point { x,
y }` is parsed by `parse_constructor_pattern` →
`Rule::pattern_unqualified_constructor`
(`crates/shape-ast/src/parser/expressions/control_flow/pattern_matching.rs:250-276`)
into `Pattern::Constructor { enum_name: None, variant: "Point", fields:
Struct([("x", Identifier("x")), ("y", Identifier("y"))]) }`. The grammar
production `pattern_unqualified_constructor` (`shape.pest:1236-1242`) accepts any
`pattern_constructor_name ~ pattern_constructor_payload` — it has no notion of
enum-vs-struct; that classification is deferred to the compiler.

The bytecode compiler then rejects it. Two pinned sites, both in the
`Pattern::Constructor` `(None, _)` arm:

- **Pattern check** (the match-arm guard):
  `crates/shape-vm/src/compiler/patterns/checking.rs:331-334` — the `_ =>` arm
  (which `(None, "Point")` falls into) pushes an unconditional fail-jump. The arm
  body never runs. (The enum-with-name case `(Some(enum_name), _)` at `:297-330`
  resolves the schema; the `(None, _)` case has no equivalent.)
- **Pattern binding** (the match-arm body bindings):
  `crates/shape-vm/src/compiler/patterns/binding.rs:473-478` — the explicit
  `(None, _)` arm returns `Err(SemanticError { message: "Bare enum variant
  patterns require type-resolved enum context. Generic fallback is disabled." })`.
  This is the error the user sees.

Neither `(None, _)` arm checks whether `variant` ("Point") resolves to a
registered **non-enum** schema. The schema registry already distinguishes them:
`Schema::is_enum()` (`crates/shape-runtime/src/type_schema/schema.rs:154-156`)
returns `false` for a struct schema, and the struct schema carries the field map
(`get_field`, `:119-121`). A struct `Point` has a registered schema with fields
`x`, `y` and `is_enum() == false`.

### 3.4 Fix plan — 4c

**Defect (ii) — classification (the primary WS-4 fix):**

1. In both `(None, _)` arms — `compiler/patterns/checking.rs:331` and
   `compiler/patterns/binding.rs:473` — before rejecting/fail-jumping, resolve
   `variant` against the schema registry (`resolve_type_name(variant)` then
   `schema_registry().get(...)`). If a schema exists and `schema.is_enum() ==
   false`, treat the `Pattern::Constructor { enum_name: None, variant, fields:
   Struct(field_pats) }` as a struct/TypedObject pattern: route to the existing
   `Pattern::Object` codegen. The `Pattern::Object` arms already do exactly the
   right thing — `checking.rs:173-206` (`emit_pattern_type_check` + `GetFieldTyped`
   per field) and `binding.rs:341-401` (`GetFieldTyped` + per-field type-name
   propagation, the same code 4b's fix touches). Concretely: extract
   `PatternConstructorFields::Struct(fields)` into the `Vec<(String, Pattern)>`
   shape the `Object` arms consume and delegate. The schema's
   `last_expr_schema`/local-type info is already established by
   `compile_match_binding` (`binding.rs:258-263`) so the struct-pattern path can
   resolve `GetFieldTyped` operands.
2. Keep the `(None, _)` reject ONLY for the genuine case: `variant` resolves to no
   schema, or to an enum schema with no matching variant. The "bare enum variant"
   diagnostic stays for the case where it is actually correct (a bare `Variant`
   with no enclosing enum type context).
3. Validate the struct pattern's field names against the schema (each field in
   `Struct(fields)` must be a declared schema field) — the `Pattern::Object` path
   already does this (`checking.rs:189-197`, `binding.rs:355-363` emit a "Field
   '…' is not declared" error), so delegation gets it for free.

**Defect (i) — parse ambiguity:** This is a grammar-level decision and should be
called by the fix-dispatch owner. Two options:

- **Option A (minimal, recommended):** require a parenthesised scrutinee when it
  is a struct literal — `match (Point { x: 3, y: 4 }) { … }`. The bare-identifier
  fast-path (`match x { … }`) and the variable form (`let p = …; match p { … }`)
  both still work; only the rare "match an inline struct literal" form needs
  parens. This needs no grammar change — it already works (verified). The fix here
  is a clearer parse-error message pointing at the ambiguity, emitted when
  `match_scrutinee_ident` is followed by a `{` that begins what looks like a
  struct-field list rather than a match arm.
- **Option B (grammar widening):** make `match_scrutinee` PEG-order-aware so
  `ident ~ struct_literal_body ~ &"{"` (a full struct literal followed by the
  match-body `{`) is recognised. This is a larger PEG change with backtracking
  cost and risks re-introducing the greedy-struct-literal problem the fast-path
  was added to solve. Not recommended for a v0.3 close.

The WS-4 deliverable for full object-destructuring requires defect (ii) fixed
unconditionally (it blocks `match p { Point { x, y } => … }` over a *variable*,
which is the common form). Defect (i) only blocks the inline-struct-literal
scrutinee; Option A makes it a parenthesisation requirement with a clear error.

**Scope estimate:** Defect (ii): 2 source files (`checking.rs`, `binding.rs`) plus
the inference-side `bind_pattern_vars` already covered by 4b's §2.5 step 2.
Defect (i): 1 file (`shape.pest` or the parser's match-scrutinee error path) for
Option A's improved diagnostic.

## 4. Cross-cutting: shared mechanism across 4a/4b/4c

All three sub-problems converge on object/struct pattern handling, and the fixes
reuse machinery that already exists for the enum-pattern path:

- 4a is a checker-table gap (`type_check_kinded` missing `"object"`).
- 4b and 4c-(ii) both need field-type propagation onto pattern bindings — the
  match-path enum-struct-variant code at `binding.rs:565-577` and the struct
  match-path at `binding.rs:376-394` already do this; the destructure path
  (`destructure.rs`) and the inference engine (`items.rs`/`expressions.rs`) do
  not.
- 4c-(ii) routes the bare struct pattern into the existing `Pattern::Object`
  codegen, which is the same code 4b's compiler fix improves.

No new opcodes, no new carriers, no dynamic-dispatch path. The
`NativeKind`-tag match in §1.5 step 1 is the same shape as the existing scalar
arms. No forbidden pattern is touched.

## 5. Territory split vs WS-3 (F4 AnyError stub)

The dispatch text flags an overlap: 4a's VM raise routes through the F4 AnyError
stub, owned by the parallel WS-3 audit.

**WS-3 owns:** the F4 AnyError stub itself — the uncaught-exception formatter at
`crates/shape-vm/src/executor/exceptions/mod.rs:237-248` (`handle_exception`

**WS-4 owns (this audit):** the object-destructure PATH —

**No double-scoping.** The 4a fix (§1.5) removes the *reason* the destructure path

the F4 stub is irrelevant to the 4a scenario. WS-4 does not touch

observation that the *symptom string* the user saw for 4a is the F4 stub's output;
the *cause* and *fix* of 4a are entirely within WS-4 territory. WS-3's fix is
still independently needed for genuine uncaught exceptions (e.g. an explicit
user `throw` with no handler) — that is not regressed or affected by WS-4.
