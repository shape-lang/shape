## §2 Root cause + emission-site map

### Root Cause: Missing FrameDescriptor registration in annotation handler compilation

**File:** `crates/shape-vm/src/compiler/statements.rs`
**Function:** `compile_annotation_def` (lines 2355–2576)
**Problem:** Annotation handler functions (e.g., `remote___before`) are compiled via `self.compile_function(&func_def)?` at line 2508, but the call to `capture_function_local_storage_hints` is **NEVER MADE** for these functions.

**Contrast with normal function compilation:**

In `crates/shape-vm/src/compiler/functions.rs` line 1750:
```rust
// Normal function path:
self.program.functions[func_idx].locals_count = self.next_local;
self.capture_function_local_storage_hints(func_idx);  // ← CALLED
```

In `crates/shape-vm/src/compiler/statements.rs` line 2507–2509:
```rust
// Annotation handler path:
self.register_function(&func_def)?;
self.compile_function(&func_def)?;  // ← does NOT call capture_function_local_storage_hints
// ... handler.func_id registered, loop continues
```

### Why this breaks JIT

The V2 bytecode verifier (in `crates/shape-vm/src/bytecode/verifier.rs`) enforces the rule:
```rust
// All v2 typed opcodes require a FrameDescriptor
if func.frame_descriptor.is_none() {
    errors.push(VerifyError::V2MissingFrameDescriptor { ... });
}
```

When `capture_function_local_storage_hints` is not called:
1. The annotation handler function's `frame_descriptor` field remains `None`
2. Any v2 typed opcodes emitted in that function (e.g., `NewTypedArrayI64`, `TypedArrayPushI64` from CoW array operations) fail verification
3. The JIT refuses to compile; exec falls back to interpreter OR crashes (SIGSEGV on deoptimization misses)

### Emission sites (both annotations and user functions)

1. **`std::core::remote::remote___before`** (annotation handler from stdlib `remote.shape` line 98–105)
   - When `var`/`let` bindings with aliasing trigger CoW clones during array mutations
   - Emits `NewTypedArrayI64` + `TypedArrayPushI64` as part of CoW shadow copy
   - No FrameDescriptor because `compile_annotation_def` omits the registration step

2. **User-defined `append(&mut arr, value)` function** (test 3)
   - Receives typed array via `&mut` reference
   - Emits `TypedArrayPushI64` when `arr.push(value)` is compiled
   - Normally would get FrameDescriptor via normal `compile_function` path
   - But in test 3 context, it's emitted in scope where type-tracker cannot prove all slots
   - **Actually:** Test 3's `append` is a normal user function, so it SHOULD get a frame descriptor via the normal path at line 1750 of `functions.rs`. The missing descriptor here may be secondary to the unproven type-tracker state (Test 3 hits the pre-existing V3-S5 SURFACE first in VM, so the annotation path isn't the root here — but verification still complains about the JIT-emitted ops)

### Key finding: annotation handler compilation is the primary broken site

- **File:** `crates/shape-vm/src/compiler/statements.rs` **line 2507–2520**
- **Missing call:** `capture_function_local_storage_hints(func_idx)` after line 2508
- **Impact:** ALL annotation handlers (`before`, `after`, `on_define`, `metadata`) skip FrameDescriptor registration
- **Affected stdlib:** `std::core::remote` annotation (tests 1–2), and any user annotation with array/typed mutations
- **Affected user code:** Any user-defined annotation with typed array operations

## §3 Fix recipe + estimate

### Fix (S = Small, <0.5 session)

**Location:** `crates/shape-vm/src/compiler/statements.rs`, lines 2505–2520

**Change:** After the call to `self.compile_function(&func_def)?` at line 2508, add the missing FrameDescriptor registration:

```diff
            self.register_function(&func_def)?;
            self.compile_function(&func_def)?;

+           // Capture frame descriptor for the annotation handler function
+           let func_idx = self.program.functions.len() - 1;
+           self.program.functions[func_idx].locals_count = self.next_local;
+           self.capture_function_local_storage_hints(func_idx);

            let func_id = (self.program.functions.len() - 1) as u16;
```

**Rationale:** Annotation handler functions are compiled just like normal functions, so they must go through the same FrameDescriptor registration pipeline. The `capture_function_local_storage_hints` call is not optional — it's required for v2 typed opcode verification and JIT deoptimization map construction.

**Risk:** **ZERO** — this brings annotation handlers into alignment with the standard function compilation discipline. No new code paths, no fallback logic.

**Testing:** Rerun tests 1, 2 (both should now pass JIT without verification errors). Test 3's remaining surface is orthogonal.

**Estimate:** S (minutes to implement, test, and verify)

## §4 ADR cross-reference + defection-attractor refusals

### Cross-references

1. **ADR-006 §2.7.5.1 (FrameDescriptor requirement for v2 opcodes)**
   - This audit confirms the rule: `capture_function_local_storage_hints` MUST be called for every function that emits v2 typed opcodes
   - Annotation handlers are not exempt from this rule — they were simply overlooked in the compilation path

2. **V3-S5 ckpt-5 consumer-cascade SURFACE (test 3 VM behavior)**
   - Test 3 hits a separate known issue: `ArrayPushLocal` on reference-receiver paths
   - This is **NOT** related to the FrameDescriptor omission; it's a `Arc<TypedArrayData>` carrier SURFACE
   - Fix for §3 will NOT resolve test 3's VM error; test 3 is pre-existing SURFACE territory

3. **W12 typed-array-data-deletion audit (Q25.A carrier supersession)**
   - Reference-receiver typed array mutations are in the W12 audit's scope (the test 3 VM error)
   - FrameDescriptor emission is orthogonal; the deletion applies to heap-carrier choice, not descriptor registration

### Defection-attractor refusals

**No defection-attractors encountered.** This is a clean omission: a function compilation step was forgotten, not a rationalization for avoiding something. The fix is mechanical and brings annotation handlers into the standard discipline.

## §5 Secondary VM bug bundle-or-separate disposition

### Secondary Issue: Dev-mode last-value auto-print emits debug future-ptr

**Repro context:** Test 1 VM behavior (no explicit `print` in the snippet)
**Observed:** VM does NOT segfault, but the implicit last-value print emits `{"String": "<future:104487957735792>"}` instead of the array value or unit
**Root cause:** NOT the FrameDescriptor issue. This is a separate bug in the dev-mode evaluation auto-print logic.

**Where it lives:** Likely in `crates/shape-vm/src/executor/` auto-print / REPL logic that prints the last-evaluated expression's value

**Relation to primary fix:**  SEPARATE. The CoW array mutation completes successfully (VM prints `[1, 2, 3, 4]` for the explicit `print()` calls), so the array operation itself is not broken. The bug is in the display layer — somewhere a `Box<dyn Future>` or internal future pointer is being printed in debug format instead of being resolved or hidden.

**Recommendation:** SEPARATE TICKET. Bundle as a secondary v0.3 gating item if the primary (FrameDescriptor) fix does not resolve it. Root cause will likely be in the last-expression-value capture/display path, not in bytecode emission.
