## §3 Tuple-carrier architecture question (significant blocker)

**Issue:** `zip` operation returns `Array<(T, U)>` (pairs). Current `TypedArray<T>` is monomorphic — no `TypedArray<(f64, i64)>` form exists.

**Design options (audit surfaces, does NOT recommend):**

**(a) New `TypedArray<TupleN<T1,...,Tn>>` carrier**
- Pros: General, extensible to N-ary tuples.
- Cons: Invasive. Touches ADR-006 §2.7.24 typed-carrier-monomorphization; impacts stamp byte (ELEM_TYPE_*) enum; requires cross-kind element layout (alignment, offset computation). Potentially 3–4 weeks of implementation + validation.
- Risk: Blocks dependent operations (zip, tuple-returning HOF builders, etc.).

**(b) Separate `ZippedArray` HeapKind**
- Pros: Special-cased, minimal surface change.
- Cons: Parallel implementation; doesn't solve N-ary generalization; adds to single-discriminator debt (ADR-005 §1).
- Risk: Code duplication in the element-access layer.

**(c) Materialize zip as `Array<Tuple>` (heap-array fallback)**
- Pros: Lowest architectural cost; uses existing `Array<T>` carrier with heap Tuple payloads.
- Cons: Slower (heap allocation per tuple; cache-inefficient vs. typed-array layout).
- Risk: Performance regression on zip benchmark.

**(d) Defer zip to v0.4 entirely**
- Pros: Unblocks J.4–J.5 partition without architectural decision.
- Cons: User-facing API gap (zip is stable in Shape stdlib).
- Risk: Requires coordinating stdlib deprecation or conditional compilation.

**Audit surfaces:** No recommendation. User/supervisor decision required per the design choice (a/b/c/d).

## §4 Deep-equality question (per-kind value-equality dispatch)

**Issue:** `includes(elem)` / `indexOf(elem)` / set operations (union, intersect) require element value-equality, not pointer equality. For native-kind elements (F64/I64/Bool), `==` on bits works. For heap-element kinds (StringV2 / DecimalV2 / TypedObject), requires structural/value comparison.

**Design options (audit surfaces, does NOT recommend):**

**(a) Per-kind `eq_element_<kind>` primitives in `v2_array_detect::*`**
- Pros: Explicit; easy to reason about (one function per kind).
- Cons: Proliferates function count (14 variants × 2–3 ops per kind ≈ 30+ primitives).
- Example: `eq_element_stringv2(ptr_a, ptr_b) -> bool`; `eq_element_decimal(ptr_a, ptr_b) -> bool`.

**(b) Generic `eq_element(a, b, elem_type) -> bool` dispatching internally**
- Pros: Single function; dispatch inside via `elem_type` match.
- Cons: Less static type safety; harder to specialize per-kind.
- Analogous to: Current `write_element(view, index, bits, kind) -> Result` design.

**(c) MethodFnV2-style trait dispatch through `Eq` impl**
- Pros: Rust-idiomatic; leverages existing trait system.
- Cons: Requires heap-element kinds to impl `Eq`; doesn't match v2-raw carrier philosophy (per ADR-006 §2.7.9; no kind-blind `&[KindedSlot]` ABI).
- Risk: Circles back to forbidden `MethodFn` bridge patterns (CLAUDE.md §Renames-to-refuse).

**Audit surfaces:** No recommendation. User/supervisor decision required.

## §5 Closure-callback return-kind threading (HOF builder design space)

**Issue:** `where(|x|...)` / `map(|x|...)` / `select(|x|...)` / `takeWhile(|x|...)` return arrays whose element kind is determined by the closure's return kind. The closure is a `KindedSlot` at runtime; its return kind is a `NativeKind` known only after the closure executes.

**Current architecture (per R8 W1 close):**
- Array-query handlers that use closure callbacks (some/every/find/findIndex per the 8 migrated ckpt3 handlers) invoke `vm.call_value_immediate_nb(closure, arg)` per ADR-006 §2.7.11/Q12 (value-call ABI).
- The result is a `KindedSlot` (bits + kind).
- For **search** operations (`find/findIndex`), the result kind matches the element kind (no problem).
- For **builder** operations (`where/map/filter`), the result kind varies per closure return — and the output array's element kind must match.

**Design questions:**

1. **Kind-rejection semantics:** If one closure invocation returns `Int64` and the next returns `Bool`, does the array (a) reject with a structured error, (b) convert/coerce, or (c) materialize as heterogeneous `Array<Any>`?
   - ADR-006 §2.7.14 forbids Bool-default (clause below).
   - Per J.4-rest discipline, no coercion opcodes (CLAUDE.md §Type System Rules).
   - **Likely answer:** Structured error on kind mismatch.

2. **Builder materialization:** How does the primitive allocate the output array before seeing any closure returns?
   - Likely: Two-pass (scan to determine element kind + size; allocate; populate).
   - Or: Grow-on-demand (start with one kind hint; realloc if kind changes).

3. **ADR-006 §2.7.10 / Q11 MethodFnV2 ABI threading:** The handler calls the closure (via Q12 value-call ABI) and gets back a `KindedSlot`. How does it thread that result-kind knowledge to the `collect_*` primitive?
   - Likely: Handler collects closure results into a temp buffer (`Vec<KindedSlot>`); calls primitive with buffer + expected kind.

**Audit surfaces:** No recommendation. Requires investigation of existing closure-callback patterns (R8 W1 migrated 8 handlers; study their approach). Surface the design shape to user/supervisor for architectural review.
