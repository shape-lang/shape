## 0. Mission scope and headline finding

WS-9 was dispatched to audit the Class (2) cluster: the ~22 non-`#[ignore]`'d
tests in `bin/shape-cli/tests/stdlib/simulation.rs` that fail red at HEAD on
what round-6 WS-1 characterized as a "generic-function-call-return-type /
unannotated-param inference loss".

**Headline correction to the WS-1 framing.** The 22 failures are NOT one
cluster. They split into THREE distinct root causes (§1). Only **14** are the
WS-9 inference-loss class. The remaining 8 are:

* **7 tests** — `__intrinsic_*` scope-gating, a *test-harness artifact* of how
  `simulation.rs` merges stdlib source (§5). Not a compiler defect.
* **1 test** — the `op_new_array(0)` SURFACE residual (V3-S5 ckpt /
  W16.2-C cluster). Already a separately-tracked workstream.

**The WS-9 root cause is NOT generic functions.** None of the failing
helpers are generic (`fn name<T>`). They are *non-generic, unannotated*
functions (`function vec_add(a, b)`). The defect is: **accessing into an
unannotated parameter — `a[i]` (index) or `a.field` (field) — produces a
disconnected `unknown` type, and callsite-driven param widening
(`apply_callsite_unions`) does not flow concrete object/array argument types
back into those access-expression result types.** §3 pins the two compiler
sites.

**This is v0.3-gating** on TWO independent counts (§2):
1. **Spurious-reject** of valid code: `Add`/`<=`/`>=` over unannotated-param
   accesses are rejected with `Cannot infer types ...`.
2. **Silent-wrong-result** soundness defect: `Sub`/`Mul`/`Div`/`Mod`/`Pow`
   over the *same* unannotated-param accesses are NOT rejected — they default
   the access to `NumericType::Number` and emit a float opcode, so
   `f([7,2])` with body `a[0] / a[1]` returns `3.5` instead of the `int` `3`.

## 2. Failure classification per the no-known-incorrectness binding

The no-known-incorrectness re-audit binding (user 2026-05-20,
`docs/cluster-audits/v0.3-no-known-incorrectness-reaudit.md`): crash /
wrong-result / VM-JIT divergence / silent-wrong-output / spurious-reject of
valid code → v0.3-gating. Clean compile error on genuinely-ambiguous code →
v0.4-OK.

**Cluster A is v0.3-gating on two counts.**

### 2.1 Count 1 — spurious-reject of valid code (`Add`, `<=`, `>=`)

Minimal reproducer (HEAD `cbc020ba`, `--mode vm`):

```shape
function twoidx(a, b) { a[0] + b[0] }
let r = twoidx([1, 2], [3, 4]);
print(r);
```
→ `error[SEMANTIC]: Cannot infer types for binary operation 'Add': operand
types are 'unknown' and 'unknown'.`

This is **valid code**: `twoidx` is called exactly once, with two concrete
`int` array literals. A correct strict-typing compiler can specialise the
callee to `(Array<int>, Array<int>) -> int`. The proof that it *should*
compile: the identical body with explicit annotation
`fn twoidx<T>(a: Array<T>, b: Array<T>) -> T` (or
`a: Array<int>, b: Array<int>`) compiles and runs (→ `4`). Rejecting the
unannotated form is a spurious-reject → v0.3-gating.

### 2.2 Count 2 — silent-wrong-result (`Sub`, `Mul`, `Div`, `Mod`, `Pow`)

The SAME unannotated-param access shape, with a strict-arithmetic operator,
does NOT error — it silently produces a wrong-typed result:

```shape
function f(a) { a[0] / a[1] }
let r = f([7, 2]);
print(r);
```
→ HEAD `cbc020ba` `--mode vm` prints `3.5`.

The argument is an `int` array; `int` division `7 / 2` must yield the `int`
`3`. The compiler defaults the un-hinted `IndexAccess` operand to
`NumericType::Number` (§3.3) and emits `DivNumber` → float semantics →
`3.5`. Similarly `function f(a){ a[0]*a[1] }` over `[6,7]` returns `42.0`
(a `number`), not the `int` `42`. The runtime bytecode verifier flags this
(`Bytecode verification failed: 16 violation(s)`) but execution proceeds and
returns the wrong-typed value. A typed numeric opcode emitted without a
proven operand kind, producing a wrong result, is exactly the
silent-wrong-output class CLAUDE.md §Mechanical-enforcement forbids →
v0.3-gating.

This count is the more serious of the two: the spurious-reject is loud, the
wrong-result is silent.

**Cluster B is NOT v0.3-gating** — it is a test-fixture mismatch (§5). The
`__intrinsic_*` gating itself is correct behaviour: gated intrinsics SHOULD
reject ordinary user code. The fix is in the test harness, not the compiler.

The defect has an inference-side cause and a bytecode-compiler-side cause that
together produce both symptoms.

### 3.2 Inference-side cause — index access loses the element type

`crates/shape-runtime/src/type_system/inference/access.rs:359`
`infer_index_access`. When the indexed object's type is a bare
`Type::Variable` (an unannotated param), control reaches the `_ =>` arm
(`access.rs:399-415`):

```rust
_ => {
    let result_type = self.fresh_type_var();   // a NEW, disconnected var
    let var = self.fresh_var();
    self.constraints.push((
        object_type.clone(),
        Type::Constrained { var, constraint: Box::new(TypeConstraint::Iterable) },
    ));
    Ok(result_type)
}
```

The `Iterable` constraint (`type_system/types/constraints.rs:13`) is a **bare
marker** — it carries no element type. So `result_type` (what `a[i]`
resolves to) is **never linked** to the iterable's element. Even after
callsite widening unifies `a` with `Array<int>`, `a[i]`'s type stays a
disconnected fresh variable → resolves to `unknown`.

Contrast: the `Type::Concrete(TypeAnnotation::Array(elem_type))` arm
(`access.rs:372-377`) correctly returns `*elem_type` — which is why the
explicitly-annotated `a: Array<int>` form works (repro R9).

The field-access twin, `infer_property_access_fallback`
(`access.rs:335-356`), is *better* — its `TypeConstraint::HasField(property,
result_type)` (`constraints.rs:15`) DOES carry the field type — but it is
still defeated by §3.4 (the constraint is solved before the param widens).

### 3.3 Bytecode-compiler-side cause — `Add` rejects, strict-arithmetic mis-defaults

`crates/shape-vm/src/compiler/expressions/binary_ops.rs`.

`is_strict_arithmetic` (`compiler/expressions/numeric_ops.rs:12`) =
`{Sub, Mul, Div, Mod, Pow}`. `Add` is excluded (it is overloaded — numeric
add / string concat / array concat / object merge).

* **`Sub`/`Mul`/`Div`/`Mod`/`Pow` path** (`binary_ops.rs:1747-1755`):
  ```rust
  if is_strict_arithmetic(op) {
      if left_numeric.is_none() && matches!(left, Expr::IndexAccess { .. }) {
          left_numeric = Some(NumericType::Number);   // <-- unproven default
      }
      ...
  }
  ```
  An `IndexAccess` operand with no numeric hint is **defaulted to
  `NumericType::Number`** so a typed `MulNumber`/`DivNumber`/... opcode fires.
  For an `int` array this is a *fabricated, wrong* kind — and the
  emit-side proof guard `numeric_operand_proof_gap`
  (`binary_ops.rs:221-272`) only inspects `Expr::Identifier`, so it returns
  `None` for `Expr::IndexAccess` and never catches the fabrication. Result:
  silent-wrong-result (§2.2).

* **`Add` path** (`binary_ops.rs:1007`, falls through to
  `binary_ops.rs:1365-1373`): the `Add` arm has the overload-disambiguation
  logic and `lhs_confirmed`/`rhs_confirmed` gates (`binary_ops.rs:1313-1326`).
  An `IndexAccess` operand whose `infer_expr_type` yields `unknown` and whose
  `last_expr_numeric_type` is `None` is `NoPlan` → `strict_typing_binop_error`
  (`binary_ops.rs:160-185`). There is **no IndexAccess→Number fallback in the
  `Add` arm** — that is the Add/Mul asymmetry (repro R19 vs R20: identical
  bodies, only the operator differs; Mul compiles, Add errors). Ordered
  comparisons (`<=`,`>=`) are likewise not `is_strict_arithmetic` and have no
  such fallback → field-access `<=` rejected (repro F1).

The `Add` rejection is the LESS dangerous of the two — and the
`IndexAccess`→`Number` default in the strict-arithmetic arm should NOT be
"copied to `Add` to make it compile". That would convert a loud spurious-reject
into a silent-wrong-result. The correct fix removes the fabrication, it does
not spread it (§6).

### 3.4 Why callsite widening does not rescue this

`apply_callsite_unions`
(`crates/shape-runtime/src/type_system/inference/mod.rs:1233`) is the
transitive callsite-driven param-type propagation that round-6 WS-2 relies on.
It DOES widen the param entry of a `Type::Function` to the union of observed
concrete arg types, and `union_from_observed_types_with_resolved`
(`mod.rs:1573`) accepts object/array types fine.

But the inference entry point (`mod.rs:1188-1230`) runs in this order:

```
infer_item (per-function body inference)  →  solver.solve(constraints)  →  apply_callsite_unions
```

The `Iterable` / `HasField` constraints are solved **before**
`apply_callsite_unions` widens the param. By the time the param widens, the
constraints are already consumed and discarded — there is no re-solve.
`apply_callsite_unions` only feeds the widened param type back into the
function's *return* type, and only through two narrow paths:
`propagate_return_alias_substitution` (`mod.rs:1460`, handles a return type
that IS a param var via `return_var_aliases`) and
`materialize_pending_return_union` (`mod.rs:1487`). Neither re-resolves a
return variable that was *produced by* an `Iterable`/`HasField` constraint
over a param var.

This is why:
* repro F2 — `getx(p){ p.x }` called with a concrete `{x:5}` — `getx`'s
  return type stays `unknown` (the return is the `HasField` `result_type`
  fresh var, not the param var).
* repro G1 — even `passthru(p){ p }` (return *is* the param var) — `r.x`
  still fails: although the param widens, the compiler's own
  `infer_expr_type` (`compiler/expressions/mod.rs:1345`) re-runs against the
  type tracker and `get_function_return_type` stores only a flat **string**
  hint (`infer_return_type_hints_from_types` →
  `inferred_type_to_hint_name`, `compiler_impl_reference_model.rs:954`),
  which cannot represent an object/array shape usable for downstream
  `.field` / `[i]` access.

Net: the unannotated array/object param is observed concretely at the
callsite, but that concrete shape never reaches the access-expression's
result type.

### 3.5 Adjacent finding — anonymous object-type annotations also fail

`function aabb_overlaps(a: {min_x: number, max_x: number}, b: {...}) { a.min_x <= b.max_x }`
**still** errors (repro `ann3`). Only a *named* `type Box {...}` annotation
resolves field access (repro `ann4` → `true`). This is an adjacent
anonymous-object-type-annotation gap, not strictly the WS-9 inference-loss
class, but it lives in the same `infer_property_access` family and a WS-9 fix
should be checked against it.

## 4. Root-cause family determination

Mission asked which family this is: (a) ε-family wrong-result residual; (b)
WS-3-named `?`-operator type-loss; (c) round-6 WS-6/WS-6b generic-arg
monomorphization; or (d) distinct.

**Determination: (d) — a distinct root cause, with a partial (a) overlap.**

* **NOT (c) generic-arg monomorphization.** WS-6 / WS-6b
  (`b61f8bf2`, `320af868`) fixed *generic free-function* calls
  (`fn f<T>(...)`) accepting struct/enum/Option/Result/inferred-var args. The
  WS-9 helpers (`vec_add`, `aabb_overlaps`, ...) declare **no type
  parameters** — they are non-generic. They never enter the
  `monomorphization/` path. The WS-1 "generic-function" framing and the
  `#[ignore]` text ("`rk4_system` ... is itself an unannotated generic
  function") are inaccurate: `rk4_system(f, y0_vec, ...)` has no `<T>`. The
  defect is unannotated-*parameter* inference, not generic instantiation.

* **NOT (b) the `?`-operator residual.** No `?` operator appears anywhere in
  the WS-9 reproducers or in `ode.shape` / `collision.shape`. WS-3's F2 is a
  `TryUnwrap`-stamp loss; orthogonal.

* **Partial (a) — same *family* as ε, distinct *instance*.** The ε-family
  (ε1-ε5) is the "typed opcode emitted on an unproven/wrong kind →
  wrong-result" class. The §2.2 silent-wrong-result count (`a[0]/a[1]` on an
  `int` array → `3.5`) is structurally a 6th ε-instance: a fabricated
  `NumericType::Number` default driving a typed float opcode. But the §2.1
  spurious-reject count and the §3.2/§3.4 inference-loss cause are NOT ε —
  ε never produced a clean rejection, and ε never touched
  `infer_index_access` / `apply_callsite_unions`. WS-9 is best treated as a
  **distinct cluster** whose silent-wrong-result symptom happens to land in
  the ε behaviour class.

**Pinned sites:**
* `crates/shape-runtime/src/type_system/inference/access.rs:399-415`
  (`infer_index_access` bare-variable arm — `Iterable` carries no element
  type).
* `crates/shape-runtime/src/type_system/inference/mod.rs:1188-1230`
  (inference ordering — `solve` before `apply_callsite_unions`; no re-solve
  of access constraints after param widening).
* `crates/shape-vm/src/compiler/expressions/binary_ops.rs:1747-1755`
  (strict-arithmetic `IndexAccess`→`NumericType::Number` fabrication).
* `crates/shape-vm/src/compiler/expressions/binary_ops.rs:221-272`
  (`numeric_operand_proof_gap` inspects only `Expr::Identifier`, misses
  `Expr::IndexAccess`).

**Stacked-blocker note.** Even with the WS-9 inference defect fixed, the
ode/physics tests will NOT immediately pass: a fully-annotated `vec_add`
(`a: Array<number>, b: Array<number>`) reaches the next blocker —
`Runtime error: Not implemented: op_new_array(0): SURFACE` from the
`let mut out = []` accumulator (Cluster C / V3-S5 ckpt). WS-9 and the
op_new_array SURFACE are stacked in the same code path. The collision tests
(`aabb_overlaps` etc.) do NOT construct empty arrays in the hot path, so they
ARE expected to pass once WS-9 lands (repro `ann4` confirms the
named-type-annotated `aabb_overlaps` runs → `true`).

## 5. Cluster B disposition — test-harness artifact, NOT a compiler defect

`bin/shape-cli/tests/stdlib/simulation.rs:32-40` `with_modules` reads raw
stdlib source via `read_stdlib_module`, runs `strip_import_lines`, and
concatenates it as ordinary user code. `core/random.shape:12` etc. call
`__intrinsic_random()` / `__intrinsic_brownian_motion()` — `allow_internal_builtins`-gated
symbols reserved for `std::*` scope and compiler-generated code. Stripped of
their `@module std::core::random` association the calls are plain user code,
and the gate correctly rejects them.

This is a **fixture mismatch**: the test exercises stdlib *source* outside its
module scope. The gating behaviour is correct. The fix path (NOT WS-9 fix
territory) is one of: (a) load these modules through the real module loader so
the `std::*` scope is preserved; (b) test the public wrapper API
(`random()`, `dist_uniform()`) through a properly-imported module rather than
raw-concatenated source. 7 tests: `test_distributions_wrappers`,
`test_stochastic_wrappers`, the 5 `test_monte_carlo_*` variance-reduction
tests. Recommend handing this to a test-infrastructure follow-up, separate
from the WS-9 compiler fix.

## 6. Disposition and fix plan

### 6.1 Cluster A (WS-9) — v0.3-gating, fix required

**Sub-cluster estimate: one moderate sub-cluster, ~3 source files, no new
opcode / no ABI change / no ADR amendment.**

The fix has an inference half and a compiler-emit half; they must land
together (fixing only the emit half without the inference half would force the
emit half to keep fabricating).

**Inference half** (`crates/shape-runtime/src/type_system/inference/`):
1. `access.rs` `infer_index_access` bare-`Type::Variable` arm: instead of an
   unconstrained `Iterable` marker + disconnected fresh var, push a constraint
   that links the indexed object's variable to `Array<result_type>` (i.e.
   constrain `object_type == Array<elem>` with `elem = result_type`), so when
   the param later unifies with a concrete `Array<int>` the element type
   propagates to `a[i]`. This is the same shape the existing
   `infer_property_access_fallback` `HasField` constraint already uses for
   field access — extend the index path to carry its element type the same
   way. Verify the constraint solver handles the new shape; check
   `inference_tests.rs` for a regression slot.
2. Ensure the access-expression constraints are re-resolved after
   `apply_callsite_unions` widens a param — OR widen params *before* the
   `solver.solve` call (`mod.rs:1188-1230` ordering). The minimal change is to
   feed the `apply_callsite_unions` `substitutions` map back through one more
   `solver.solve` / `unifier.apply_substitutions` pass over the recorded
   access constraints. (Investigate which is cheaper — re-solve vs.
   re-order — the fixpoint in `apply_callsite_unions` already iterates.)
3. The compiler-side flat-string return-type hint
   (`infer_return_type_hints_from_types` / `inferred_type_to_hint_name`,
   `compiler_impl_reference_model.rs:954`) cannot represent object/array
   return shapes. For `getx(p){ p.x }`-shaped callees to expose a usable
   return type, the per-function inferred `Type::Function` return must reach
   the compiler's `infer_expr_type` for `FunctionCall`
   (`compiler/expressions/mod.rs:1391`) as a structured type, not a `Basic`
   string. Investigate whether `infer_param_concrete_types_from_types`'s
   `ConcreteType` projection (already structured) can be reused for the
   return position.

**Compiler-emit half** (`crates/shape-vm/src/compiler/expressions/binary_ops.rs`):
4. Once the inference half resolves `a[i]` to a concrete element type, the
   `IndexAccess`→`NumericType::Number` fabrication at `binary_ops.rs:1747-1755`
   becomes both unnecessary and harmful (it would still mis-default an
   `int`-element array to `Number`). **Remove the fabrication** and let the
   typed-emit path read the proven element kind. If, post-inference-fix, an
   `IndexAccess` operand still has no proven kind, that is a genuine
   `ProofGap` → surface a clean error (extend `numeric_operand_proof_gap`,
   `binary_ops.rs:221`, to also inspect `Expr::IndexAccess`). Do NOT add an
   `IndexAccess`→`Number` fallback to the `Add` arm — that spreads the
   silent-wrong-result.
5. With the element type proven, the `Add` arm's `lhs_confirmed`/
   `rhs_confirmed` gates (`binary_ops.rs:1313-1326`) and the ordered-comparison
   path will see a concrete numeric type and the spurious-reject disappears.

**Verification gates for the fix:** the §3.1 reproducer ladder must flip
(R3/R5/R14/F1/F2/G1 → compile-and-run; R19/wrong2 → either run with the
*correct* `int` result or, for genuinely-ambiguous cases, a clean `ProofGap`
error — never a fabricated `Number`). The 8 collision tests in Cluster A are
