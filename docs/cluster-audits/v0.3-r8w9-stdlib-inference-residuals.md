## §1 — distributions_advanced.shape Investigation

### Test Program
```shape
from std::core::distributions_advanced use { normal_pdf };
print("loaded distributions_advanced")
```

### Empirical Results

**VM:**
```
error[SEMANTIC]: Cannot infer types for binary operation `Sub`: operand types are `unknown` and `unknown`. Strict typing requires both operands to have a known concrete type at compile time. Add a type annotation to disambiguate.
  --> <input>:3:1
```

**JIT:**
```
Error: Runtime error: Bytecode compilation failed: Semantic error: Cannot infer types for binary operation `Sub`: operand types are `unknown` and `unknown`...
```

### Root Cause Analysis

The module's function signatures lack type annotations on parameters. Example at line 223:
```shape
pub fn beta_pdf(x, a, b) {
    ...
    exp((a - 1.0) * ln(x) + (b - 1.0) * ln(1.0 - x) - ...)
}
```

When the compiler encounters `a - 1.0`, it sees:
- `a` has type `TypeVar::fresh()` (unknown; could be any type)
- `1.0` is `number`
- The Sub operator demands **both operands to have concrete types at compile-time** per Shape v0.3 strict-typing rule
- Inference fails → compile error

**Affected functions:** ~20 public and internal functions with arithmetic operations on parameters:
- `chi_square_pdf(x, k)` — `k / 2.0`
- `chi_square_sample(k)` — `k / 2.0`
- `t_pdf(x, df)` — `(df + 1.0) / 2.0`
- `t_cdf(x, df)` — arithmetic on `df`
- `t_sample(df)` — arithmetic on `df`
- `beta_pdf(x, a, b)` — `a - 1.0`, `b - 1.0`
- `beta_cdf(x, a, b)` — delegates (no direct arithmetic)
- `gamma_pdf(x, k, theta)` — `k - 1.0`
- `gamma_cdf(x, k, theta)` — delegates
- `gamma_sample(k, theta)` — `k < 1.0`, `k - 1.0 / 3.0`
- `regularized_gamma_p(a, x)` — internal helper with arithmetic
- `regularized_gamma_q(a, x)` — internal helper with arithmetic
- `regularized_beta(x, a, b)` — internal helper with arithmetic

### Failure Classification

**Type:** Clean compile-error (not runtime divergence)  
**VM ec:** 1 (compilation fails)  
**JIT ec:** 1 (compilation fails)  
**Both modes agree:** YES (same compile-time semantic check)

### Unblocking Strategy

Add `: number` annotations to all parameter signatures. Examples:

```shape
// Before:
pub fn beta_pdf(x, a, b) { ... }
pub fn gamma_pdf(x, k, theta = 1.0) { ... }
function regularized_gamma_p(a, x) { ... }

// After:
pub fn beta_pdf(x: number, a: number, b: number) { ... }
pub fn gamma_pdf(x: number, k: number, theta: number = 1.0) { ... }
function regularized_gamma_p(a: number, x: number) { ... }
```

**Effort estimate:** 0.5–1 hour (annotation-only, no logic changes)  
**Pattern:** Identical to Cluster B fix pattern (a06469b2)

### Supervisor Disposition Mapping

**Is this a Cluster-B-follow-up situation?**
- ✓ Same-file unannotated parameter inference loss (YES)
- ✓ Fix is local type annotation (YES)
- ✓ No cross-module boundary involved (YES)
- ✓ Clean compile error (YES)

**→ Classification: (b) Cluster-B-follow-up — v0.3-gating candidate**

Recommendation: Add type annotations to unblock. Should be batched with any remaining Cluster B sites.

## §2 — ode.shape Investigation

### Test Program
```shape
from std::core::ode use { euler };

```

### Empirical Results

**VM:**
```
error[SEMANTIC]: Cannot infer types for binary operation `Add`: operand types are `unknown` and `unknown`. Strict typing requires both operands to have a known concrete type at compile time. Add a type annotation to disambiguate.
  --> <input>:3:1
```

**JIT:**
```
Error: Runtime error: Bytecode compilation failed: Semantic error: Cannot infer types for binary operation `Add`: operand types are `unknown` and `unknown`...
```

### Root Cause Analysis

Function signatures lack type annotations. Example at line 27:
```shape
pub fn euler(f, y0, t_start, t_end, dt) {
    let steps = floor((t_end - t_start) / dt);
    let mut t = t_start;
    let mut y = y0;
    let mut results = [];
    for i in range(0, steps + 1) {
        results.push({ t: t, y: y });
        y = y + f(t, y) * dt;  // ← line 35: fails here
        t = t + dt;
    }
    results
}
```

At line 35, `y = y + f(t, y) * dt`:
- `y` has type `TypeVar::fresh()` (unknown; from unannotated `y0` parameter)
- `f(t, y) * dt` has type `TypeVar::fresh()` (unknown; `f` return type not specified)
- Add operator requires **both operands concrete** → compile error

**Affected functions:** All 6 integrators + 5 helpers:
- **Public scalar solvers:** `euler(f, y0, t_start, t_end, dt)`, `rk4(...)`, `rk45(...)`
- **Public vector solvers:** `euler_system(f, y0_vec, t_start, t_end, dt)`, `rk4_system(...)`, `rk45_system(...)`
- **Internal helpers:** `vec_add(a, b)`, `vec_scale(a, s)`, `vec_add_scaled(a, b, s)`, `vec_sub(a, b)`, `vec_norm(a)`

### Unblocking Strategy

Annotate all function signatures with appropriate types:

**Scalar solvers:**
```shape
pub fn euler(f: (number, number) -> number, y0: number, t_start: number, t_end: number, dt: number) { ... }
pub fn rk4(f: (number, number) -> number, y0: number, t_start: number, t_end: number, dt: number) { ... }
pub fn rk45(f: (number, number) -> number, y0: number, t_start: number, t_end: number, tol: number = 0.000001, dt_init: number = 0.0, dt_min: number = 0.000000000001, dt_max: number = 0.0) { ... }
```

pub fn rk45_system(f: (number, Array<number>) -> Array<number>, y0_vec: Array<number>, t_start: number, t_end: number, tol: number = 0.000001, dt_init: number = 0.0, dt_min: number = 0.000000000001, dt_max: number = 0.0) { ... }

**Classification:** Module imports cleanly. V2 verifier preamble is a **cosmetic v0.4 follow-up** (tracked in v0.3-r8w6-hashmap-key-kind-audit.md as "full V2 type soundness for every JIT-emitted opcode"). JIT fallback to interpreter preserves correctness. This is Δ3 behavior per G.2 §1.

### Part B: Function Usage Test

**Test program:**
```shape
from std::core::utils::property_testing use { property, gen_int };

let test_fn = || { true };
let gen_fn = gen_int(0, 10);
let result = property("test", 5, gen_fn, |x| {
  x == x
});

print(result.passed)
```

**VM Result:**
```
error[SEMANTIC]: Cannot infer types for binary operation `Equal`: operand types are `unknown` and `unknown`. Strict typing requires both operands to have a known concrete type at compile time. Add a type annotation to disambiguate.
  --> <input>:6:3
   |
 6 |   x == x
     |   ^~~~~~
```

**JIT Result:** (expected same compile error)

### Root Cause Analysis

Function signature at line 14:
```shape
pub fn property(name, n_trials, gen_fn, prop_fn) {
    ...
    for i in range(0, n_trials) {
        let input = gen_fn();
        let result = prop_fn(input);  // ← type of input unknown
        ...
    }
    ...
}
```

The user calls:
```shape
property("test", 5, gen_fn, |x| { x == x })
```

**Type inference path:**
1. User passes closure `|x| { x == x }` as `prop_fn` argument
2. Function body attempts to call `prop_fn(input)`, which invokes the closure with argument type = type of `input`
3. `input = gen_fn()` where `gen_fn` is a generator closure with **no return-type annotation**
4. Therefore, `input` has type `TypeVar::fresh()` (unknown)
5. Closure parameter `x` receives type `TypeVar::fresh()` (unknown)
6. Closure body `x == x` fails inference because Equal demands concrete operand types

**Key difference from Cluster B:** The problem is **not** in property_testing.shape's own signature. The problem is at the **generic-function boundary** where the caller's closure argument types are not propagated inward.

### Existing Cluster C Changes (2026-05-24)

Commit 979727f1 annotated `run_properties(tests)` with `let mut results: Array<int> = []` to fix empty-array element-type inference. That fix resolved the module body, but did **not** address the closure-argument type-propagation gap in the public `property()` function.

The residual is **different** from Cluster C (which was about empty-array binding types) — this is about **closure-parameter inference through a generic-function boundary**.

### Unblocking Attempts

**Attempt 1: Annotate property() parameters**
```shape
// Cannot do this—property() doesn't know the type of its caller's closure args
pub fn property(name: string, n_trials: int, gen_fn: () -> _, prop_fn: (_) -> bool) {
    ...
}
```
This doesn't work because `gen_fn()` can return any type, and `_` is a wildcard (not a concrete type).

**Attempt 2: Use bidirectional inference**
```shape
// Require the caller to annotate closure args:
property("test", 5, gen_fn, |x: int| { x == x })
```
This WOULD work but requires the user to annotate. The compiler currently lacks bidirectional inference to auto-propagate `int` from `gen_fn`'s actual type.

**Attempt 3: Monomorphic wrapper**
```shape
pub fn property_int(name: string, n_trials: int, gen_fn: () -> int, prop_fn: (int) -> bool) {
    property(name, n_trials, gen_fn, prop_fn)
}
```
This is a workaround (create specialized versions for common types), but defeats the purpose of a generic function.

### Supervisor Disposition Mapping

**Is this a Cluster-B-follow-up situation?**
- ✗ NOT same-file parameter annotation (NO — the signature can't be annotated usefully)
- ✗ NOT same-file local fix (NO — the issue is at the cross-module boundary)
- ✓ Cross-module generic-function inference loss (YES)

**Is this a simple v0.4 deferral?**
- YES — requires bidirectional type inference to auto-propagate closure-arg types from call sites inward

**→ Classification: (c) v0.4 different territory — cross-module generic-fn inference gap**

Recommendation: Document as a design limitation for v0.3 (closure-arg inference through generic boundaries requires bidirectional inference, not available in v0.3 forward-inference-only architecture). Defer to v0.4 type-system enhancement.
