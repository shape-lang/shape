### §1.B The W16.2-A subsumption mechanism

`Array<dyn HasX> = [Bar{v:1}, Bar{v:2}]` does NOT resolve through the
`dyn`-annotation path. `resolve_typed_array_kind_from_annotation`
(`v2_typed_emission.rs:507-521`) only matches `Generic{name:"Array",
args:[Basic(n)]}` where `n` is a registered struct — `args[0]` being
`TypeAnnotation::Dyn(...)` (the `dyn HasX` form, `ast/types.rs:46`)
returns `None`. The literal instead picks up `TypedArrayKind::TypedObject`
through the element-inference arm: each `Bar{v:1}` is a struct literal
inferring `ConcreteType::Struct(_)`, and `array_elements_all_typed_object`
(`collections.rs:258`) routes the literal to the v2-raw
`TypedArray<*const TypedObjectStorage>` carrier. `arr[i].x_str()`
then dispatches via the existing TypedObject schema → trait-method
machinery (which already works at HEAD per Smoke s3).

### §1.C The genuine gap

Fixture 7 (`nonstruct`) is a genuine functional gap. `Array<dyn Speak>
= [1, "hello"]` — trait objects over scalar `int` and `string` — has
NO struct elements to fall through on: `array_elements_all_typed_object`
returns false, `infer_array_element_type` finds a heterogeneous
`[int, string]` shape, and the literal falls to `OpCode::NewArray`,
which SURFACEs `op_new_array(2)` VM and JIT (both ec=1). This is the
case W16.2-B's `BoxTraitObject` per-element auto-boxing genuinely
addresses: each scalar must be boxed into `TraitObjectStorage` with a
vtable, because a raw `int` slot carries no trait-method dispatch
identity.

### §1.D §1.B-style cascade behavior is identical between TypedObject and TraitObject

`arr.len()` / `arr.slice()` / `arr.map()` fail identically on
`Array<dyn HasX>` AND `Array<TypedObject>` (`Array<Bar>`) — both
surface `Array.len: SURFACE — V3-S5 ckpt-5 consumer-cascade tier 3`
(W16.1 audit §1.B `ckpt[2-5]_surface` cascade; `array_operations.rs`
`ckpt5_typed_array_surface`). This is the W16.1 §1.B 125-site cascade,
NOT a W16.2-B-specific gap — the TypedObject and TraitObject carriers
are equally blocked on it.

### §1.E A trait-object-array iteration type-inference gap (separate class)

`fn describe(items: Array<dyn HasX>) { for it in items { ... it.x_str() } }`
fails compile-time inference: `it.x_str()` resolves `it` to `unknown`
("Cannot infer types for binary operation `Add`: operand types are
`string` and `unknown`"). The same `for it in items` over a
`Array<Bar>` param works (`to_fn` ec=0). This is a trait-object-array
**iteration element-type inference** loss — `for` over a `dyn Trait`
array param does not narrow the loop variable to the trait type.
Distinct from `op_new_array`; NOT W16.2-C territory; NOT W16.2-B
territory either (W16.2-B is a construction-site sub-cluster). Named
here for class-shift awareness — INVESTIGATE-class, tracked separately.

## §3 W16.2-C codegen recommendation (mission Q3 / W16.1 item 6.B.1)

### §3.A The two options (W16.1 audit §2.1 empty-literal sub-case)

The W16.1 audit named two §2.7.5-compliant codegen alternatives:

- **(a) Defer the allocator emission to the first push site** — the
  existing `compile_array_with_spread` shape, generalized: instead of
  emitting `NewArray(0)` up front, emit nothing at the accumulator
  site; at the first `push`, emit the typed `NewTypedArray<kind>`
  allocator with the proven element kind, then `TypedArrayPush<kind>`.
- **(b) Thread the destination slot's `ConcreteType::Array<T>`
  through a new `Operand::TypedArrayAlloc { elem_kind, capacity }`
  operand** — analogue of the existing `Operand::TypedObjectAlloc`.
  The `NewArray` emit site becomes a typed `NewTypedArray<kind>` emit
  with the element kind carried in the operand, because the
  destination's `ConcreteType::Array<T>` is known at compile time.

### §3.B Empirical constraint that shapes the recommendation

Confirmed at HEAD `3f227c63`: `op_array_push` and `op_array_push_local`
(`array_operations.rs:69-181`) ONLY accept a
`NativeKind::Ptr(HeapKind::TypedArray)` receiver — a v2-raw
`*mut TypedArray<T>` with a stamped element-type byte. Any other
receiver kind hits `ckpt5_typed_array_surface`. The runtime element
kind is read from the array header's stamped `elem_type` byte
(`v2_array_detect::read_elem_type_byte`), and `push_element` dispatches
on `V2ElemType`. **There is no untyped/heterogeneous array carrier at
runtime** — every live array MUST be a kind-monomorphized
`TypedArray<T>`.

This is decisive. Both (a) and (b) must produce a typed
`NewTypedArray<kind>` allocation; the question is only *where the
element kind is sourced*.

Spread complication (E2): `[...a, 4, 5]` — the spread source `a` and
the literal tail `4, 5` may have different element kinds in the
general case. For the v0.3 spread snippets (`arr_spread`,
`arr_spread_min`) the sources are homogeneous (`[1,2,3]` int spreads +
int tail). A genuinely mixed `[...intArr, "str"]` is the same
heterogeneous-element gap as W16.1 §1.A.1 / E3 — out of the W16.2-C
empty-literal scope and must surface-and-stop honestly (the W16.1
§6.B.2 heterogeneous-stance item).

### §3.C Recommendation: **option (b)** — `Operand::TypedArrayAlloc { elem_kind, capacity }`

**Recommend option (b)** for the W16.2-C empty-literal close, with
this concrete rationale (decision-ready for supervisor ratify):

1. **Runtime-allocator discipline (the deciding factor).** Option (a)
   defers allocation to the first push — but then the *empty-array
   case* (`let xs = []` with zero pushes, or a comprehension/spread
   that produces zero elements at runtime) has no allocator emission
   at all, leaving a hole. The accumulator slot would hold an
   uninitialized / null value when the loop body never runs. Option
   (b) emits exactly one typed allocator at a deterministic point
   with `capacity` (0 for the empty accumulator; the
   comprehension/spread then pushes). The runtime always has a real
   `TypedArray<T>` to push into, even for zero-iteration loops. This
   matches the existing `compile_typed_object_literal` →
   `NewTypedObject` + `Operand::TypedObjectAlloc` shape that the
   annotation harness already uses for empty objects (E4-E9 emit
   `NewTypedObject` with `Operand::TypedObjectAlloc { field_count: 0 }`
   right next to their `NewArray(0)` — the object side ALREADY uses
   option (b)'s shape; the array side is the inconsistent half).

2. **§2.7.5 producer-side stamp-at-compile-time.** For E1
   (comprehension) the element kind is the `comp.element` expression
   type — proven at compile time. For the accumulator-binding cases
   the destination `ConcreteType::Array<T>` is in the type-tracker.
   Option (b) carries that proof in the operand; the runtime stamps
   the `elem_type` byte from the operand, never decodes it. This is
   the ADR-006 §2.7.5 discipline verbatim.

3. **Surface area.** Option (a) requires every push site
   (`compile_array_with_spread` has 3 distinct push paths — range
   spread, generic-iterator spread, literal tail;
   `compile_comprehension_clauses` has its own) to carry "is this the
   first push? if so emit the allocator" branching state. Option (b)
   localizes the change to the emit-site: the accumulator emit picks
   the typed opcode + operand once. Fewer mutation points, lower risk
   of an un-allocated accumulator slipping through one push path.

4. **Bytecode density.** Option (b) is denser: one `NewTypedArray<kind>
   capacity=N` vs option (a)'s allocator-emitted-mid-loop with
   first-push tracking. Marginal, but it favors (b).

5. **Consistency with W16.2-A.** W16.2-A already established
   `NewTypedArrayTypedObject` + the typed-push opcodes; the
   `TypedObjectAlloc` operand precedent exists. A new
   `Operand::TypedArrayAlloc { elem_kind, capacity }` is a direct
   analogue. The `TypedArrayKind` enum already maps each kind to its
   `new_opcode()` (`v2_typed_emission.rs:106-125`) — option (b) reuses
   that mapping; the operand carries `elem_kind` only when the
   compiler needs a single generic emit point (the comprehension /
   spread accumulator) rather than 15 per-kind branches at the call
   site.

**Refinement.** The cleanest form: the comprehension/spread
accumulator emit resolves the destination `ConcreteType::Array<T>` →
`TypedArrayKind` via `should_use_typed_array`, then emits
`kind.new_opcode()` with `Operand::Count(0)` — i.e. it reuses the
EXISTING typed-array opcodes (`NewTypedArrayI64`, `NewTypedArrayF64`,
…, `NewTypedArrayTypedObject`) directly, exactly as the non-empty
typed-literal path at `collections.rs:273-312` already does. A NEW
`Operand::TypedArrayAlloc` operand is only required if the compiler
genuinely cannot resolve a single `TypedArrayKind` at the emit site
and must defer the kind to a runtime-threaded operand — which, given
the comprehension element type and the binding `ConcreteType::Array<T>`
are both compile-time-known, it CAN. **Therefore the recommended
concrete shape is option (b) realized WITHOUT a new operand: emit the
existing `kind.new_opcode()` with `Count(0)` at the accumulator
site, picking `kind` from the proven destination/element
`ConcreteType`.** This is the minimal §2.7.5-compliant change and
needs zero new opcode / operand surface. A new `Operand::TypedArrayAlloc`
is the fallback only if the supervisor wants a single generic emit
point across all 10 `Count(0)` sites; that is a density-vs-surface
trade the supervisor can rule on, but it is not functionally
required.

**Heterogeneous-element accumulator** (E3 territory, mixed spread):
remains surface-and-stop per W16.1 §6.B.2 — no fast-path emission,
honest structured compile error. NOT closed by W16.2-C.

module: std::core::queryable: expected something else, found

This is NOT the `op_new_array` SURFACE — it is a `queryable.shape`
PARSE error. Root cause located precisely:

`crates/shape-runtime/stdlib-src/core/queryable.shape:37`:

```
    filter(predicate: (T) => bool): Self,
```

Line 37 uses a TypeScript-style method declaration (`name(params):
ReturnType,`) while every sibling line (39+) uses the correct Shape
trait-method syntax (`method map(transform) -> Self;`). The Shape
parser rejects the bare `filter` identifier where it expects the
`method` keyword. Confirmed in isolation: a 3-line trait with line 37's
exact shape produces `error[E0001]: unexpected identifier 'filter',
expected something else`; the corrected `method filter(predicate:
(T) => bool) -> Self;` parses clean.

`queryable.shape` is pulled in transitively by the prelude / stdlib
module graph that `with_modules(&["core/ode.shape"], ...)` and
`with_modules(&["physics/collision.shape"], ...)` load. The parse
error fires at module-load time before any test code runs. This is a
**stdlib source defect**, a distinct class from `op_new_array`.

(plus `Mul`/`Sub` siblings). This originates inside the stdlib
`core/ode.shape` module. `rk4_system` (`ode.shape:82`) is an
UNANNOTATED generic function: `pub fn rk4_system(f, y0_vec, t_start,
t_end, dt)`. The `vec_sub` / `vec_norm` / `vec_add` helpers are also
unannotated (`function vec_sub(a, b) { ... a[i] - b[i] ... }`). When
`rk4_system` calls `f(t, y)` (the closure result) and feeds it through
`vec_add` / `vec_add_scaled`, the closure-result + generic-helper
return types resolve to `unknown` and the `Add`/`Sub`/`Mul` operations
inside the helpers fail strict-typing inference. This is a
**generic-function-call-return-type inference loss** — the same class
the recent epsilon-4 commit (`a9b9ce15` "resolve function-call
argument return types in `concrete_type_for_expr`") targeted, just not
yet covering this `unannotated-generic-fn → closure-result →
unannotated-helper` chain. The `let mut results = []` empty literal in
`rk4_system` IS W16.2-C territory (E1/E2 family) — but the test never
reaches array construction; it fails at compile-time type inference of
`vec_sub`/`vec_add` first.

### §5.D JIT-side parallel

`statements.rs:144` `ArrayStore`) are a SEPARATE territory — they fire
